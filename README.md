## AI อ่านข้อมูลตามงาน (11 ตุลาคม 2026)

Web Chat ที่ตั้งโมเดลแล้วไม่ส่งบัญชี ยอด และแผนทั้งหมดตั้งแต่เริ่มคุย ใช้เครื่องมือค้นเฉพาะข้อมูลที่จำเป็นพร้อมแบ่งหน้า รายงานรายเดือนคำนวณยอดครบจาก backend และส่งรายละเอียดแบบจำกัดขนาด รูปย้อนหลังไม่แนบทุกข้อความ การบันทึก/แก้ยังทวนและรอพิมพ์ **ยืนยัน** อ่านรายละเอียดและขอบเขตที่ [ผู้ช่วย AI](docs/AI_ASSISTANT.md#อ่านข้อมูลตามงานและรองรับประวัติเพิ่มขึ้น)

อัปเดตฐานข้อมูลด้วย migration ตามขั้นตอนเดิม ไม่ต้องเพิ่ม API key หรือค่าใหม่ใน `.env` เวอร์ชันนี้เพิ่มดัชนีฐานข้อมูล; ฐานใหญ่ควรสำรองและอัปเดตช่วงใช้งานน้อย เพราะการสร้างดัชนีปกติอาจรอ/กั้นการเขียนชั่วคราว

เว็บจัดการรายรับรายจ่ายแบบ self-hosted ภาษาไทย โทนสว่างขาวนวล–เขียวอ่อน: Next.js/TypeScript/Tailwind/shadcn-style UI, FastAPI/SQLAlchemy/Alembic, PostgreSQL, Redis + worker และ Telegram aiogram

**เริ่มใช้งานได้โดยไม่ต้องมี API key** ระบบเริ่มด้วย mock/demo และไม่บันทึกเงินจาก AI อัตโนมัติ จำนวนเงินใช้ integer สตางค์ รองรับ THB เท่านั้นในรุ่นนี้

## ยืนยันอีเมลและกู้รหัสผ่าน

หน้าเข้าสู่ระบบมี “ลืมรหัสผ่าน?” และ **ตั้งค่า → บัญชีผู้ใช้ → ยืนยันอีเมล** สมัครบัญชีใหม่เมื่อเปิดการส่งอีเมลจะเข้าคิวลิงก์ยืนยันให้ด้วย บัญชีเดิมและบัญชีจากคำเชิญขอลิงก์ในตั้งค่าได้ รุ่นนี้การยืนยันอีเมลเป็นทางเลือก ยังไม่บังคับก่อนเข้าสู่ระบบและยังเปลี่ยนอีเมลเองไม่ได้

การส่งอีเมลปิดไว้เป็นค่าเริ่มต้น ตั้งค่าใน `.env` เฉพาะ backend แล้วสร้างคอนเทนเนอร์ api/worker ใหม่:

```dotenv
MAIL_ENABLED=true
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_FROM=finance@example.com
```

ใช้ค่าของบริการ SMTP ที่คุณดูแล รองรับ `starttls` (ทั่วไปพอร์ต 587) หรือ `ssl` (ทั่วไปพอร์ต 465) ตรวจใบรับรอง TLS เสมอ ไม่มีโหมด plaintext ตั้ง `APP_ORIGIN` ให้ตรงกับ URL ที่ผู้ใช้เปิดจริง และใช้ HTTPS เมื่อเปิดนอก localhost ไม่ส่งผ่าน provider AI หรือ Telegram และไม่ส่งอีเมลจริงจนกว่าจะตั้งค่า ระบบไม่แสดง SMTP credentials ผ่านเว็บ

ลิงก์ตั้งรหัสผ่านมีอายุ 30 นาที ลิงก์ยืนยันอีเมล 24 ชั่วโมง ใช้ได้ครั้งเดียว การขอใหม่ทำให้ลิงก์ประเภทเดิมใช้ไม่ได้ เปิดลิงก์แล้วต้องกดปุ่มยืนยันเอง ส่วน token อยู่ใน URL fragment ซึ่งไม่ถูกส่งเป็น query ไปที่เซิร์ฟเวอร์ และหน้าเว็บนำออกจากแถบที่อยู่ทันทีหลังอ่าน ไม่มีการเปลี่ยนรหัสผ่านจาก GET หรือการเปิดอีเมลเฉย ๆ

การตั้งรหัสผ่านใหม่เพิกถอนเซสชันทั้งหมดและลิงก์ที่ค้างอยู่ ยืนยันการครอบครองอีเมลไปด้วย จากนั้นต้องเข้าสู่ระบบใหม่ การเปลี่ยนรหัสผ่านจากตั้งค่าก็ยกเลิกลิงก์กู้รหัสผ่านเดิม คำตอบขอกู้รหัสผ่านเหมือนกันสำหรับอีเมลที่มีและไม่มีบัญชี และมี rate limit ป้องกันการส่งซ้ำ

คิวอีเมลบันทึกพร้อม token ใน transaction เดียวกัน เก็บ token สำหรับตรวจสอบเป็น hash และเข้ารหัสเนื้อหา outbox ด้วย `ENCRYPTION_KEY` ก่อน worker ส่ง ลบเนื้อหาหลังส่ง/ยกเลิก/หมดอายุ/ส่งล้มเหลวครบ 3 ครั้ง (เว้น 60 และ 120 วินาที) worker ตรวจทุกวงรอบและไม่เก็บข้อผิดพลาด SMTP ที่มีข้อมูลส่วนตัว หาก worker หยุดก่อนบันทึกผล อีเมลเดิมอาจส่งซ้ำได้ แต่ token ยังใช้ได้ครั้งเดียว ต้องเก็บสำรอง `ENCRYPTION_KEY` คู่กับฐานข้อมูล

ยังไม่ได้ทดสอบส่งผ่าน SMTP จริงหรือรับอีเมลจากบริการภายนอก ผลทดสอบครอบคลุมคิว การเข้ารหัส TLS transport ที่จำลอง ลิงก์ใช้ซ้ำ/หมดอายุ/พร้อมกัน และหน้าเว็บ ยังไม่รวม 2FA รายการอุปกรณ์ หรือการบังคับยืนยันอีเมลก่อนเข้าใช้

## แชทภาษาธรรมชาติและ Telegram

โมเดลตีความคำถามเป็นเจตนา/วันที่/ตัวกรองที่ backend ตรวจได้แล้ว เช่น “อาทิตย์ก่อนฉันจ่ายอะไรบ้าง”, “รายจ่ายเจ็ดวันที่ผ่านมา” หรือ “รายจ่ายกันยาเป็นไงบ้าง” ถ้าบัญชี/หมวดหรือช่วงเวลากำกวมจะถามเพิ่ม ไม่เดาหรือบันทึกอัตโนมัติ ใช้ได้ทั้งเว็บและ Telegram ดูขอบเขตและข้อจำกัดใน [คู่มือ AI Assistant](docs/AI_ASSISTANT.md)

รายงาน AI กรองคำค้น เช่น “กาแฟเดือนนี้” และรวมผลตรงเงื่อนไขครบทุกหน้า รองรับเดือนย่อ เช่น ก.ย. 2569 ถามงบคงเหลือและเปรียบเทียบเดือนนี้กับเดือนก่อนจาก backend ได้ ผลค้นแสดงวัน/บัญชี/หมายเลขเลือก และ Telegram เก็บผลยืนยันไว้ในคิวส่งซ้ำหากเครือข่ายสะดุด โดยไม่บันทึกเงินซ้ำ

Telegram พิมพ์ `/new` หรือ `/reset` เพื่อเริ่มห้องใหม่ เก็บประวัติเก่าไว้บนเว็บ ยกเลิกร่าง/คำตอบค้างในห้องเดิม และไม่กระทบรายการเงินจริง แชทยาวจำกัดประวัติพร้อมบันทึกย่อจากข้อความผู้ใช้เก่าในเครื่องโดยไม่เรียกโมเดลเพิ่ม ดู [ขอบเขตบริบท](docs/AI_ASSISTANT.md#บริบทบทสนทนายาว)

พิมพ์ “เมื่อกี้จ่ายค่ากาแฟ 75 จากเงินสด”, “กินข้าว 80.50 เมื่อวาน”, “รับเงินเดือน 30,000 บาท”, “โอน 500 จากเงินสด ไปธนาคาร” หรือ “จ่ายบัตร 200 จากเงินสด ไปบัตรเครดิต” ได้ ระบบเตรียมรายการ ทวนยอด/วัน/บัญชี/หมวด แล้วให้พิมพ์ `ยืนยัน` ภายใน 15 นาที จึงลง ledger เหมือนกันทั้งเว็บและข้อความใน Telegram ที่เชื่อมบัญชีแล้ว รูปพร้อมคำบรรยายจาก Telegram ใช้ AI Chat เดียวกับเว็บ ทวนและพิมพ์ ยืนยัน ใน Telegram ได้เลย โดยต้องส่งข้อความทวนครบก่อน ไม่รับคำยืนยันจากภาพหรือข้อความโมเดล

ถ้ามีหลายบัญชีหรือไม่รู้หมวด ระบบถามต่อในห้องเดิม ตอบชื่อบัญชีหรือ `หมวด ชื่อหมวด` ภายใน 15 นาทีได้ ใช้ `ยกเลิกการกรอก` เพื่อเริ่มใหม่ หลังยืนยันในห้องนั้นแล้วใช้ “แก้รายการล่าสุดเป็น 90 บาท” เพื่อทวนก่อน–หลัง และยืนยันอีกครั้ง ระบบเก็บประวัติการแก้ ไม่เขียนทับ ledger เดิม คำว่า “ล่าสุด” อ้างอิงรายการที่คุณยืนยันในห้องนั้นเท่านั้น ไม่เลือกจากข้อมูลของสมาชิกอื่น

เมื่อไม่ได้ตั้ง Chat model การอ่านภาษาธรรมชาติใช้กฎภาษาไทยที่ตรวจสอบได้และไม่ต้องมี API key แนะนำหมวดอาหาร/เดินทางจากคำที่รู้จัก และใช้บัญชีอัตโนมัติเฉพาะกรณีมีตัวเลือกเดียว ทุกค่าต้องตรวจจากข้อความทวน รองรับหนึ่งรายการต่อข้อความ หากยอดหลายจำนวน/วันที่ผิด/บัญชีหรือหมวดกำกวมจะไม่สร้างรายการ ไม่ได้รองรับภาษาธรรมชาติทุกสำนวนหรือการสั่งแก้ข้อมูลทุกประเภท

เว็บโหลดครั้งละ 50 ข้อความและเลื่อนขึ้นเพื่อโหลดข้อความเก่าต่อเนื่อง รักษาข้อความที่โหลดแล้วระหว่างรอคำตอบใหม่ ปุ่มค้นหาแชทยังใช้เปิดข้อความเก่าเฉพาะจุดได้ Telegram ตรวจ membership/archive อีกครั้งและกันข้อความ message ID ซ้ำก่อนทำงาน รหัสยืนยันผูกผู้ใช้/พื้นที่/ห้อง การต่อ Telegram จริงยังต้องตั้ง token และตรวจบนเครื่องปลายทาง

## PWA และพื้นที่ออฟไลน์

เปิด **ตั้งค่า → ติดตั้งแอปและออฟไลน์** ติดตั้งจากปุ่มเมื่อเบราว์เซอร์รองรับ หรือเมนู “เพิ่มลงในหน้าจอหลัก” บน iPhone ใช้ Safari → แชร์ → เพิ่มลงในหน้าจอโฮม ต้องใช้ HTTPS หรือ localhost การติดตั้งบนมือถือจริงยังไม่ได้ตรวจในรุ่นนี้ ดู [แนวทางติดตั้ง PWA ของ MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/How_to/Trigger_install_prompt)

ข้อมูลออฟไลน์ **ปิดโดยค่าเริ่มต้น** เลือกเก็บยอดบัญชีและ 100 รายการล่าสุดของหนึ่ง workspace บนเครื่องได้ ตั้งรหัสออฟไลน์ 12–200 ตัวอักษรแยกจากรหัสเข้าสู่ระบบ ข้อมูลและร่างเข้ารหัส AES-256-GCM โดยใช้ PBKDF2-SHA256 210,000 รอบ พร้อม salt/IV ใหม่ทุกครั้ง ไม่เก็บรหัสปลดล็อกไว้ หากลืมรหัสต้องล้างข้อมูลบนเครื่องแล้วเลือกเก็บใหม่ ร่างเก่าจะหาย ยอดที่เก็บเป็น snapshot พร้อมเวลาบันทึก ไม่ใช่ยอดล่าสุด

เมื่อเปิดแอปขณะขาดอินเทอร์เน็ตจะเข้าสู่ `/offline.html` ปลดล็อกดูข้อมูลและเก็บ/แก้/ลบร่างข้อความได้สูงสุด 20 ร่าง (ร่างละ 4,000 ตัวอักษร) เมื่อออนไลน์ต้องกดส่งร่างเอง ระบบตรวจบัญชีที่ login และสิทธิ์ใน workspace เตรียมข้อความทวน แล้วให้พิมพ์ยืนยันพร้อมรหัสก่อนลงยอด ไม่มี background posting หรือ auto-sync ledger เปิดห้องแชทบนเว็บจากร่างเพื่อคุยต่อได้

Service worker cache เฉพาะไฟล์แอปสาธารณะ ไม่ cache API, cookies, รูปแชท หรือหน้าเว็บที่มีข้อมูลการเงิน ข้อมูลออฟไลน์ไม่รวมประวัติแชท รูปสลิป หรือ API keys ล็อกเมื่อแท็บไปอยู่เบื้องหลัง ล้าง vault และร่างเมื่อออกจากระบบ มี generation guard ป้องกันการเข้ารหัสที่ยังทำงานเขียนข้อมูลกลับหลัง logout ข้อมูลที่เลือกเก็บไว้ยังดูออฟไลน์ได้ด้วยรหัสจนกว่าจะล้างหรือออกจากระบบ การเพิกถอนสิทธิ์บนเซิร์ฟเวอร์ลบ snapshot บนอุปกรณ์ที่ออฟไลน์ทันทีไม่ได้ แต่การส่งและยืนยันต้องตรวจสิทธิ์ออนไลน์ใหม่เสมอ

ดู [หลักการ service worker และ offline ของ MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation) แอปรุ่นนี้ไม่รองรับ AI ตอบขณะออฟไลน์หรือการลง ledger ขณะออฟไลน์

## สมัครบัญชีผ่านเว็บ (เปิด–ปิดได้)

ตั้ง `ALLOW_REGISTRATION=true` ใน `.env` แล้วใช้ `docker compose up -d --force-recreate api worker` จากนั้นหน้าเข้าสู่ระบบจะแสดงปุ่มสมัคร และเปิด `/register` ได้ สมัครด้วยอีเมล ชื่อที่แสดง และรหัสผ่าน 12–200 ตัวอักษร พร้อมยืนยันรหัสผ่าน เมื่อสำเร็จจะเข้าสู่ระบบและได้ workspace ส่วนตัวใหม่ ไม่มีการเข้าร่วมพื้นที่ของผู้ใช้อื่นโดยอัตโนมัติ

ค่าเริ่มต้น `ALLOW_REGISTRATION=false` ปิดทั้งปุ่มและ API สมัครสาธารณะ การเข้าสู่ระบบของบัญชีเดิมและการสมัครด้วยคำเชิญยังใช้ได้ตามปกติ หากต้องการปิดภายหลังให้เปลี่ยนเป็น `false` แล้วใช้คำสั่งเดียวกัน บัญชีที่สมัครไปแล้วจะยังใช้งานได้ ไม่ต้องสร้าง frontend image ใหม่เมื่อเปลี่ยนค่านี้

การสมัครจำกัดจำนวนคำขอตาม IP และอีเมล รหัสผ่านเก็บเป็น Argon2 hash และ session เป็น HttpOnly cookie ตรวจที่มาและป้องกันการส่งรหัสผ่านกลับในข้อความ validation ระบบส่งอีเมลยืนยันและกู้รหัสผ่านเปิดได้เมื่อผู้ดูแลตั้งค่า SMTP การเปิดสมัครหมายถึงใครก็ตามที่เข้าถึงเว็บไซต์สามารถสร้างบัญชีส่วนตัวได้

## จัดการพื้นที่ทำงานและบัญชีแยกคน

เปิด **บริการทั้งหมด → จัดการพื้นที่ทำงาน** (`/workspaces`) เพื่อสร้าง/ค้นหาพื้นที่ แบ่งครั้งละ 6 พื้นที่ ดูบทบาท จำนวนสมาชิกและรายการบัญชีรวมประวัติ เจ้าของเปลี่ยนชื่อ เก็บเข้าคลัง และกู้คืนได้ สมาชิกไม่มีสิทธิ์ดำเนินการเหล่านี้ การเปลี่ยนชื่อ/สถานะมี version check ป้องกันการใช้หน้าจอเก่าเขียนทับข้อมูลล่าสุด

- **เก็บเข้าคลัง:** พิมพ์ชื่อพื้นที่ให้ตรงก่อนยืนยัน พื้นที่หายจากตัวสลับปกติ สมาชิกเข้าข้อมูล/API/SSE ไม่ได้ คิว AI, Telegram capture/link และการสร้างข้อเสนอรายการประจำพักไว้ ข้อมูลการเงินและสมาชิกเดิมยังอยู่
- **กู้คืน:** เจ้าของเข้าหน้านี้ได้แม้ไม่มีพื้นที่ที่กำลังใช้งาน คิวที่ยังใช้ได้กลับมาทำงาน รายการประจำอาจสร้างข้อเสนอรอบค้างตามขอบเขต batch เดิม โดยไม่ลง ledger อัตโนมัติ อายุคำเชิญ/แชทชั่วคราวและนโยบายล้างประวัติยังเดินตามเวลาเดิม
- **ลบถาวร:** ทำได้เฉพาะพื้นที่เริ่มต้นที่มีคุณคนเดียว มีแต่บัญชี/หมวดเริ่มต้น และยังไม่มีรายการ แชท ข้อเสนอ คำเชิญ/ประวัติ สมาชิกอื่น provider การตั้งค่า หรือข้อมูลเพิ่มเติม ต้องพิมพ์ชื่อยืนยัน ตรวจสิทธิ์และข้อมูลจริงอีกครั้งใต้ workspace lock ก่อนลบ ไม่ลบผู้ใช้หรือ session พื้นที่ที่มีประวัติใช้เก็บเข้าคลัง; รุ่นนี้ไม่มีการล้างประวัติการเงินถาวร

**ให้เพื่อนใช้งานแยกคน:** เจ้าของพื้นที่ที่กำลังใช้งานเปิดส่วน “ให้เพื่อนมีบัญชีส่วนตัว” ระบุอีเมลและสร้างรหัส ให้เพื่อนเปิด `/join` บนเซิร์ฟเวอร์เดียวกัน ใส่อีเมล/รหัสเชิญ แล้วตั้งรหัสผ่านของตัวเอง เพื่อนได้พื้นที่ส่วนตัวใหม่และไม่มีสมาชิกในพื้นที่ของผู้เชิญ แต่ละบัญชีมีสิทธิ์เข้าถึงเฉพาะพื้นที่ที่เป็นสมาชิก การแยกสิทธิ์นี้เป็นระดับแอป ผู้ดูแลฐานข้อมูล/ไฟล์สำรองยังเข้าถึงข้อมูลบนเซิร์ฟเวอร์ได้ตามสิทธิ์ของตน

รหัสสร้างบัญชีส่วนตัวเป็น **คนละประเภท** กับคำเชิญ “เข้าร่วมพื้นที่” เดิม หากต้องการแชร์ข้อมูลกับเพื่อนภายหลัง ให้เชิญจากหน้าสมาชิกอีกครั้ง ทั้งสองประเภทผูกอีเมล ใช้ได้ครั้งเดียว/7 วัน เก็บเฉพาะ hash ในฐานข้อมูล เปิดรหัสให้คัดลอกเฉพาะตอนสร้าง ซ่อนรหัสได้ และยกเลิกจากหน้าสมาชิกของพื้นที่ที่ออกคำเชิญ ไม่มีอีเมลส่งอัตโนมัติ และไม่สร้างรหัสผ่านแทนผู้รับ การสมัครสาธารณะแยกควบคุมด้วย `ALLOW_REGISTRATION`

## บันทึกและแก้ไขผ่าน Web Chat

คุยเหมือนบอกเลขาได้เลย ไม่ต้องกรอกตามช่อง เช่น:

```text
คุณ: ช่วยจดค่ากาแฟให้หน่อย
ผู้ช่วย: ยอดเท่าไหร่คะ?
คุณ: 75 บาทค่ะ
ผู้ช่วย: ใช้บัญชีไหนคะ? เงินสด, ธนาคาร
คุณ: เงินสดจ้า
ผู้ช่วย: [ทวนรายจ่าย 75 บาท พร้อมวันที่ บัญชี และหมวด]
คุณ: จริง ๆ 90 บาท
ผู้ช่วย: [ทวนยอดใหม่ 90 บาท]
คุณ: ยืนยัน
```

รองรับรายรับ รายจ่าย โอนเงิน และจ่ายบัตร ระบบถามเฉพาะข้อมูลที่ยังขาด ใช้ชื่อบัญชี/หมวดในพื้นที่ และทวนข้อมูลก่อนลง ledger พิมพ์แค่ **`ยืนยัน`** หรือ **`ยกเลิก`** ภายใน 15 นาที เว็บผูกการยืนยันกับข้อความทวนล่าสุดที่ไคลเอนต์แสดงอยู่ หากมีข้อเสนอใหม่หรือมีข้อความอื่นแทรก จะให้พิมพ์ **`ทวนอีกที`** ก่อน ไม่เลือกข้อเสนอข้ามห้อง/ผู้ใช้/workspace ยืนยันซ้ำไม่เพิ่มรายการ รหัส `ยืนยัน CODE` ยังรองรับสำหรับไคลเอนต์เดิม แต่ไม่จำเป็นและซ่อนจากข้อความทวนบนเว็บ

แก้ก่อนบันทึก: `จริง ๆ 90 บาท` / `แก้ยอดเป็น 90` / `เอาเป็น 90 บาท` สร้างข้อเสนอใหม่ให้ตรวจอีกครั้ง ไม่เปลี่ยนยอดเงินจริง แก้รายการที่ยืนยันแล้ว: `แก้รายการล่าสุดเป็น 95 บาท` หรือเปิดรายละเอียดรายการ → “คัดลอกคำขอแก้ผ่านแชท” → วางและปรับช่อง ระบบทวน **ก่อน/หลัง** แล้วรอ `ยืนยัน` เก็บต้นฉบับ+กลับรายการ+รายการทดแทนพร้อม audit trail การบันทึก/สถานะข้อเสนอ/ข้อความยืนยัน commit พร้อมกัน ถ้าล้มเหลว rollback ทั้งคำขอ

หากตั้งโมเดลงาน **Chat** ไว้ คุยเรื่องทั่วไปหรือถามต่อได้ตามปกติ โมเดลรับประวัติช่วงล่าสุดและข้อมูลบัญชี/หมวดที่มีสิทธิ์ใช้ เมื่อขอจดเงิน โมเดลใช้ function tool `prepare_transaction` เพื่อเสนอร่าง และใช้ `prepare_management_plan` เพื่อเสนอแผนบัญชี/หมวด/งบ/เป้าออม/รายการประจำ สูงสุด 10 ขั้นตอนที่ยืนยันครั้งเดียวได้ ระบบตรวจจำนวนเงิน บัญชี หมวด วันที่ และ tenant ก่อนสร้างข้อความทวน โมเดลไม่มีสิทธิ์ยืนยันหรือเขียน ledger; JSON ตัวอย่างหรือคำว่า “ยืนยัน” ที่โมเดลตอบไม่กลายเป็นคำสั่งผู้ใช้ คำตอบทั่วไปทยอยแสดงได้ แต่ไม่แสดง arguments ของ tool หรือ reasoning fields

แนบรูปพร้อมข้อความ เช่น “ช่วยจดค่าอาหารในรูปนี้ จ่ายจากเงินสด” ได้ ถ้า Chat model รองรับ vision และเปิด **รับรูปภาพในแชท** ในศูนย์ตั้งค่า AI ผู้ช่วยอ่านรูป ถามข้อมูลที่ขาด แล้วทวนพร้อมหลักฐานในห้องเดิม พิมพ์ **ยืนยัน** จึงบันทึก หากยังไม่มีโมเดลอ่านรูปจะบอกตามจริงและไม่เดายอด ไม่มีข้อเสนอ pending ใน Inbox จากรูปแชทใหม่

ตั้ง **Thinking แยกแต่ละโมเดล** ใน `/ai-settings`: ค่าเริ่มต้น/ปิด/น้อยมาก/น้อย/ปานกลาง/มาก/มากพิเศษ ตามที่ provider และรุ่นรองรับ เลือกโมเดลสำหรับงาน Chat จัดลำดับสำรอง เปิดรับรูปตามความสามารถจริง และเพิ่ม timeout/token budget เมื่อใช้ thinking มาก ดูข้อจำกัดและตัวอย่างที่ [คู่มือ AI Assistant](docs/AI_ASSISTANT.md)

แชทใช้ลำดับ AI ของ workspace ทุกห้อง; Cloud ต้องเปิดในศูนย์ตั้งค่า AI ของพื้นที่ หากไม่ได้ตั้งโมเดลหรือใช้ demo fallback ยังช่วยจดด้วยกฎภาษาไทยและถามต่อได้ แต่ไม่ใช่ AI อิสระทุกสำนวน รายงานที่รองรับใช้ตัวเลขที่ backend คำนวณจาก ledger แล้วให้โมเดลเรียบเรียง ไม่ให้โมเดลเขียน SQL หรือคำนวณยอดแทนระบบ

โมเดลสร้าง/เปลี่ยนชื่อบัญชีและหมวด ตั้ง/แก้/นำงบออก/คัดลอกงบ สร้าง/แก้/เก็บเป้าออม และสร้าง/พัก/เปิดรายการประจำได้ ทวนแผนก่อนยืนยันและมีประวัติงานถาวรหลังลบแชท ยังไม่รองรับแก้ไขอิสระทุกชนิด การแก้รายการที่บันทึกแล้วใช้คำสั่งที่ระบุข้างต้น ไม่แก้ยอดตั้งต้น ชนิดบัญชี สมาชิก รหัสผ่าน หรือ API keys และไม่ลบรายการเงินผ่านแชท Telegram ยังใช้กฎภาษาไทย/คำยืนยันสั้นและภาพเข้า Inbox; สนทนาผ่านโมเดล/vision แบบเลขารอบนี้ใช้เฉพาะ Web Chat ลบห้องแล้วร่างหาย แต่รายการที่ยืนยันแล้ว ประวัติแก้ไข และรูปหลักฐานการเงินยังอยู่

## เริ่มใช้งานบน Ubuntu Server / Hyper-V

เตรียม Ubuntu VM ที่มี Docker Engine และ Compose v2.24.4 ขึ้นไป ([คู่มือติดตั้ง Docker บน Ubuntu](https://docs.docker.com/engine/install/ubuntu/)) เริ่มต้นแนะนำ 2 vCPU, RAM 4 GB และพื้นที่ว่าง 10 GB ไม่รวมโมเดล Ollama ไม่ต้องมี GPU สำหรับ mock หรือ Cloud AI

คัดลอกโฟลเดอร์นี้ไปยัง VM แล้วทำงานจากโฟลเดอร์ `smart-finance`:

```sh
python3 scripts/configure.py
docker compose up -d --build
docker compose ps
docker compose exec api python -m app.bootstrap
```

คำสั่งสุดท้ายถามอีเมลและรหัสผ่าน (อย่างน้อย 12 ตัวอักษร, ไม่แสดงรหัสผ่านขณะพิมพ์) แล้วสร้าง workspace ส่วนตัวพร้อมเงินสดและหมวดเริ่มต้น ไม่มีผู้ใช้หรือรหัสผ่านตายตัว ผู้ใช้คนถัดไปสร้างด้วยคำสั่งเดียวกัน หรือใช้รหัสเชิญที่เจ้าของพื้นที่สร้างให้ได้ การสมัครสาธารณะเปิดได้ด้วย ALLOW_REGISTRATION=true (ค่าเริ่มต้นปิด)

ค่าเริ่มต้นผูกเว็บกับ `127.0.0.1:8080` ของเซิร์ฟเวอร์ เพื่อเข้าจากเครื่อง Windows/เครื่องที่ใช้ Hyper-V ให้เปิด SSH tunnel:

```sh
ssh -L 8080:127.0.0.1:8080 ubuntu@VM_IP
```

เปิด [http://localhost:8080](http://localhost:8080) บนเครื่องที่เปิด tunnel แล้วล็อกอิน PostgreSQL, Redis, API และ Ollama ไม่มีพอร์ตที่เปิดออกนอก Docker network

1. ไป “บริการทั้งหมด → บัญชี” เพิ่มบัญชีธนาคารหรือบัตรเครดิต หมวดรายรับ/รายจ่ายจัดการแยกที่ “หมวดหมู่”
2. กด “เพิ่มรายการ → ยอดตั้งต้น” ก่อนมีรายการอื่นในบัญชี ยอดตั้งต้นบัตรคือยอดหนี้
3. บันทึกรายรับ รายจ่าย โอน หรือจ่ายบัตร แล้วดู Dashboard
4. AI Inbox รับข้อความ เช่น `ข้าว 75 น้ำ 25` และรูปสลิป ต้องเลือกบัญชี หมวดหมู่ วันที่และตรวจยอดก่อน “ยืนยันและบันทึก”
5. Web Chat เปิดได้ทันทีและใช้ลำดับ AI ของ workspace หรือ mock เก็บประวัติบนเซิร์ฟเวอร์ และแนบรูปสลิปพร้อมข้อความได้

ตรวจสุขภาพ API ที่ `/api/health` และเอกสาร API ที่ `/api/docs` คำขอ API ที่แก้ข้อมูลต้องมี header `X-SF-Request: 1` และ cookie session (ยกเว้น login/preview/register-invite) ถ้ามี Origin ต้องตรงกับ `APP_ORIGIN` หน้าเว็บจัดการให้อยู่แล้ว

### ตัวอย่างข้อมูลสาธิต (ทางเลือก)

```sh
python3 scripts/seed_demo.py
```

สร้างผู้ใช้สาธิตและ workspace แยก มีตัวอย่างเงินเดือน โอนเงิน ซื้อด้วยบัตรและจ่ายบัตร รหัสผ่านสุ่มเก็บใน `artifacts/demo-access.json` (สิทธิ์ 0600, ไม่อยู่ใน source archive/Git) สคริปต์ไม่ทับผู้ใช้เดิม ข้อมูล demo แสดงธุรกรรมสมมติและไม่เกี่ยวกับบัญชีเงินจริง ใช้ผู้ใช้ใหม่จาก bootstrap สำหรับข้อมูลส่วนตัว

## ใช้ Nginx ที่มีอยู่แล้ว

รองรับ Nginx เดิมบน host โดยส่งมาที่ `127.0.0.1:8080` และมี `compose.nginx.yaml` สำหรับเปลี่ยน gateway เป็น Nginx ทั้งหมด พร้อม config สำหรับ SSE/อัปโหลด/ปิด cache ดู [วิธีติดตั้ง Nginx](docs/NGINX.md) แล้วตั้ง `APP_ORIGIN` เป็น HTTPS URL จริงกับ `COOKIE_SECURE=true`

## HTTPS และการเข้าจากภายนอก

สำหรับโดเมนที่ชี้เข้าเซิร์ฟเวอร์ ตั้งค่าใน `.env`:

```dotenv
APP_DOMAIN=finance.example.com
APP_ORIGIN=https://finance.example.com
COOKIE_SECURE=true
```

แล้วใช้ Caddy HTTPS configuration:

```sh
docker compose -f compose.yaml -f compose.https.yaml up -d --build
```

Caddy ขอ certificate เมื่อ DNS/พอร์ต 80/443 เข้าถึงได้ เก็บ certificates ใน volume ของตัวเอง หากใช้ Tailscale/Cloudflare Tunnel/reverse proxy เดิม ให้ proxy มาที่ localhost:8080 และตั้ง APP_ORIGIN เป็น HTTPS URL ที่ใช้งานจริง เปิด COOKIE_SECURE=true อย่าส่งรหัสผ่านผ่าน HTTP บน LAN/อินเทอร์เน็ต การเปิด HTTP แบบเริ่มต้นมีไว้สำหรับ localhost/SSH tunnel เท่านั้น

Hyper-V ใช้ network switch ที่เครื่องผู้ใช้ SSH เข้าถึง VM ได้ ไม่ต้องเปิด PostgreSQL/Redis ออกสู่ Windows host หรืออินเทอร์เน็ต

## AI และ Privacy

| โหมด | เส้นทางข้อมูล |
|---|---|
| Web Chat — ปิด Cloud AI | ใช้ Ollama ที่เปิดไว้ตามลำดับ หรือ mock; ไม่ fallback ไป Cloud |
| Web Chat — เปิด Cloud AI | ทุกห้องใช้ลำดับโมเดล/fallback ของ workspace ทั้ง Local และ Cloud ที่เปิดไว้ |
| Inbox/Telegram | Inbox เลือก Private/Standard ต่อการรับข้อมูลได้; Telegram ใช้ Private/Ollama/mock ตามเดิม |

ทุกโหมดใช้ PostgreSQL ระหว่างประมวลผล รองรับแชทชั่วคราว/ตั้งอายุประวัติแล้ว แต่ยังไม่มี Incognito แบบไม่เขียนดิสก์ ผู้ดูแลต้องตั้ง OLLAMA_URL ไปยังเซิร์ฟเวอร์ภายในจริงจึงจะเป็น local-only ตามความหมายทาง deployment; ค่า URL มาจากผู้ดูแลเท่านั้น ผู้ใช้เว็บแก้ปลายทางไม่ได้

### Ollama ภายใน Compose

```sh
docker compose --profile local-ai up -d ollama
docker compose exec ollama ollama pull MODEL_NAME
```

ค่าเริ่มต้น `OLLAMA_URL=http://ollama:11434/v1` จากนั้น Settings เพิ่ม provider `ollama`, ชื่อโมเดลที่ติดตั้งจริง และเลือกงาน `chat` หรือ `extract` การอ่านรูปต้องใช้โมเดลที่รองรับภาพ ขนาด/ความเร็วโมเดลขึ้นกับ RAM/CPU ที่จัดให้ VM หากมี Ollama หลายเครื่อง ใส่ **Ollama Base URL** แยกแต่ละโมเดลจากเว็บ เช่น `http://192.168.1.20:11434/v1` หรือ IP Tailscale เว้นว่างใช้ค่าเริ่มต้นเดิม URL ต้องเข้าถึงได้จาก backend Docker

### Cloud / OpenAI-compatible

1. เปิด **ตั้งค่า → เปิดศูนย์ตั้งค่า AI** หรือ `/ai-settings` (เฉพาะเจ้าของพื้นที่)
2. เปิด **อนุญาต Cloud AI** สำหรับพื้นที่นี้ ไม่ต้องแก้ `.env` หรือ restart หลังบันทึก
3. เพิ่ม Gemini, OpenRouter, Groq, OpenAI หรือ **Custom API** ใส่ชื่อโมเดล/คีย์ และเลือกงานแชทหรืออ่านข้อความ/สลิป
4. Custom API รับ Base URL เช่น `https://api.example.com/v1` ผ่านเว็บ รองรับ OpenAI-compatible HTTP/HTTPS รวม LAN/Tailscale/Docker และพอร์ตอื่น เช่น `http://192.168.1.30:8081/v1` ไม่มี credentials/query/fragment และไม่ redirect; ตรวจ DNS และ pin IP พร้อม Host/port/TLS SNI โดยปิด metadata/link-local/multicast/unspecified/reserved ตาม policy ผู้ตั้ง URL ต้องเป็น owner และ URL ภายในเข้าถึงจากเครือข่าย backend; HTTP ไม่เข้ารหัสข้อมูลหรือคีย์
5. กด **ทดสอบ** เพื่อส่งข้อความสังเคราะห์สั้น ไม่มีข้อมูลการเงินจริง อาจมีค่าบริการ กด **โหลดโมเดล** เพื่อดึง `/models` แล้วเลือกในฟอร์มแก้ไข หาก API ไม่รองรับให้กรอกชื่อโมเดลเอง ไม่ส่งคำตอบดิบของผู้ให้บริการกลับหน้าตั้งค่า
6. เลื่อนขึ้น/ลงเพื่อจัดลำดับตามงาน เปิด–ปิดหรือแก้ไขโมเดลได้ คีย์ที่เว้นว่างเมื่อแก้ไขใช้คีย์เดิม มีช่องล้างคีย์สำหรับ API ที่ไม่ต้องยืนยันตัวตน
7. ตั้ง timeout 5–60 วินาที ลองซ้ำ 0–2 ครั้ง tokens 64–8192 และ temperature 0–2 แยกต่อโมเดล ลองสูงสุด 1–5 โมเดลต่องาน มีกรอบรวมแบบ soft deadline 90 วินาที (request/stream ที่กำลังทำงานอาจเกินกรอบนี้ได้) เลือกปิด demo fallback เพื่อให้งานล้มเหลวเมื่อไม่มีโมเดลพร้อม
8. Web Chat ทุกห้องใช้ลำดับโมเดลตามการตั้งค่าและสวิตช์ Cloud นี้อัตโนมัติ ไม่ต้องเลือกโหมดห้อง ส่วน Inbox ยังเลือก Standard สำหรับงานที่อนุญาต Cloud ได้

`EXTERNAL_AI_ENABLED` เดิมใช้เป็นค่าเริ่มต้นเฉพาะพื้นที่ที่ยังไม่เคยบันทึกการตั้งค่า เมื่อบันทึกจากเว็บแล้วใช้ค่าของ workspace แทน `COMPATIBLE_URL` เดิมรองรับ providers เก่าที่ไม่มี endpoint ในฐานข้อมูล; providers ใหม่ใส่ URL ผ่านเว็บได้ Local Ollama ยังใช้บริการภายในที่ผู้ดูแลเตรียมไว้ ไม่ติดตั้ง/ดาวน์โหลดโมเดลจากหน้าเว็บ และไม่อนุญาต Custom URL ไปบริการ private network ของ tenants อื่น

Key เข้ารหัส Fernet ที่ backend ด้วย ENCRYPTION_KEY ไม่คืน key/ciphertext ผ่าน API และไม่มี key ใน frontend bundle ระบบใช้ OpenAI-compatible chat completions รวมถึง [Gemini compatibility](https://ai.google.dev/gemini-api/docs/openai) และ [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility) ความสามารถภาพ/พารามิเตอร์ขึ้นกับโมเดลที่เลือก

Task routing แยก chat/extract และ priority เลขน้อยก่อน ลองไม่เกิน 3 providers, 2 ครั้งต่อ provider, HTTP timeout 20 วินาที (connect 5), ไม่ตาม redirect, ไม่ใช้ proxy environment ไม่มีการเรียก provider จนกว่าจะตั้งค่า โมเดลผิดรูปแบบ/ใช้ไม่ได้จะ fallback ไป demo โดยระบุในผลลัพธ์; demo parser รองรับข้อความสั้นแบบ “ชื่อรายการ จำนวนบาท” เท่านั้น รูป demo จะได้ข้อเสนอที่ **ยังไม่ทราบยอด** ไม่ได้ทำ OCR จริง

Web Chat ตอบคำถามรายงานภาษาไทยจาก backend โดยตรง เช่น เดือนนี้/เดือนที่แล้วใช้เท่าไหร่ มีรายการอะไร ใช้จากบัญชีไหน; รองรับ YYYY-MM, ชื่อเดือนภาษาไทยและปี พ.ศ., วันนี้/เมื่อวาน และช่วง YYYY-MM-DD ถึง YYYY-MM-DD ไม่เกิน 366 วัน ระบุชื่อบัญชี/หมวดตรงตามที่สร้างได้ และต่อคำถามสั้นโดยใช้ช่วงวันก่อนหน้า รายงานไม่เรียกโมเดลภายนอกและไม่เปลี่ยน ledger แสดงไม่เกิน 20 รายการต่อคำตอบ แต่ยอดรวมจากทั้งหมด พร้อมระบุขอบเขตและช่วงวันที่เสมอ คำถามทั่วไปยังส่งบริบทไม่เกิน 12 ข้อความและยอดสะสมบัญชีให้โมเดลตาม privacy; ยังไม่มี arbitrary tool-calling หรือวิเคราะห์ทุกคำถามอย่างอิสระ ส่งรูปผ่านแชทเพื่อสร้างข้อเสนอรอตรวจสอบใน Inbox ได้

## Telegram

1. สร้างบอตกับ BotFather แล้วใส่ `TELEGRAM_BOT_TOKEN` ใน `.env` (อย่า commit)
2. `docker compose --profile telegram up -d telegram`
3. Settings บนเว็บ → สร้างรหัสเชื่อมต่อ → ส่ง `/start รหัส` ใน private chat กับบอต
4. ส่งข้อความหรือรูป แล้วตรวจสอบ AI Inbox บนเว็บ

รหัสสุ่มใช้ได้ครั้งเดียว 10 นาที เก็บ hash ในฐานข้อมูล รับเฉพาะ private chat ตรวจ membership ใหม่ทุกครั้ง Telegram capture ใช้ Private/Ollama/mock เท่านั้น ใช้ `/unlink` หรือปุ่มยกเลิกบนเว็บเพื่อเพิกถอน ข้อความบันทึกบน Telegram รองรับทวนและพิมพ์แค่ `ยืนยัน` หรือ `ยกเลิก` ตามหัวข้อแชทธรรมชาติ; รูปสลิปยังตรวจและยืนยันบนเว็บ ไม่เปิด webhook บอตทำ long polling ข้อมูลที่ส่งผ่านบอตยังผ่าน Telegram แม้ประมวลผลด้วย Local AI

## บัญชีและการแยก workspace

- ทุก endpoint การเงินตรวจ membership ของผู้ใช้และ workspace จาก session ฝั่งเซิร์ฟเวอร์
- Composite foreign keys บังคับ ledger line, proposal receipt, proposal entry และ chat message ให้อยู่ใน workspace เดียวกัน
- เงินใช้ integer สตางค์ ไม่ใช้ float ใน ledger; API `amount=7500` คือ 75 บาท
- การบันทึกเงินเป็น transaction เดียว header + debit/credit lines + การเปลี่ยนสถานะ proposal
- PostgreSQL deferred constraint trigger บังคับ debit=credit และอย่างน้อย 2 lines ก่อน commit; posted ledger แก้/ลบ/เติม line ภายหลังไม่ได้
- Workspace row lock ทำให้การเขียนพร้อมกันและ idempotency replay ถูกต้อง รหัสรายการเดิมกับข้อมูลอื่นตอบ 409
- รายรับ: Dr สินทรัพย์ / Cr รายรับ; รายจ่าย: Dr รายจ่าย / Cr สินทรัพย์หรือหนี้บัตร
- โอน: Dr บัญชีปลายทาง / Cr บัญชีต้นทาง; จ่ายบัตร: Dr หนี้สิน / Cr สินทรัพย์ ไม่เพิ่มรายจ่าย
- ยอดตั้งต้นหักบัญชี equity; หมวดหมู่คือ ledger accounts ชนิด expense/income จึง reconcile กับรายงานได้
- สมาชิก workspace เดียวกันเห็นข้อมูลการเงินร่วมกัน แต่ห้องแชทเป็นของผู้ใช้แต่ละคน Settings provider จำกัด owner

Tenant isolation รุ่นนี้ใช้ application authorization + composite FK ไม่ใช่ PostgreSQL RLS ผู้ดูแลฐานข้อมูล/เซิร์ฟเวอร์ยังเข้าถึงข้อมูลทั้งหมดได้ บัญชี service ฐานข้อมูลต้องรักษาเป็นความลับ มีหน้าเชิญและจัดการสมาชิกแล้ว โดยรองรับ owner/member ตามรายละเอียดหัวข้อสมาชิกและคำเชิญ

## สำรอง อัปเดต และหยุด

```sh
sh scripts/backup.sh
python3 scripts/verify_restore.py
docker compose up -d --build
docker compose down
```

Backup รวม PostgreSQL (ledger, chats, รูปสลิป, encrypted provider keys) สำรอง `.env` แยกอย่างปลอดภัยด้วย โดยเฉพาะ ENCRYPTION_KEY หาก key หายจะถอดรหัส provider keys ไม่ได้ อย่าเปลี่ยน ENCRYPTION_KEY โดยตรงโดยไม่ migrate ciphertext ยังไม่มีระบบ key rotation อัตโนมัติ

`verify_restore.py` สร้างฐานข้อมูลชื่อสุ่มสำหรับทดสอบ restore เท่านั้น เปรียบเทียบจำนวนแถวกับฐานข้อมูลต้นทาง ตรวจสมดุล ledger แล้วลบฐานข้อมูลทดสอบของตัวเอง หากต้องการเทียบจำนวนแถว ให้หยุดการเพิ่มข้อมูลระหว่าง backup/verify (สคริปต์ไม่หยุด production ให้อัตโนมัติ)

ทดสอบ restore ใน instance แยกก่อนใช้จริง: สร้าง empty database แล้วใช้ `pg_restore -U finance -d TARGET_DB` จาก dump ผ่าน stdin การ restore ทับ production ต้องมี backup ล่าสุดและหยุด api/worker/bot ก่อน ปกติ `docker compose down` เก็บ volumes ไว้ **อย่าใช้ `down -v` กับข้อมูลที่ต้องการเก็บ**

API access logs ปิด, AI errors เก็บเฉพาะรหัสเหตุผล, middleware ไม่พิมพ์ traceback/DB parameters, bot ปิด library logging เพราะ URL อาจมี token ไม่เปิด debug logging ใน production Service worker cache เฉพาะไฟล์สาธารณะ ข้อมูลการเงินออฟไลน์ต้องเลือกเก็บเองและเข้ารหัสตามส่วน PWA ด้านบน

| Encrypted provider keys, model/task/priority routing, retry/timeout/fallback | ทำแล้วและทดสอบด้วย mock HTTP; ยังไม่ได้เรียกบริการจริงด้วย key หรือ Ollama model จริง |

| Backup/restore script / HTTPS configuration | backup และ restore ใน DB disposable ผ่านแล้ว; ยังไม่ได้ทดสอบ certificate จริงหรือ Ubuntu/Hyper-V เครื่องปลายทาง |

member management และ retention ทำแล้ว ค้นหา/เปลี่ยนชื่อแชททำแล้ว chat streaming ทำแล้ว PWA offline แบบ snapshot/ร่างทำแล้ว ยืนยันอีเมลและกู้รหัสผ่านผ่าน SMTP ทำแล้ว งานที่เหลือมี 2FA/จัดการอุปกรณ์ และตรวจ deployment จริง ไม่มีการเชื่อมธนาคารหรือเคลื่อนย้ายเงินจริงในรุ่นนี้

## Web Chat แนบรูป — รุ่นที่ต่อจาก MVP

กดคลิปหนีบกระดาษ เลือก JPG/PNG/WebP ไม่เกิน 8 MB ดูตัวอย่าง/นำออก แล้วกดส่ง สามารถส่งรูปอย่างเดียวหรือพร้อมข้อความได้ รูปถูกตรวจชนิดไฟล์ ลบ metadata และแปลงเป็น JPEG ก่อนเก็บ รูปเกิน 16 ล้านพิกเซลถูกปฏิเสธ ประวัติแสดงรูปและเปิดดูภาพได้

รูปใน Web Chat ใช้โมเดลงาน `chat` ที่เปิด **รับรูปภาพในแชท** ส่งประวัติล่าสุดไม่เกิน 20 ข้อความและ 3 รูป จึงอ้างถึงรูปและตอบคำถามต่อในห้องเดิมได้ แชททุกห้องใช้ลำดับโมเดลของ workspace ส่งภาพ/ข้อความให้ Cloud ได้เมื่อเปิด Cloud ในศูนย์ตั้งค่า AI แล้ว ไม่มีโมเดลที่ใช้ได้จะบอกว่ายังอ่านรูปไม่ได้ ไม่เดาจำนวนเงินจากข้อความประกอบ

ก่อนยืนยัน รูปและร่างอยู่เฉพาะเจ้าของห้อง เมื่อผู้ใช้ยืนยันจะบันทึก ledger พร้อมข้อเสนอสถานะ confirmed เพื่อเก็บรูปเป็นหลักฐาน สมาชิก workspace เห็นหลักฐานการเงินนั้นได้ รูปเดิมที่ยืนยันแล้วจะไม่ลงเงินซ้ำทั้งจากแชทหรือ Inbox หากร่างรูปอยู่ในอีกห้องต้องจัดการร่างนั้นก่อน

ลบห้องจะยกเลิกงานที่ยังรอและลบข้อความ/รูปที่ไม่มีการอ้างอิง รูปที่ยืนยันเป็นหลักฐานหรือเชื่อมกับ Inbox ยังอยู่ ไม่ลบรายการการเงิน Telegram ใช้ Chat runtime และยืนยันในห้อง Telegram ได้ ส่วนช่องทาง Inbox ยังคงใช้งาน `extract` และยืนยันใน Inbox ดู [คู่มือ AI Assistant](docs/AI_ASSISTANT.md) และ [ลำดับงาน](docs/ROADMAP.md)

## UX/UI รุ่นออกแบบใหม่

หน้าการเงินใช้โทนขาวนวล/เขียวอ่อน โครง desktop และ mobile แยกตามพื้นที่ใช้งาน มือถือใช้เมนูด้านล่างและ header สั้น แชท `/assistant` เป็นแอปเต็ม viewport มีประวัติที่เปิด/ปิดได้ ข้อความเลื่อนอิสระและช่องพิมพ์อยู่ด้านล่าง แนบรูปและยืนยันรายการในแชทได้ พร้อม Inbox สำหรับช่องทางอื่น ดูรายละเอียด [docs/UI.md](docs/UI.md)

## ภาพรวมรายเดือนและรายการแบบเลือกช่วงวัน

- Dashboard เลือกเดือนจากปฏิทินแบบตารางหรือปุ่มก่อนหน้า/ถัดไป ไม่ต้องพิมพ์ มีกราฟรายจ่ายสะสม เปรียบเทียบยอดเต็มเดือนก่อน และกราฟวงกลมแยกหมวด กดหมวด/บัญชีเพื่อเปิดรายการที่กรองแล้ว
- หน้ารายการมีวันนี้/เดือนนี้/เดือนก่อน/ทั้งหมด และปฏิทินเลือกวันเริ่ม–สิ้นสุด ค้นหาคำอธิบาย กรองประเภท/บัญชี/หมวด แบ่งหน้า 30 รายการและจัดกลุ่มตามวัน ยอดรวมคำนวณจากทุกรายการที่ตรงตัวกรอง
- ยอดบัญชีและมูลค่าสุทธิบน Dashboard คือยอดล่าสุด ณ ปัจจุบัน ส่วนรายรับ/รายจ่าย/รายการล่าสุดเป็นเดือนที่เลือก ไม่ใช่รายงานยอดบัญชีสิ้นเดือน
- API เพิ่ม `GET /workspaces/{wid}/transaction-report` พร้อม membership และ scoped filters; API รายการเดิมยังใช้งานได้ ไม่เปลี่ยน schema ของ ledger

## บริการทั้งหมดและเมนู

เข้า `/services` เพื่อค้นหาและเลือกบริการทั้งหมดที่ใช้ได้จริง มือถือมี 5 เมนูหลัก: ภาพรวม, รายการ, แชท AI, AI Inbox, ทั้งหมด บัญชีอยู่ `/accounts` และหมวดหมู่อยู่ `/categories` แยก form และรายการชัดเจน โดยข้อมูลยังเชื่อม ledger เดิม กดบัญชี/หมวดเพื่อดูรายการได้ Shortcut ตั้งค่า privacy/Telegram/provider พาไปส่วนที่เกี่ยวข้อง Provider แสดงเฉพาะ owner การเชื่อมบริการจริงยังต้องตั้งค่าตามส่วนติดตั้ง

## งบประมาณรายเดือน

เปิด `/budgets` หรือบริการทั้งหมด → งบประมาณ ตั้งวงเงินรายหมวดรายจ่ายเป็นบาท พร้อมทศนิยมไม่เกิน 2 ตำแหน่ง รองรับแก้ไข/นำวงเงินออกและคัดลอกเดือนก่อนเฉพาะหมวดที่ยังไม่ได้ตั้ง (ไม่ทับของเดิม) แยกแต่ละเดือนและ workspace สมาชิกในพื้นที่เดียวกันร่วมดูและตั้งงบได้

ยอดใช้จริงมาจาก expense ที่ยืนยันแล้วตามวันที่เกิดรายการ รวมการใช้บัตรเมื่อซื้อสินค้า ไม่รวมโอนเงิน/จ่ายบัตรซ้ำ/ยอดตั้งต้น/ข้อเสนอที่ยังไม่ยืนยัน แสดงอยู่ในงบ/ใกล้เต็มตั้งแต่ 80%/ใช้ครบ/เกินงบ รายจ่ายในหมวดที่ไม่ตั้งงบแสดงแยก ไม่ได้กันเงินหรือเคลื่อนย้ายเงิน

ถาม Web Chat ว่า “งบเดือนนี้เหลือเท่าไหร่” หรือระบุเดือนและชื่อหมวดได้ ระบบอ่านจาก backend โดยตรง ไม่เรียก Cloud และไม่สร้างหรือแก้งบจากแชท งบไม่ทบยอดเงินที่เหลือไปเดือนถัดไป คัดลอกเฉพาะวงเงิน ไม่มีแจ้งเตือน push/Telegram และยังไม่มีประวัติการแก้ไขงบ

อัปเดตด้วย `docker compose build api worker migrate web` แล้ว `docker compose up -d` หลังสำรองข้อมูล Migration `monthly_budgets` เพิ่มตารางใหม่ ไม่แก้ ledger การเลือก workspace จำในแท็บเดียวกันและตรวจสิทธิ์กับรายการสมาชิกก่อนใช้ทุกครั้ง


## แก้ไขและยกเลิกรายการ พร้อมประวัติ

เปิด **รายการเงิน → กดรายการ → แก้ไขรายการ** เพื่อแก้คำอธิบาย จำนวนเงิน วันที่ บัญชี หรือหมวดหมู่ ระบุเหตุผลและกดยืนยันก่อนบันทึก รองรับรายรับ รายจ่าย โอนเงิน จ่ายบัตร และยอดตั้งต้น การแก้ใช้ประเภทเดิม; ยอดตั้งต้นแก้ได้เฉพาะบัญชีเดิม รวมถึงวันที่และจำนวนเงิน

**ยกเลิกรายการ** กลับยอดเดิมออกจากบัญชี ไม่ลบต้นฉบับ เปิด **ประวัติการแก้ไข** เพื่อดูข้อมูลก่อน/หลัง เหตุผล เวลา และเปิดรายการเดิมหรือรายการทดแทนได้ ประวัติรวมทุกเดือนใน workspace และแบ่งหน้า 30 เหตุการณ์ ผู้แก้ถูกเก็บในฐานข้อมูลด้วย รายการที่ถูกแก้หรือยกเลิกแล้วแก้ซ้ำไม่ได้ ให้เปิดรายการทดแทนล่าสุดแทน ยังไม่มีปุ่มคืนรายการที่ยกเลิกโดยอัตโนมัติ

Ledger เดิมไม่ถูกแก้: ระบบเพิ่ม journal กลับยอดที่มี lines ตรงข้ามต้นฉบับ และเพิ่มรายการทดแทนใน transaction เดียวกัน ล้มเหลวแล้ว rollback ทั้งชุด ใช้ workspace lock และ idempotency กันกดซ้ำ/แก้พร้อมกัน PostgreSQL ตรวจสมดุล ห้ามแก้/ลบ audit และตรวจบัญชีใน journal กลับยอดบนฐานข้อมูลด้วย journal กลับยอดเก็บ `kind` เดียวกับต้นฉบับ; บทบาท `entry_revisions.reversal_id` แยกออกจากรายงาน เช่นเดียวกับต้นฉบับที่ถูก supersede นักพัฒนาต้องใช้ `reporting.active_entry()` สำหรับรายงานธุรกิจ ไม่รวมยอดดิบจาก `entries` โดยตรง ยอดบัญชีรวมทุก line จึงหักล้างต้นฉบับอย่างถูกต้อง

Dashboard, รายการเงิน, งบประมาณและ AI report ใช้รายการปัจจุบันร่วมกัน ย้ายวันที่ข้ามเดือนแล้วทั้งสองเดือนคำนวณใหม่ ประวัติการแก้เป็นประวัติรายการเงินจริง แยกจากการแก้วงเงินงบซึ่งยังไม่มี audit trail โมเดลไม่มีสิทธิ์แก้ไข/ยกเลิกเอง; ผู้ใช้สั่งแก้ผ่าน trusted chat handler และพิมพ์ยืนยันได้ตามหัวข้อแชท

สำรองข้อมูลก่อนอัปเดตด้วย `sh scripts/backup.sh` แล้ว `docker compose build api worker migrate web` และ `docker compose up -d` Migration `entry_revisions` เพิ่ม audit table/guards โดยไม่เปลี่ยนแถว ledger เดิม รองรับอัปเกรดจาก `monthly_budgets` และติดตั้งฐานใหม่


## ส่งออก CSV

เปิด **บริการทั้งหมด → ส่งออกข้อมูล** หรือหน้ารายการเงิน เลือกวันเริ่มต้น–สิ้นสุด ประเภท บัญชี หมวดหมู่ หรือคำค้น แล้วกด **ส่งออก CSV** ไฟล์รวมทุกรายการที่ตรงตัวกรองทุกหน้า (ไม่จำกัด 30 แถวตามหน้าจอ) ใช้รายการปัจจุบันเท่านั้น ไม่รวมต้นฉบับที่ถูกแก้ รายการที่ยกเลิก journal กลับยอด หรือข้อเสนอที่ยังไม่ยืนยัน

คอลัมน์มีรหัสรายการ วันที่ ประเภท รายละเอียด จำนวนเงินเป็นบาท บัญชีขาออก/ขาเข้า และหมวดหมู่ ตัวเลขใช้จุดทศนิยมสองตำแหน่งโดยไม่ผ่าน float จำนวนเงินเป็นบวก แยกความหมายด้วยประเภทและทิศบัญชี จึงไม่ควรรวมโอนเงินหรือจ่ายบัตรเป็นรายจ่ายซ้ำ ไฟล์ใช้ comma-separated CSV + UTF-8 BOM สำหรับภาษาไทย ไม่ใช่ไฟล์ XLSX หากโปรแกรมไม่แยกคอลัมน์อัตโนมัติ ให้นำเข้าแบบ UTF-8 และตัวคั่น comma

เปิด **ประวัติการแก้ไข → ส่งออกประวัติ CSV** เพื่อเก็บเหตุผล เวลา (Asia/Bangkok) รหัสผู้แก้ไข รหัส journal กลับยอด และข้อมูลก่อน/หลัง เลือกช่วงตาม **วันที่แก้ไขหรือยกเลิก** ไม่ใช่วันที่ของรายการต้นฉบับ ช่องวันว่างหมายถึงทุกวัน ตัวกรองนี้ใช้กับทั้งหน้าประวัติและไฟล์ส่งออก

ทั้งสองแบบจำกัด 10,000 แถวต่อไฟล์ ถ้าเกินจะแจ้งให้ลดช่วงวันหรือตัวกรอง ไม่ส่งไฟล์ที่ตัดข้อมูลบางส่วน สมาชิกที่ดูข้อมูล workspace ได้จึงดาวน์โหลดได้เช่นเดียวกับสิทธิ์รายงาน ข้อมูลแชท รูป และ API keys ไม่รวมใน CSV การส่งออกไม่เขียน ledger และไฟล์ถูกส่งตรงให้เบราว์เซอร์ ไม่มีสำเนา export เก็บบนเซิร์ฟเวอร์

ข้อความผู้ใช้ที่อาจเป็นสูตร เช่น ขึ้นต้น `=`, `+`, `-`, `@` หรือ control characters จะเติม apostrophe (`'`) ในไฟล์เพื่อให้เปิดเป็นข้อความ โดยไม่เปลี่ยนข้อมูลต้นทาง การแก้/ลบประวัติหรือการนำเข้า CSV/XLSX ยังไม่มีในรุ่นนี้ ยังไม่ได้ทดสอบเปิดไฟล์ด้วย Excel/Numbers บนเครื่องจริง

รอบนี้ไม่มี migration ใหม่ อัปเดตด้วย `docker compose build api worker migrate web` แล้ว `docker compose up -d` หลังสำรองข้อมูลตามขั้นตอนเดิม


## เป้าหมายออม

เข้า **บริการทั้งหมด → เป้าหมายออม** (`/goals`) ตั้งชื่อ ยอดเป้าหมาย และวันที่อยากไปถึง (ไม่บังคับ) บันทึก “จัดสรรเพิ่ม” หรือ “นำออก” พร้อมวันที่และบันทึกช่วยจำ ติดตามเปอร์เซ็นต์ ยอดที่ยังขาด และสถานะถึงเป้า/เลยกำหนด ดูประวัติทีละ 30 เหตุการณ์ เป้าหมายที่เก็บไว้ยังดูประวัติและเปิดใช้ใหม่ได้ แต่ไม่นับในยอดรวมของแผนที่ใช้อยู่

**ยอดจัดสรรเป็นแผนที่ผู้ใช้บันทึกเอง ไม่ได้โอนหรือกันเงินในบัญชี และไม่รับรองว่ามีเงินออมจริงเท่ากับยอดนี้** ไม่มีบัญชีผูกกับเป้าหมาย จัดสรรเกินเป้าได้ แต่ยอดรวมต่อเป้าหมายต้องไม่เกิน 1,000,000,000 บาท นำออกได้ไม่เกินยอดจัดสรร ไม่ให้บันทึกวันที่ในอนาคต รองรับไม่เกิน 500 เป้าหมายต่อ workspace รวมที่เก็บไว้แล้ว

การจัดสรรเป็นประวัติเพิ่มอย่างเดียว ไม่มีแก้/ลบย้อนหลัง ถ้าผิดให้เพิ่มการจัดสรรหรือนำออกเพื่อปรับยอด PostgreSQL ป้องกันแก้/ลบประวัติ มี composite tenant FK และตรวจยอดตอน commit การเรียกซ้ำด้วยรหัสเดิมไม่เพิ่มเงินซ้ำ ล็อก workspace ระหว่างเปลี่ยนยอดและตรวจ version เมื่อแก้/เก็บเป้าหมาย เพื่อป้องกันข้อมูลเก่าทับการเปลี่ยนล่าสุด สมาชิกใน workspace ใช้แผนร่วมกันได้ตามสิทธิ์ข้อมูลการเงิน

ยังไม่มีการแบ่งเงินจริงอัตโนมัติ เป้าหมายออมรายเดือน/จัดสรรเงินออมประจำ การแจ้งเตือน การอ่านเป้าหมายผ่าน AI chat การส่งออกเป้าหมาย หรือประวัติการเปลี่ยนชื่อ/ยอดเป้า (ประวัติการจัดสรรยังอยู่ครบ) API keys และ AI ไม่เกี่ยวข้องกับการบันทึกเป้าหมาย

สำรองก่อนอัปเดต `sh scripts/backup.sh` แล้ว `docker compose build api worker migrate web` และ `docker compose up -d` Migration `savings_goals` ต่อจาก `entry_revisions` เพิ่มตารางใหม่โดยไม่แก้ ledger เดิม รองรับฐานใหม่และการอัปเกรด


## รายการประจำ

เข้า **บริการทั้งหมด → รายการประจำ** (`/recurring`) ตั้งรายรับหรือรายจ่าย จำนวนเงิน บัญชี หมวดหมู่ ความถี่รายวัน/รายสัปดาห์/รายเดือน วันเริ่มรอบแรก (วันนี้หรืออนาคต) และวันสิ้นสุดที่เลือกได้ รอบรายสัปดาห์ห่างกัน 7 วัน รอบรายเดือนยึดวันที่เริ่ม เช่น 31 มกราคม → วันสุดท้ายกุมภาพันธ์ → 31 มีนาคม รองรับ leap year วันสิ้นสุดนับรวมถ้ามีรอบตรงวันนั้น วันที่ทั้งหมดใช้ Asia/Bangkok

**ระบบสร้างข้อเสนอใน Inbox เท่านั้น ไม่ลงบัญชีและไม่ชำระเงินจริงอัตโนมัติ** Worker ตรวจรอบประมาณทุก 30 วินาทีขณะทำงาน หรือกด “ตรวจรายการถึงกำหนด” ได้เอง เมื่อเข้าตรวจใน Inbox จะเติมจำนวนตามแผน วันที่รอบ บัญชี และหมวดให้ แก้ยอดจริงและตรวจข้อมูลก่อนกด “ยืนยันและบันทึก” การยกเลิกข้อเสนอหนึ่งรอบไม่หยุดรอบถัดไปและไม่สร้างรอบเดิมซ้ำ

พักรายการเพื่อหยุดสร้างข้อเสนอใหม่ ข้อเสนอเก่าและรายการเงินที่ยืนยันแล้วยังอยู่ครบ เปิดใช้อีกครั้งแล้วระบบจะทยอยสร้าง **รอบค้างรวมช่วงที่พัก** ให้ตรวจสอบ ไม่ข้ามรอบให้เอง การแก้รายละเอียด/ยอด/บัญชี/หมวดมีผลเฉพาะข้อเสนอที่ยังไม่สร้าง ข้อเสนอเดิมคงข้อมูลตอนสร้าง สามารถดูประวัติทีละ 30 รอบพร้อมสถานะ และเปิดรายละเอียดรายการเงินจริงที่ยืนยันแล้วได้ (รวมรายการที่ถูกแก้หรือยกเลิกในภายหลัง)

รุ่นนี้ไม่เปลี่ยนความถี่/วันเริ่ม/วันสิ้นสุดของตารางที่สร้างแล้ว หากต้องการตารางใหม่ ให้พักรายการเดิมแล้วสร้างใหม่ รองรับไม่เกิน 200 ตารางต่อ workspace รวมที่พัก/สิ้นสุด แต่ละรอบตรวจเลือกไม่เกิน 25 ตารางและสร้างไม่เกิน 25 ข้อเสนอรวม ไม่เกิน 10 รอบต่อตาราง เพื่อทยอยจัดการ backlog เมื่อ workspace มีข้อเสนอ pending ครบ 100 รายการจะรอให้ตรวจสอบก่อนสร้างเพิ่ม Inbox แสดง pending ก่อนสถานะอื่น สูงสุด 100 รายการ และรีเฟรชประมาณทุก 10 วินาทีขณะเปิดหน้า

มีรหัสกันสร้างตารางซ้ำ, unique ตาราง/วันที่รอบ, transaction/workspace lock ให้ข้อเสนอ ประวัติ และวันถัดไป commit พร้อมกัน PostgreSQL ป้องกันแก้/ลบข้อมูลรอบย้อนหลัง มี tenant FK ทั้งบัญชี หมวด ตาราง และข้อเสนอ ไม่มี AI/provider/Redis เป็นแหล่งข้อมูลหลักของกำหนดรอบ Worker อ่านตารางที่บันทึกใน PostgreSQL จึงทำต่อได้หลัง restart

ยังไม่มี recurring transfer/card payment, รอบรายปี/กำหนดวันเอง/หลายครั้งต่อวัน, ปุ่มข้ามรอบค้างรวม, แจ้งเตือน push/Telegram, จ่ายธนาคารจริง, AI สร้างตาราง หรือ audit trail การแก้รายละเอียดตาราง (ประวัติการสร้างข้อเสนอแต่ละรอบยังอยู่ครบ) หน้า Inbox ใช้ร่วมกับข้อเสนอ AI จะแสดงป้าย “รายการประจำ” แยกชัดเจน

สำรองก่อนอัปเดตด้วย `sh scripts/backup.sh` แล้ว `docker compose build api worker migrate web` และ `docker compose up -d` Migration `recurring_rules` ต่อจาก `savings_goals` เพิ่มตารางและ unique constraint ของข้อเสนอ ไม่แก้ยอด ledger เดิม ต้องเปิด worker เพื่อให้ตรวจรอบอัตโนมัติ


## สมาชิกและคำเชิญ

เปิด **บริการทั้งหมด → สมาชิกและคำเชิญ** (`/members`) เจ้าของพื้นที่สร้างรหัสเชิญผูกอีเมลได้ รหัสสุ่มแสดงครั้งเดียว เก็บเฉพาะ SHA-256 hash ในฐานข้อมูล ใช้ได้ 7 วันและใช้ได้ครั้งเดียว กดคัดลอกแล้วส่งรหัสกับลิงก์ `/join` ให้ผู้รับด้วยตัวเอง ระบบไม่ส่งอีเมลและไม่ใส่รหัสลง URL หากทำรหัสหาย ให้ยกเลิกคำเชิญเดิมแล้วสร้างใหม่

ผู้รับตรวจรหัสและอีเมลก่อนเห็นชื่อพื้นที่ จากนั้นตั้งรหัสผ่านของตัวเองอย่างน้อย 12 ตัวอักษร หรือเข้าสู่บัญชีเดิมแล้วรับคำเชิญ บัญชีใหม่ได้พื้นที่ส่วนตัวและสิทธิ์สมาชิกในพื้นที่ที่เชิญ ไม่จำเป็นต้องขอให้ผู้ดูแลเซิร์ฟเวอร์สร้างบัญชีให้ทุกคน การรับคำเชิญและสร้างบัญชีเกิดในธุรกรรมเดียวกัน จำกัดการเรียกหน้ารับคำเชิญด้วย IP ไม่เปิดให้สร้างบัญชีโดยไม่มีรหัสที่ใช้ได้

| สิทธิ์ | สมาชิก | เจ้าของพื้นที่ |
|---|---|---|
| ดู/บันทึก/แก้กลับยอดข้อมูลการเงิน, งบ, เป้าหมาย, รายการประจำ และ CSV | ได้ | ได้ |
| ใช้ AI Inbox และดูหลักฐานที่แชร์ในพื้นที่ | ได้ | ได้ |
| อ่านแชทส่วนตัวของผู้อื่น | ไม่ได้ | ไม่ได้ |
| ดูรายชื่อสมาชิกและออกจากพื้นที่ | ได้ | ได้ |
| เชิญ/ยกเลิกคำเชิญ/เปลี่ยนสิทธิ์/นำสมาชิกออก/ดูประวัติสมาชิก | ไม่ได้ | ได้ |
| จัดการผู้ให้บริการ AI | ไม่ได้ | ได้ |

สมาชิกใหม่เป็น `member` เสมอ การมอบสิทธิ์ `owner` ให้ผู้ที่เข้าร่วมแล้วต้องยืนยันจากหน้าสมาชิก ระบบป้องกันการลดสิทธิ์/นำออก/ออกจากพื้นที่ของเจ้าของคนสุดท้ายทั้งใน API และ PostgreSQL แม้มีคำขอพร้อมกัน จำกัดสมาชิก 100 คนและคำเชิญรอรับที่ยังไม่หมดอายุ 100 รายการต่อพื้นที่ ประวัติการเชิญ เข้าร่วม เปลี่ยนสิทธิ์ นำออก และออกเองแบ่งหน้า 30 เหตุการณ์ ระบุผู้ดำเนินการ และ PostgreSQL ป้องกันการแก้/ลบประวัติ

เมื่อนำสมาชิกออก จะลบสิทธิ์เข้าพื้นที่และการเชื่อม/รหัสเชื่อม Telegram ของผู้ใช้นั้น งาน AI ที่ยังไม่เริ่มจะตรวจสิทธิ์ใหม่และหยุดก่อนเรียก provider งานที่ได้รับสิทธิ์และเริ่มก่อนการนำออกอาจทำเสร็จก่อน ระบบล็อก workspace ระหว่างตรวจสิทธิ์และทำงาน จึงไม่ตอบว่าตัดสิทธิ์สำเร็จขณะที่งานนั้นยังถือสิทธิ์อยู่ คำขอข้อมูลที่เริ่มหลังนำออกสำเร็จจะถูกปฏิเสธ หน้ารายการพื้นที่อัปเดตเมื่อกลับเข้าแท็บหรือทุก 30 วินาที ข้อมูลที่ดาวน์โหลด/แสดงก่อนหน้านั้นไม่สามารถเรียกคืนจากอุปกรณ์ผู้ใช้ได้

การนำออกไม่ลบบัญชีผู้ใช้ พื้นที่อื่น รายการเงิน ประวัติ หรือแชทเดิม รหัสเชิญที่ใช้แล้วไม่สามารถคืนสิทธิ์ให้สมาชิกที่ถูกนำออก ต้องเชิญใหม่อย่างชัดเจน หากเข้าร่วมใหม่ ผู้ใช้จะเห็นประวัติแชทส่วนตัวเดิมของตนที่ยังไม่หมดอายุหรือถูกล้างในพื้นที่นั้นอีกครั้ง เจ้าของคนอื่นยังอ่านไม่ได้

ยังไม่มี read-only/custom roles, 2FA, ลบบัญชีผู้ใช้ หรือย้ายข้อมูลระหว่าง workspace; ยืนยันอีเมล/ลืมรหัสผ่านผ่าน SMTP และจัดการ workspace มีแล้วตามขอบเขตที่ระบุข้างต้น ผู้ดูแลต้องส่งรหัสให้ผู้รับที่ตั้งใจเชิญ การล็อกแบบต่อ workspace เน้นความถูกต้องของ MVP และอาจทำให้คำขอในพื้นที่เดียวกันรอระหว่างงาน AI; ยังไม่ได้ทำ load test เพื่อรองรับผู้ใช้จำนวนมาก

สำรองข้อมูลก่อนอัปเดต แล้วใช้ `docker compose build api worker migrate web` และ `docker compose up -d` Migration `workspace_members` ต่อจาก `recurring_rules` เพิ่มคำเชิญ ประวัติ และตัวป้องกันเจ้าของคนสุดท้าย โดยไม่แก้ ledger เดิม สำรองและกู้คืนต้องเก็บตารางสมาชิก/คำเชิญ/ประวัติด้วย


## แชทชั่วคราวและอายุประวัติ

ในหน้าแชท เปิดเมนูประวัติแล้วเลือก **ห้องใหม่เป็นแชทชั่วคราว** ก่อนสร้างห้อง ข้อความและรูปทำงานเหมือนห้องปกติ แต่ห้องไม่อยู่ในรายการประวัติและหมดอายุ 24 ชั่วโมงนับจากสร้าง กด **จบและล้างแชท** เพื่อล้างทันทีได้ การ reload/ออกจากหน้าอาจทำให้ไม่มีทางเปิดห้องชั่วคราวเดิมจาก UI; ข้อมูลที่เหลือจะรอหมดอายุและล้างตามรอบ อายุแชทแยกจากการเลือกโมเดล แชทใช้ค่าของ workspace ปิด Cloud AI ในศูนย์ตั้งค่า AI หากต้องการเฉพาะ Local AI/mock

หน้า **ตั้งค่า → อายุประวัติแชทของคุณ** เลือกเก็บไว้จนลบเอง (ค่าเริ่มต้น) หรือหมดอายุหลังคุณไม่ได้ส่งข้อความ 7/30/90 วัน เป็นค่าของผู้ใช้แต่ละคนในแต่ละ workspace เจ้าของพื้นที่ไม่สามารถเปลี่ยนอายุแชทของสมาชิกคนอื่น ต้องยืนยันก่อนบันทึกเพราะมีผลต่อห้องเดิมด้วย การเปลี่ยนกลับเป็นเก็บตลอดไม่คืนห้องที่ล้างแล้ว

เมื่อหมดอายุ API จะไม่ให้ดูข้อความ ส่งข้อความ/รูป หรือดูรูปส่วนตัวผ่านห้องนั้น งาน AI ที่ยังไม่เริ่มตรวจอายุใหม่ก่อนเรียก provider Worker ตรวจทุกประมาณ 30 วินาทีและล้างสูงสุด 50 ห้องต่อรอบ ถ้า worker หยุด/มีงานค้าง ข้อมูลอาจยังอยู่ในฐานข้อมูลหลังหมดอายุ แต่ API ปิดการเข้าถึงแล้ว คำขอที่ได้รับสิทธิ์และเริ่มก่อนหมดอายุอาจทำเสร็จก่อนล้าง มี workspace lock ป้องกันการล้างชนกับการส่ง/ประมวลผล

ล้างห้องจะลบข้อความ งานที่ยังมีข้อมูลห้อง และรูปที่ไม่เหลือการอ้างอิง รูปที่ใช้ในห้องอื่น/งานอื่น หรือถูกแชร์เป็นข้อเสนอใน Inbox (รวม pending/rejected/confirmed) จะคงอยู่ **ไม่ลบรายการเงิน ข้อเสนอ หรือหลักฐานการเงิน** การลบห้องด้วยปุ่มเดิมใช้กติกาเดียวกัน งานที่เสร็จแล้วล้าง payload อยู่แล้ว อาจเหลือ metadata สถานะที่ไม่มีข้อความ/รหัสห้อง

นี่เป็นการเก็บชั่วคราวบนฐานข้อมูลเพื่อให้ worker ทำงานได้ ไม่ใช่ Incognito ที่ไม่เขียนดิสก์หรือรับประกัน secure erase การล้างไม่ลบสำเนาใน backup, browser/ไฟล์ที่ดาวน์โหลด หรือข้อมูลที่ Cloud provider ได้รับ ต้องจัดอายุ backup แยกต่างหาก ยังไม่มีการล้าง Inbox/หลักฐานอัตโนมัติหรือปุ่มกู้คืนแชท

สำรองข้อมูลก่อนอัปเดต แล้วใช้คำสั่งอัปเดต Docker เดิม Migration `chat_retention` ต่อจาก `workspace_members` ตั้งเวลาเริ่มต้นใหม่ให้ห้องเก่าเพื่อไม่ให้การอัปเกรดล้างประวัติเอง การล้างอัตโนมัติจะเริ่มเมื่อผู้ใช้เลือกอายุเก็บและยืนยันเท่านั้น (ยกเว้นห้องชั่วคราวที่เลือกตั้งแต่สร้าง)


## ค้นหาและเปลี่ยนชื่อแชท

ในเมนูประวัติของหน้าแชท ใช้ **ค้นหาประวัติแชท** ค้นจากชื่อห้อง ข้อความที่คุณส่ง หรือคำตอบ AI ค้นแบบข้อความต่อเนื่อง (ไม่ใช่ semantic search) รองรับภาษาไทยและไม่แยกตัวพิมพ์ใหญ่/เล็กภาษาอังกฤษ `%`, `_` และ backslash เป็นตัวอักษรตามจริง ไม่ใช่ wildcard ผลลัพธ์นับเป็นห้อง ครั้งละ 20 ห้อง เรียงตามเวลาที่คุณส่งล่าสุด ห้องหนึ่งมีข้อความตัวอย่างจากข้อความที่ตรงคำค้นล่าสุด

ผลค้นหาเฉพาะห้องของผู้ใช้ใน workspace ที่เลือก ไม่รวมแชทของสมาชิกคนอื่น แชทชั่วคราว หรือห้องที่หมดอายุแล้ว กดผลที่ตรงข้อความเพื่อเปิดบริเวณนั้น พร้อมไฮไลต์และบริบทรอบข้างไม่เกิน 50 ข้อความก่อน/หลัง กด **ดูข้อความล่าสุด** หรือส่งข้อความต่อเพื่อกลับสู่ช่วงล่าสุด หากตรงเฉพาะชื่อห้องจะเปิดช่วงล่าสุดตามปกติ การเปิดห้องปกติแสดง 50 ข้อความล่าสุด เลื่อนขึ้นหรือกดโหลดข้อความก่อนหน้าเพื่ออ่านเก่าต่อเนื่องได้ ใช้ cursor จากห้องเดียวกันและรักษาข้อความที่โหลดระหว่าง polling

เมื่อเปิดห้องถาวร เมนูประวัติมี **เปลี่ยนชื่อบทสนทนา** ชื่อยาว 1–100 ตัวอักษรหลังตัดช่องว่างรอบนอก สมาชิกเปลี่ยนชื่อได้เฉพาะห้องตนเอง การเปลี่ยนชื่อและค้นหาไม่เลื่อนวันหมดอายุ ไม่แก้ข้อมูลการเงิน และไม่เรียก AI ชื่อและข้อความแสดงเป็นข้อความธรรมดา

คำค้นส่งผ่าน POST body ไม่ใส่ใน URL และไม่เก็บเป็นประวัติการค้นหา ฝั่งเว็บยกเลิกผลคำค้นเก่าขณะพิมพ์คำใหม่ ไม่มี provider หรือ API key เกี่ยวข้อง ไม่มี migration ใหม่ในรอบนี้ การค้นหาใช้ฐานข้อมูลของคุณ ยังไม่มี full-text index/จัดอันดับ/ค้นจากข้อความ OCR ในรูป หรือการยืนยันประสิทธิภาพกับประวัติขนาดใหญ่


## ตั้งค่าบัญชีผู้ใช้

ไปที่ **ตั้งค่า → บัญชีผู้ใช้** เพื่อบันทึกชื่อที่แสดง (1–100 ตัวอักษร) ชื่อใช้กับบัญชีผู้ใช้ของคุณในทุก workspace ไม่เปลี่ยนชื่อพื้นที่หรือชื่อบัญชีเงิน อีเมลเข้าสู่ระบบแสดงให้อ่านและยังเปลี่ยนผ่านหน้าเว็บไม่ได้

เปลี่ยนรหัสผ่านต้องระบุรหัสปัจจุบัน รหัสใหม่ 12–200 ตัวอักษร และยืนยันให้ตรงกัน ต้องต่างจากเดิม รหัสเก็บเป็น Argon2 hash ฝั่ง backend เท่านั้น เมื่อสำเร็จเซสชันเดิมทั้งหมดจะถูกยกเลิกและเครื่องที่เปลี่ยนได้รับเซสชันใหม่ สมาชิกอื่นไม่ถูกออกจากระบบ ข้อมูลการเงิน/แชท/สมาชิกไม่เปลี่ยน รหัสในฟอร์มถูกล้างหลังส่งคำขอและไม่บันทึกใน localStorage มีการจำกัดความถี่การลองรหัสผ่านเดิม

Migration `user_profile` เพิ่มชื่อว่างให้บัญชีเดิม โดยคงอีเมลและรหัสเดิมไว้ การเข้าสู่ระบบเดิมและการเปลี่ยนรหัสใช้ lock ของผู้ใช้เดียวกัน และตรวจเซสชันซ้ำหลังได้ lock เพื่อป้องกันคำขอเปลี่ยนรหัสที่รออยู่ใช้เซสชันที่ถูกเพิกถอนไปแล้ว ผล validation ของ API เปลี่ยนรหัสไม่คืนค่ารหัสที่ส่งมา

ยืนยันอีเมลและลืมรหัสผ่านมีแล้วเมื่อเปิด SMTP; ยังไม่มีเปลี่ยนอีเมล 2FA รายการอุปกรณ์เข้าสู่ระบบ หรือลบบัญชีผ่านเว็บ Telegram link และ API keys เดิมยังอยู่ การยกเลิกเซสชันเว็บไม่ยกเลิก Telegram link และไม่ย้อนคำขอที่เริ่มทำงานก่อนเปลี่ยนรหัส


## แชทแบบทยอยแสดงคำตอบ

Web Chat ใช้ SSE เชื่อมต่อระหว่าง browser กับ backend และ Redis Pub/Sub ส่ง preview ขณะโมเดล OpenAI-compatible ตอบ (`stream=true`) รองรับ Ollama/Cloud ตาม privacy และค่าเซิร์ฟเวอร์เดิม ไม่มีการเรียกบริการจริงจนตั้งค่าเอง ข้อความที่กำลังตอบมีป้าย **ยังไม่สมบูรณ์** และแสดงเป็นข้อความธรรมดา ไม่รัน HTML หรือคำสั่งจากโมเดล

บันทึก assistant Message เมื่อคำตอบสำเร็จทั้งชุดเท่านั้น Worker ส่ง done หลัง commit หาก stream ขาด/ข้อมูลไม่ถูกต้อง/เกินขีดจำกัด จะลอง provider ใหม่ตามลำดับเดิม โดยล้าง preview เก่า ไม่ต่อคำตอบของคนละ attempt เข้าด้วยกัน Preview ส่งเป็น snapshot เพื่อให้เชื่อมต่อใหม่กลางคำตอบแล้วรับข้อความส่วนต้นได้ด้วย ไม่มี Redis key/replay cache ที่เก็บเนื้อหา streaming เพิ่ม Pub/Sub ไม่ได้ใช้เป็นประวัติสนทนา

เมื่อ Redis หรือ SSE ใช้ไม่ได้ เว็บกลับไปตรวจประวัติที่บันทึกแล้วตามปกติ ปิดหน้า/เปลี่ยนห้องจะปิดการรับ stream ฝั่ง browser แต่ไม่ยกเลิกงาน worker คำตอบแบบรายงานที่ backend คำนวณโดยตรง/โหมดสาธิต/ผู้ให้บริการที่ไม่ส่ง stream อาจแสดงทั้งคำตอบทันที ไม่มีการจำลองหน่วงพิมพ์ทีละตัว

SSE ตรวจ session, membership, เจ้าของห้องและอายุประวัติซ้ำระหว่างเชื่อมต่อ รวมก่อนส่งข้อมูล ไม่ถือ transaction หรือ workspace lock ตลอดการเชื่อมต่อ จึงอ่าน preview ระหว่าง worker ถือ lock ได้ หนึ่งการเชื่อมต่อมีอายุไม่เกิน 120 วินาที browser เชื่อมต่อใหม่ได้อัตโนมัติ HTTP model มี timeout อ่านตั้งได้ 5–60 วินาที (ค่าเริ่มต้น 20)/connect 5 และ stream budget ประมาณ 45 วินาทีต่อ attempt (การอ่านที่ค้างอาจเพิ่มได้อีกหนึ่ง read timeout) จำกัดข้อความ 16,000 ตัวอักษร และ SSE provider response 256 KB

เลื่อนโหลดประวัติเก่าต่อเนื่องและ PWA offline แบบ snapshot/ร่างทำแล้ว ยังไม่มีปุ่มหยุดสร้างคำตอบหรือการ replay ทุก event ยังไม่ได้ทดสอบโมเดลภายนอกจริงหรือการรับ stream พร้อมกันจำนวนมาก และ Incognito แบบไม่เขียนดิสก์ยังไม่เสร็จ


## AI ค้นหาและแก้รายการ / วิเคราะห์เพื่อปรับงบ

Web Chat ที่ตั้งค่าโมเดลรองรับ tools แล้ว ค้นหาจากข้อมูลจริงก่อนเสนอแก้ เช่น “ค่ากาแฟเมื่อวานที่ลง 90 จริง ๆ 75” ถ้าพบหลายรายการจะถามให้เลือก ทวนก่อน/หลัง แล้วรอพิมพ์ **ยืนยัน** การแก้เก็บประวัติและไม่แก้ ledger เดิม ถามภาพรวมรายเดือน/เดือนก่อน/งบจริงได้ และขอเสนอปรับงบเป็นแผนรอยืนยันพร้อมเหตุผลได้ ข้อมูลที่ใช้วิเคราะห์เปลี่ยนระหว่างรอจะต้องทบทวนแผนใหม่

ดูขอบเขต ช่วงค้นหา และข้อจำกัดโมเดล/Telegram ที่ [AI_ASSISTANT.md](docs/AI_ASSISTANT.md) ยังไม่ได้ทดสอบคุณภาพกับ provider จริง ไม่มี auto-post หรือเคลื่อนย้ายเงินจริง


Web Chat ใช้ลำดับโมเดล/fallback ของ workspace โดยอัตโนมัติ ทั้งห้องเดิมและใหม่ ไม่มีตัวเลือก Private/Online รายห้อง ใช้ workspace ที่เลือกอยู่เป็นค่าเริ่มต้นร่วมกับหน้าการเงินและจำในแท็บเดิม แสดงชื่อพื้นที่บนหัวแชท ผู้ช่วยไม่ถาม workspace ซ้ำเมื่อทำรายการ เปลี่ยนเองจากช่องเลือกได้ สวิตช์ Cloud AI ในศูนย์ตั้งค่า AI ยังควบคุมว่าจะอนุญาตส่งไปบริการภายนอกหรือไม่ ไม่เปิด Cloud ให้อัตโนมัติ


### AI จดหลายรายการและลดการเรียกโมเดล

Web Chat เตรียมได้สูงสุด 10 รายการจากข้อความ/รูปเดียว ทวนทั้งชุดก่อนพิมพ์ `ยืนยัน` ครั้งเดียว บันทึกแบบ atomic แก้ยอด/ลบรายการในร่างตามหมายเลขได้ เตือนข้อความที่อาจซ้ำใน workspace และบล็อกรูปที่บันทึกแล้ว ตรวจทั้งหมดใน backend โดยไม่เรียก AI เพิ่ม ข้อความหลายรายการที่ระบุครบใช้ parser โดยตรง จำกัดบริบทข้อความย้อนหลังรวม 24,000 ตัวอักษรและส่งรูปซ้ำครั้งเดียวต่อคำขอ รายละเอียด/ข้อจำกัดและตัวอย่างอยู่ใน [AI_ASSISTANT.md](docs/AI_ASSISTANT.md) ฟีเจอร์ภาพ/ภาษาธรรมชาติต้องใช้โมเดลที่รองรับ ส่วนแบบระบุครบใช้ได้ใน demo โดยไม่ตั้งคีย์


แชทรองรับ **Markdown** ทั้งประวัติและตอนทยอยตอบ: หนา/เอียง/ขีดฆ่า, `==ไฮไลต์==`, หัวข้อ รายการ ตาราง quote และโค้ดพร้อมปุ่มคัดลอก ตาราง/โค้ดยาวเลื่อนในกรอบบนมือถือ ไม่เปิด HTML/รูปภายนอกอัตโนมัติ ข้อความทวนก่อนยืนยันยังแสดงข้อมูลตามตัวอักษรจริง ไม่ต้อง migrate หรือใช้ AI เพิ่มเพื่อจัดรูปแบบ

AI เลขาส่วนตัวมีความจำแยกแต่ละคน/พื้นที่ ตั้งบัญชีเริ่มต้นและกฎหมวดได้ในตั้งค่า AI หรือสั่ง “จำไว้ว่า…” แล้วพิมพ์ยืนยัน แชทถามเฉพาะข้อมูลที่ขาด รายงานแนบการ์ดเปิดรายการต้นทาง เจ้าของดูการใช้โมเดลและตั้งราคา/วงเงินรายเดือนได้ ค่าใช้จ่ายเป็นประมาณการตามราคาที่ตั้ง ดูข้อจำกัดใน [คู่มือ AI](docs/AI_ASSISTANT.md) การอัปเดตนี้มี migration ซึ่ง Compose รันให้อัตโนมัติ ควรสำรองข้อมูลก่อนอัปเดต

### หยุด AI และตรวจปัญหาการเชื่อมต่อ

ใน Web Chat กด **หยุด** ได้ตั้งแต่รอคำตอบ คิด หรือทยอยตอบ ระบบจะไม่เก็บคำตอบบางส่วนหรือสร้างข้อเสนอที่มาหลังรับคำขอหยุด งานที่เริ่มแล้วแสดง **กำลังหยุด…** จน worker จบ ข้อความที่ตอบเสร็จและรายการที่เคยยืนยันไปแล้วคงอยู่ การปิดการเชื่อมต่อ upstream เป็น best effort อาจรอ timeout และ provider อาจคิด tokens ที่เริ่มไปแล้ว

ปุ่มทดสอบ provider และคำตอบเมื่อ AI ล้มเหลวแจ้งจุดตรวจที่ชัดขึ้น เช่น IP/พอร์ต, timeout, โมเดลไม่พบ, tools/ภาพ/Thinking ไม่รองรับ หรือ API key/สิทธิ์ โดยไม่เปิดเผยข้อความผิดพลาดดิบจาก provider ยังคงใช้โมเดลสำรองตามลำดับที่ตั้งไว้ Ollama รับ URL รากแล้วเติม `/v1` ให้อัตโนมัติ เช่น `http://192.168.25.5:11434` ดูรายละเอียดใน [คู่มือผู้ช่วย](docs/AI_ASSISTANT.md)

อัปเดตครั้งนี้มี migration `chat_generation_stop` ใช้วิธีอัปเดตตามปกติและสำรองข้อมูลก่อน: `git pull --ff-only` แล้ว `docker compose up -d --build` (หากใช้ Compose overlays ให้ใช้ชุดไฟล์เดิมของเครื่องนั้น) ห้ามลบ volumes เพื่ออัปเดต

### AI ตอบช้าแล้วหน้าเว็บโหลดค้าง

การเปิด dashboard, รายการ, ประวัติแชท และ settings ไม่ต้องรอ lock ของงาน AI แล้ว จึงเปิดดูข้อมูลที่บันทึกสำเร็จแล้วได้ระหว่าง AI รอคำตอบ ข้อมูลระหว่างเตรียมยังไม่แสดงจน commit สิทธิ์สมาชิกและ workspace ยังตรวจทุกคำขอ การแก้ไข/บันทึกใน workspace เดียวกันยังอาจรอ AI เพราะใช้ตัวป้องกันงานเขียนเดิม สามารถใช้ปุ่มหยุดได้ ไม่มี migration ใหม่สำหรับการแก้นี้

การแก้นี้ครอบคลุมการรอล็อกในแอป ไม่ได้ยืนยันสาเหตุของหน้า 502/เครื่อง restart หรือ RAM เต็มบน server จริง ซึ่งต้องตรวจเหตุการณ์ของเครื่องนั้นแยกกัน

### ทดสอบเลขา AI จากเว็บ

เจ้าของ workspace เปิด **ตั้งค่า → ศูนย์ตั้งค่า AI → ทดสอบและวิเคราะห์ AI** เลือกโจทย์จาก 5 แบบและโมเดลที่ตั้งไว้ แล้วกดเริ่ม ใช้ข้อมูล/ภาพสังเคราะห์เท่านั้น ไม่แตะ ledger หรือประวัติจริง แต่เรียก provider จริงและอาจมีค่าบริการ ดูเวลา tool tokens และสาเหตุปัญหาได้ในแท็บวิเคราะห์ย้อนหลัง 30 วัน ล้างประวัติได้ รายละเอียดและข้อจำกัดอยู่ใน [คู่มือ AI](docs/AI_ASSISTANT.md#ห้องทดสอบและวิเคราะห์-ai) อัปเดตนี้มี migration `ai_diagnostics`; การเริ่ม Compose จะให้ migrate ทำก่อน API ตามเดิม

AI Chat ใช้เครื่องมือตามงาน ตรวจร่างและให้โมเดลแก้ข้อผิดพลาดก่อนทวน เก็บข้อมูลที่กำลังถามเพิ่ม 15 นาที และแสดงขั้นตอนระหว่างทำงานแล้ว ดู [โครงสร้าง AI runtime และข้อจำกัด](docs/AI_RUNTIME.md)

### AI Chat หลัง audit (12 ตุลาคม 2026)

คำตอบยอดเงินและรายรับรายจ่ายผ่านการตรวจขอบเขตและสร้างตัวเลขจาก backend; ถ้าตีความบัญชี/หมวด/ช่วงวันไม่ได้จะถามเพิ่ม ข้อความดิบระหว่างโมเดลคิดไม่แสดงก่อนตรวจและ commit (ยังแสดงสถานะและกดหยุดได้) AI Lab ตรวจผลหลังผ่าน runtime เดียวกับแชท ไม่ใช่คะแนนความถูกต้องของข้อความดิบจากโมเดล

อัปเดตรอบนี้มี migration `ai_evidence_epoch` ควรสำรองฐานข้อมูลก่อนอัปเดตตามขั้นตอนปกติ Worker ไม่ล็อกงานเขียนใน workspace ระหว่างรอโมเดล แต่จะปฏิเสธคำตอบ/ร่างเก่าถ้าข้อมูลหรือสิทธิ์เปลี่ยนระหว่างรอ รายละเอียดและขอบเขตที่รองรับใน [AI_RUNTIME.md](docs/AI_RUNTIME.md)
# วิเคราะห์การเงินและ UX สำหรับใช้ทุกวัน

หน้า `/insights` สรุปรายรับ/รายจ่าย ค่าเฉลี่ย อันดับหมวดและบัญชี รายการจ่ายมากที่สุด แนวโน้มรายเดือน และค่าเฉลี่ยตามวันในสัปดาห์ เลือกเดือนนี้ถึงวันนี้ เดือนก่อน 90 วัน ปีนี้ หรือช่วงกำหนดเองได้ไม่เกิน 366 วัน กรองบัญชี/หมวดและกดไปดูรายการต้นทางได้ เปรียบเทียบกับช่วงก่อนหน้าที่มีจำนวนวันเท่ากัน ตัวเลขคำนวณจาก PostgreSQL โดยไม่เรียก AI และไม่ใช้ token

Dashboard แยกยอดสุทธิปัจจุบันออกจากกระแสเงินของเดือน หน้ารายการยุบตัวเลือกขั้นสูงไว้ที่ “ตัวกรอง” (รวมวันที่และ CSV) เมนูคอมแบ่งกลุ่มและตรึงบริการทั้งหมดเหนือข้อมูลผู้ใช้ เมนูมือถือมีทางเข้าวิเคราะห์ ส่วน AI Inbox อยู่ในบริการทั้งหมด หน้าแชทมีตัวอย่างคำถามเพิ่มและข้อความประกอบที่อ่านชัดขึ้น ไม่มี migration หรือ `.env` ใหม่สำหรับชุดนี้
