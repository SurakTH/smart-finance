# ผู้ช่วย AI บนเว็บและ Telegram

## วันที่ในแชท (14 ตุลาคม 2026)

ส่งคำถามเช่น “สัปดาห์ที่แล้วใช้ไปเท่าไหร่”, “เมื่อวานละ”, “วันที่ 13/10 ละ” ได้เลย AI ส่งคำวันที่เดิมให้backendคำนวณ ไม่ต้องเลือก period.mode หรือพิมพ์ISOเอง ช่วงสัมพันธ์ใช้วันปัจจุบันกรุงเทพ วันที่ไม่ใส่ปีใช้ปีปัจจุบันและแสดงช่วงที่ใช้จริง สัปดาห์ที่แล้วหมายถึงจันทร์–อาทิตย์ของสัปดาห์ก่อน

ถ้าAIส่งชื่อช่วงผิด ละวันที่ หรือส่งช่วงมาไม่ครบ ระบบซ่อมเฉพาะวันที่จากข้อความuserที่มีช่วงเดียวชัดเจน และยังตรวจสิทธิ์/บัญชี/ช่วงวันตามเดิม ถ้าหลายช่วงกำกวมหรือวันที่ไม่มีจริงจึงถามเพิ่ม คำถามต่อที่มีแต่วันจะคงตัวกรองจากการอ่านก่อนหน้าเฉพาะข้อความต่อกันในห้องเดียวและบริบทยังไม่หมดอายุ การเริ่มเรื่องใหม่หรือเว้นจนบริบทหมดอายุจะไม่เอาตัวกรองเก่ามาใช้เอง

## อ่านข้อมูลเองและตอบเป็นภาษาปกติ (14 ตุลาคม 2026)

ผู้ใช้ไม่ต้องพิมพ์คำสั่งตาม format หรือใส่ชื่อเครื่องมือ เช่น “อาทิตย์ก่อนกระเป๋าฉันโดนไปหนักแค่ไหนจ๊ะ” โมเดลเรียก `fetch_finance` เพื่ออ่านยอด รายการ งบ หรือ analytics ที่ต้องการได้ทันที ไม่ต้องผ่านเครื่องมือวางแผนก่อน ถ้าต้องดูหลายอย่างประกอบกันเรียกอ่านต่อได้ภายในขอบเขตเดิม จากนั้นตอบเป็นภาษาไทย/Markdown และตัวเลขปกติ ไม่บังคับใช้ answer tool หรือ fact placeholders `lookup_workspace` ยังใช้ค้นชื่อบัญชี หมวด เป้าออม รายการประจำ และความชอบส่วนตัวได้

วันที่สัมพันธ์คำนวณที่ backend และแสดงช่วงที่ใช้จริง ถ้าไม่ได้เลือกช่วง รายงานเริ่มเดือนถึงวันนี้ รายการย้อนหลัง30วัน งบเดือนนี้; ยอดบัญชีเป็นยอดสะสมปัจจุบัน รายการแบ่งหน้าครั้งละ10 แต่ยอดรวมคำนวณจากรายการครบทั้งช่วง ไม่บวกจากหน้าที่เห็นเท่านั้น ช่วงกำกวมหรือชื่อไม่ชัดยังถามเฉพาะข้อมูลนั้นได้ โดยไม่สั่งให้กรอก JSON หรือรูปแบบคำสั่ง

ระบบตรวจ arguments ภายในของ AI รวมถึงสิทธิ์และตัวเลข ไม่ใช่ตรวจว่าผู้ใช้ต้องพูดตามรูปแบบ โมเดลเลือก user/workspace/ห้องแชทเองไม่ได้ อ่านตามผู้ใช้ที่เข้าสู่ระบบ สมาชิกพื้นที่ และเจ้าของห้องแชทเท่านั้น ID บัญชี/หมวดต่างพื้นที่ถูกปฏิเสธ ทุกการอ่านตรวจสมาชิกอีกครั้ง และก่อนส่งคำตอบยังมี stop/context/epoch/authorization fences เหมือนเดิม ความจำและห้องแชทส่วนตัวไม่ใช้ร่วมกัน ส่วน ledger ของ workspace ที่เชิญสมาชิกมาร่วมโดยตั้งใจ ยังคงเป็นข้อมูลร่วมของสมาชิกในพื้นที่นั้น

ตัวเลขที่ AI ตอบถูกเทียบกับข้อมูลที่อ่านจริง ถ้าไม่ตรงให้ AI แก้ภายในก่อนใช้รายงานจริงสำรอง การตรวจนี้ไม่ใช่การพิสูจน์ว่าการตีความคำถาม ตัวกรอง หรือเหตุผลที่โมเดลอธิบายจะถูกทุกครั้ง การบันทึก/แก้ไขยังต้องมีร่างจริงและให้ผู้ใช้พิมพ์ **ยืนยัน** ไม่ให้ข้อความธรรมดาของโมเดลกลายเป็นหลักฐานว่ามีร่างหรือบันทึกแล้ว

## สนทนาด้วยความหมาย ไม่บังคับรูปแบบคำสั่ง (14 ตุลาคม 2026)

เครื่องมือหลักของโมเดลเปลี่ยนเป็น `understand_request` ให้โมเดลตีความข้อความ ประวัติ ชื่อเรียกบัญชี และช่วงเวลาของผู้ใช้ ไม่ต้องพูดตรงคำศัพท์หรือวันที่ตามแพตเทิร์นของ backend ตัวอย่าง “ตั้งแต่เปิดเดือนมาจนตอนนี้เหมือนเงินไหลไปกับคาเฟ่ ช่วยไล่ให้หน่อย” โมเดลเลือกช่วง คำค้น และประเภทข้อมูลเอง แล้วระบบตรวจชนิด/สิทธิ์/บัญชีใน workspace/ขนาดช่วง ก่อนอ่านฐานข้อมูล ไม่รัน legacy subject regex มาบังคับให้โมเดลยอมรับคำค้นที่ backend เดาผิดซ้ำ

คำถามต่ออย่าง “เรื่องเดิม”, “รวมทุกอย่างเลย”, “แล้วบัญชีนี้ตอนนี้เหลือเท่าไร” ใช้ขอบเขตที่ตรวจไว้ในห้องเดิม โมเดลเปลี่ยนช่วง/ตัวกรองตามความหมายได้ เมื่อเปลี่ยนจากรายจ่ายเป็นยอดบัญชี ระบบไม่เอาคำค้นรายจ่ายหรือชนิดรายการเดิมมาปน ชื่อเล่นอาจถูกโมเดลแปลงเป็นชื่อจริงจาก lookup; backend ตรวจชื่อที่มีอยู่และไม่เลือกบัญชีชื่อกำกวมให้เอง วันที่สัมพันธ์คำนวณใน backend ช่วงวันที่ที่โมเดลตีความเองต้องเรียงถูกและไม่เกิน366วัน พร้อมแสดงช่วงและตัวกรองในคำตอบ

หลังอ่านข้อมูล โมเดลใช้ `respond_finance` เรียบเรียงคำตอบธรรมชาติ อธิบายสิ่งที่เห็นหรือชวนวางแผนต่อ ตัวเลขใช้ fact slots ที่ backend เติมจากผลคำนวณจริง เช่นจำนวนเงิน จำนวนรายการ ค่าเฉลี่ย งบ และตัวเปรียบเทียบ ผู้ใช้ไม่เห็นหรือต้องพิมพ์ slots เหล่านี้ โมเดลใส่จำนวนอิสระ/คีย์ที่ไม่มีจริง/อ้างบันทึกสำเร็จจะถูกซ่อมภายใน; ถ้ายังตอบไม่ผ่านคืนรายงานจริงแทนการบังคับผู้ใช้กรอก schema

ข้อมูลที่โมเดลส่งเข้า tool ผิดจะส่ง field feedback ให้โมเดลแก้ก่อน ภายในเพดานเดิม ถ้ากำกวมจริงโมเดลถามเรื่องนั้นเป็นภาษาไทยตามธรรมชาติ ไม่ถามเมนูดูหรือบันทึกทุกครั้ง คุยเรื่องทั่วไปหรือแนวคิดจัดการเงินได้โดยไม่บังคับออก report การบันทึก/แก้ยังไป typed draft และต้องทวน/รอยืนยันจากผู้ใช้เหมือนเดิม

`interpret_request` แบบตรวจ phrase เดิมยังรองรับภายในเพื่อ compatibility แต่ไม่อยู่ใน initial catalog แล้ว คำถามข้อความล้วนที่รู้ขอบเขตครบจากรุ่นก่อนยังอ่านโดยตรงได้เพื่อประหยัดคำขอ คำถามอื่นมีเส้นทาง model-led เป็นหลัก โดยทั่วไปอ่าน→ตอบใช้2model requests และอาจเพิ่มเมื่อซ่อม ไม่ใช่ข้ออ้างว่าทุกกรณีเร็วหรือถูกกว่าก่อนโดยยังไม่ benchmark

ใน **AI Lab** เพิ่มโจทย์ **คุยภาษาธรรมชาติและตอบจากข้อมูลตัวอย่าง** ใช้ schema/runtime ใหม่และ fake facts เท่านั้น ไม่อ่าน ledger/ชื่อบัญชีจริง ไม่เฉลย alias/date mode ใน prompt และตรวจว่าทั้งอ่านกับตอบ fact slots สำเร็จ ผลสังเคราะห์ไม่รับรองว่าทุกสำนวนของ Qwen/Gemma จริงจะถูกต้อง การตีความวัน/ตัวกรองและคำอธิบายเชิงความหมายยังอาจผิด ต้องดูขอบเขต/หลักฐานที่แนบด้วย ไม่มี semantic search ทุกคำพ้อง/เว็บค้นข้อมูลภายนอกหรือการรับรองเหตุเชิงสาเหตุเพิ่มในรอบนี้

## แก้คำถามภาษาพูดและคำถามต่อ (14 ตุลาคม 2026)

คำถามอ่านข้อมูลแบบสั้นที่ระบบรู้ขอบเขตครบ เช่น “เมื่อวานเสียตังกับไรบ้าง”, “สัปดาห์ที่แล้วใช้ตังไรบ้าง”, “เดือนนี้ละ ใช้ตังเท่าไหร่” และ “เมื่อวานมีไรบ้าง” อ่านจาก ledger โดยตรงใน runtime ไม่ต้องเรียกโมเดลให้แปลง schema ก่อน คำพูดตัง/ตังค์/ละ/ล่ะไม่กลายเป็น description filter ทางลัดนี้ใช้เฉพาะข้อความล้วน ไม่แย่งงานอ่านข้อความที่แนบรูป ทุกคำต้องตรง grammar ทั้งข้อความ ถ้ามีชื่อบัญชี หมวด คำค้น ตัวเลข คำขอแก้ไข/บันทึก หรือโจทย์ซับซ้อนเพิ่มเติม ใช้เส้นทางโมเดลและตรวจสิทธิ์เดิม ไม่ตัดทิ้งเพื่ออ่านยอดรวมกว้างขึ้น

ช่วงสัปดาห์ก่อน/สัปดาห์ที่แล้ว/อาทิตย์ก่อน/อาทิตย์ที่แล้วเป็นจันทร์–อาทิตย์ของสัปดาห์ก่อนตามเวลาไทย ไม่ fallback เป็นเดือนปัจจุบัน งานรายการแสดงวันที่ ยอด บัญชี และหมายเลขจากรายการจริง ยอดรวมไม่ขึ้นกับหน้าที่แสดง รายงานกรองเฉพาะรายจ่าย/รายรับแสดงเฉพาะชนิดนั้น รวมถึงการ์ดหลักฐาน ไม่แสดงอีกชนิดเป็นศูนย์เสมือนเป็นยอดทั้งพื้นที่

“วันอาทิตย์ละ” จะถามว่าเป็นวันที่เท่าไร ไม่เดาวันหรือถามซ้ำว่าต้องการดู/บันทึก ตอบ “ที่ผ่านมา” หรือ “ที่จะถึง” ต่อได้ทันที บริบทผูกกับห้อง ข้อความผู้ใช้ก่อนหน้า และหมดอายุ15นาที ถ้ามีคำถามอื่นแทรกจะไม่ใช้บริบทเก่านี้ “วันพุธที่ผ่านมา” ในวันพุธหมายถึงพุธสัปดาห์ก่อน; “วันนี้” ใช้วันปัจจุบัน

คำถามต่อที่มีละ/ล่ะคงตัวกรองบัญชี/หมวด/คำค้นจากรายงานก่อนหน้าที่ยัง valid ภายในห้อง/workspaceเดียวกัน ตรวจบัญชีอีกครั้ง ไม่คงตัวกรองข้อความผิด “ละ ใช้ตัง” ที่รุ่นเดิมเคยสร้าง การแก้เป็นบริบทแชทเท่านั้น ไม่แก้รายการเงินย้อนหลัง

สถานะ `repairing` หมายถึงกำลังตรวจแผนหรือ arguments จากโมเดลอีกครั้ง ไม่ใช่การแก้ข้อมูลผู้ใช้ หน้าเว็บแสดง “กำลังตรวจคำถามและเงื่อนไขอีกครั้ง…” แล้ว ขอบเขตนี้ไม่ได้รับรองว่าภาษาพูดทุกสำนวนหรือการเลือก tools ของโมเดลทุกตัวจะถูกต้องทั้งหมด

## วิเคราะห์ข้อมูลหลายรูปแบบ (14 ตุลาคม 2026)

Web Chat และ Telegram ใช้ `interpret_request` → `intent=analytics` เส้นทางเดียวกัน โมเดลแปลงคำถามเป็นช่วงวัน ตัวกรอง และประเภทวิเคราะห์ จากนั้น SQL รวมรายการที่ตรงเงื่อนไขทั้งหมด ไม่ส่งประวัติรายการทั้งหมดให้โมเดลและไม่รวมยอดจากหน้าตัวอย่าง ผลและคำอธิบายเชิงตัวเลข render จาก backend ที่ตรวจแล้ว แทนการยอมรับตัวเลขหรือคำอ้างสาเหตุใน model prose

| วิเคราะห์ | ผลที่ได้ |
|---|---|
| `summary` / `average` | ยอด จำนวนรายการ เฉลี่ยต่อวันปฏิทิน (รวมวันไม่มีรายการ) และต่อรายการ |
| `compare` | สองช่วงวันที่อิสระ ยอดส่วนต่าง เปอร์เซ็นต์ และส่วนต่างเฉลี่ยต่อวัน เตือนจำนวนวันไม่เท่ากัน/ช่วงซ้อนกัน |
| `trend` | รายวัน/สัปดาห์จันทร์–อาทิตย์/เดือน เติมศูนย์วันที่ไม่มีรายการและตัดขอบให้ตรงช่วง รวมครบก่อนแสดง 12 ช่วงท้าย พร้อมช่วงยอดสูงสุด/ต่ำสุดทั้งหมด |
| `ranking` | หมวด บัญชี หรือรายละเอียดตรงกัน มาก→น้อย/น้อย→มาก สูงสุด 10 กลุ่ม สัดส่วนใช้ยอดครบทุกกลุ่ม ไม่ใช่เฉพาะอันดับที่แสดง |

ตัวอย่างคำถาม:

- “ค่าเฉลี่ยรายจ่ายกาแฟ 2026-10-01 ถึง 2026-10-14”
- “เปรียบเทียบรายจ่าย 2026-10-01 ถึง 2026-10-14 กับ 2026-09-01 ถึง 2026-09-14”
- “แนวโน้มรายจ่ายรายวันเจ็ดวันที่ผ่านมา”
- “อันดับรายจ่ายตามบัญชีเดือนนี้”
- “วิเคราะห์รายรับ 1/10/2569 ถึง 14/10/2569”

ใช้รายจ่ายเป็นค่าเริ่มต้น หรือระบุรายรับ วิเคราะห์ครั้งละหนึ่งชนิด ไม่ปนการโอน/จ่ายบัตร/ยอดยกมาเป็นรายรับรายจ่าย ช่วงละไม่เกิน 366 วันรวมวันแรกและวันสุดท้าย รองรับวันที่ ISO และ dd/mm/yyyy รวม พ.ศ./เลขไทย ตลอดจนวัน/สัปดาห์/เดือนแบบสัมพันธ์ที่ interpreter รองรับเดิม คำถามที่กำกวมหรือวัน/ชื่อ/ชนิดขัดกับแผนต้องถามเพิ่ม เปรียบเทียบต้องระบุช่วงเทียบ ไม่เดาว่าต้องการเดือนก่อนหรือช่วงยาวเท่ากัน

ฐานข้อมูลแยก workspace ตลอดเส้นทาง ตัดรายการเดิมที่ถูกแก้และ journals กลับรายการออกจากการวิเคราะห์ ใช้ยอดล่าสุดที่ยัง active ลิงก์หลักฐานเก็บวัน/บัญชี/หมวด/ชนิด/คำค้นตรงกันทั้งสองช่วง งานอ่านไม่สร้างร่างหรือบันทึกเงิน ค่าเฉลี่ยต่อรายการเมื่อไม่มีรายการ และเปอร์เซ็นต์เทียบฐานศูนย์แสดงว่าคำนวณไม่ได้ ยอดเท่ากันจัดอันดับตามชื่อแล้วรหัส; อันดับน้อยสุดนับเฉพาะกลุ่มที่มีรายการ

ยังไม่รองรับ forecast, การอธิบายเหตุเชิงสาเหตุโดยไม่มีหลักฐาน, การเทียบรายรับกับรายจ่ายในคำสั่งเดียว หรือการรวมหลายสกุลเงิน ผล mock tests พิสูจน์การคำนวณ/สิทธิ์และการเชื่อม runtime ไม่ได้พิสูจน์ว่า Qwen/Gemma จริงเลือกแผนถูกทุกสำนวน

## Telegram แบบผู้ช่วยสนทนา

พิมพ์ **`/new` หรือ `/reset`** เพื่อเริ่มห้องใหม่ โดยเก็บห้องและข้อความเดิมไว้บนเว็บ ยกเลิกร่างที่ยังไม่ยืนยัน/ข้อมูลถามต่อ/งานและคำตอบค้างของห้องเดิม ไม่ลบ ledger หรือความชอบส่วนตัวที่เคยตั้งไว้ คำยืนยันใหม่ใช้ได้เฉพาะร่างในห้องใหม่ ไม่ย้อนยืนยันร่างเก่า ส่งคำสั่งเดิมซ้ำจาก Telegram retry ไม่สร้างห้องเพิ่ม งานโมเดลที่เริ่มแล้วหยุดแบบ best effort แต่ตรวจ stop/context ก่อนสร้างร่างเสมอ ข้อความที่ส่งถึง Telegram ไปแล้วเรียกคืนไม่ได้

หลังเชื่อมบัญชี ส่งข้อความหรือรูปพร้อมคำบรรยายได้ เช่น “ค่าหนังสือ” พร้อมสลิป หรือ “เดือนนี้ใช้ไปเท่าไร” ใช้ลำดับ Chat models, fallback, timeout, thinking, Cloud switch และเครื่องมือที่ตั้งไว้ใน workspace เดียวกับเว็บ รูปต้องใช้โมเดลที่รองรับภาพและเปิด **รับรูปภาพในแชท** ไม่มีโมเดลที่อ่านภาพได้จะบอกตามจริง ไม่เดายอด

ประวัติอยู่ในห้องของเจ้าของชื่อ **Telegram · ผู้ช่วย AI** บนเว็บ (ห้องเก่าอาจใช้ชื่อเดิม) แยกแต่ละ Telegram account/ผู้ใช้/workspace ร่างจาก AI ต้องทวนผ่าน backend ก่อน แล้วผู้ใช้พิมพ์ **ยืนยัน** ใน Telegram ได้เลย ไม่ต้องเปิด Inbox สำหรับรูปใหม่ ระบบรอส่งข้อความทวนครบทุกส่วนก่อนอนุญาตยืนยัน รูปที่ยืนยันแล้วเก็บเป็นหลักฐานตามกติกาเว็บ ไม่ auto-post จากภาพหรือคำตอบโมเดล

ต้องเปิดทั้งบริการ `telegram` และ `worker` ระหว่างเข้าคิวบอตไม่ส่งข้อความรับเรื่องซ้ำ ส่งเฉพาะคำตอบจริง/ข้อผิดพลาด/ข้อความทวนหรือยืนยันผล คำตอบจาก worker มีคิวส่งกลับถาวร รองรับ restart, แบ่งข้อความยาว และ retry เมื่อ Telegram ขัดข้อง ตรวจ membership/การเชื่อมต่อ/workspace/การหมดอายุห้องก่อนส่งแต่ละส่วน ถ้ายกเลิกเชื่อมหรือเปลี่ยน workspace จะยกเลิกคำตอบเก่าที่ยังไม่ส่ง การส่งภายนอกเป็น at-least-once: หาก process ล้มหลัง Telegram รับข้อความแต่ก่อนบันทึกผล อาจเห็นข้อความส่วนเดิมซ้ำได้ แต่ update ID และการยืนยันยังป้องกัน ledger ซ้ำ

ข้อความและรูปผ่าน Telegram ก่อนถึงระบบ แม้ตั้งใช้ Ollama เท่านั้นจึงไม่ใช่ช่องทาง local-only ทางเครือข่าย ส่งคำตอบเป็น plain text และปิด link preview; ยังไม่มีปุ่มหยุดและรูปแบบ Markdown บน Telegram (ใช้ /new หรือ /reset เพื่อเลิกคำขอเดิมและเริ่มใหม่ได้) การทดสอบใช้ model transport/Telegram sender จำลอง ไม่ได้รับรองความแม่นยำ OCR หรือภาษาเมื่อใช้โมเดลจริง

## ตั้งค่า

เจ้าของ workspace เปิด **ตั้งค่า → ศูนย์ตั้งค่า AI** (`/ai-settings`) เพิ่มโมเดลงาน **Chat** ระบุ provider/ชื่อโมเดล/API key หรือเลือก Ollama ที่ผู้ดูแลติดตั้งแล้ว จัดลำดับหลักและสำรองได้ คีย์เข้ารหัสที่ backend และไม่ส่งกลับ browser ไม่ต้องใส่คีย์ใน `.env`

- เปิด **รับรูปภาพในแชท** เฉพาะโมเดลที่รองรับภาพจริง การเรียก Chat ใช้ OpenAI-compatible Chat Completions พร้อม function tools; รุ่นที่รับแต่ข้อความหรือไม่รับ tools อาจใช้ไม่ได้
- เลือก **Thinking** ของแต่ละโมเดล ค่าเริ่มต้นไม่ส่ง effort เพิ่ม ระดับอื่นขึ้นกับ provider/รุ่น ไม่ใช่ทุกโมเดลรองรับทุกค่า ระบบปฏิเสธบางชุดที่ทราบว่าใช้ไม่ได้ แต่ไม่สามารถยืนยันความสามารถจากชื่อโมเดลเพียงอย่างเดียว
- เพิ่ม timeout และจำนวน output tokens สำหรับ thinking มาก (บางบริการนับ reasoning ในงบเดียวกับคำตอบ) เมื่อเลือก effort ระบบไม่ส่ง temperature และใช้ sampling default ของโมเดล Timeout ต่อ request สูงสุด 60 วินาทีและมีงบ soft deadline รวม 90 วินาที ไม่รองรับงานคิดยาวหลายสิบนาที
- ปุ่มทดสอบใช้ข้อความสังเคราะห์ และภาพขาวสังเคราะห์เมื่อเปิดรับรูป ไม่ส่งบัญชีหรือประวัติการเงิน เป็นเพียงการตรวจเรียก API ได้ ไม่รับรองคุณภาพ OCR หรือความถูกต้องของ function arguments
- แชททุกห้องใช้ลำดับโมเดลและ fallback ที่ตั้งไว้ใน workspace โดยไม่เลือก Private/Online รายห้อง เปิด Cloud AI ในศูนย์ตั้งค่า AI เมื่อต้องการใช้บริการภายนอก ปิดเพื่อใช้เฉพาะ Ollama/demo ทั้งรูปและประวัติที่ส่งให้ Cloud อยู่ภายใต้นโยบายของบริการนั้น ห้องเดิมและงานแชทที่ยังรอใช้ค่าปัจจุบันนี้ด้วย

## สนทนาและจดเงิน

โมเดล Chat รับข้อความทั่วไปได้ ไม่จำเป็นต้องเริ่มจากคำสั่งการเงิน เช่น “วันนี้เหนื่อย ช่วยวางแผนพรุ่งนี้หน่อย” จากนั้นคุยเรื่องเงินต่อได้ ตัวอย่าง:

```text
คุณ: [แนบรูป] ช่วยจดค่าอาหารในรูปนี้หน่อย
ผู้ช่วย: จ่ายจากบัญชีไหนคะ?
คุณ: เงินสดจ้า
ผู้ช่วย: [ทวนยอด วันที่ บัญชี หมวด และรูปหลักฐาน]
คุณ: ยืนยัน
ผู้ช่วย: [ผลการบันทึกจากระบบ]
```

โมเดลใช้ `prepare_transaction` เสนอรายการเงิน หรือ `prepare_management_plan` เสนอแผนจัดการ 1–10 ขั้นตอนต่อครั้ง ทั้งสองไม่มีสิทธิ์ยืนยัน ต้องพิมพ์ ยืนยัน จากห้องและข้อความทวนล่าสุดภายใน 15 นาที เมื่อข้อมูลเปลี่ยนให้สั่งใหม่ หากโมเดลอ่านรูปหรือเข้าใจผิด ผู้ใช้ต้องแก้/ยกเลิกก่อนยืนยัน

## สั่งงานแบบเลขาเป็นชุด

ใช้ Chat model ที่รองรับ function tools แล้วบอกความต้องการ เช่น:

- “สร้างหมวดสัตว์เลี้ยง ตั้งงบเดือนนี้ 2,000 บาท แล้วสร้างเป้าเงินฉุกเฉิน 50,000 บาท”
- “เปลี่ยนชื่อเงินสดเป็นกระเป๋าสตางค์ แล้วคัดลอกงบเดือนก่อนมาเดือนนี้”
- “เปลี่ยนเป้าเที่ยวญี่ปุ่นเป็น 80,000 บาท สิ้นปีนี้ ส่วนรายการค่าเน็ตพักไว้ก่อน”
- “ตั้งค่าอาหารแมว 600 บาททุกเดือนจากเงินสด หมวดสัตว์เลี้ยง เริ่มวันนี้”

ก่อนยืนยันยังแก้บางส่วนต่อได้ เช่น “งบสัตว์เลี้ยงเอาเป็น 3,000 ที่เหลือเหมือนเดิม” ระบบส่งแผนเดิมที่ยังไม่ยืนยันเป็นบริบทให้โมเดลเตรียมทั้งชุดใหม่ ต้องตรวจและยืนยันข้อความทวนใหม่ ไม่ใช้ข้อความทวนเก่า

ถ้าชื่อ/ข้อมูลกำกวมผู้ช่วยควรถามก่อน และเมื่อได้ข้อมูลครบ backend ทวนทั้งชุดให้ตรวจพร้อมรายละเอียด **ก่อน → หลัง** ผู้ใช้พิมพ์ยืนยันครั้งเดียว ทำทั้งชุดใน transaction เดียว หากล้มเหลวย้อนกลับทั้งหมด ยืนยันซ้ำไม่ทำซ้ำ ระบบตรวจบัญชี/งบ/เวอร์ชันเป้าหมายและรายการประจำจาก snapshot ก่อนเขียน หากมีการเปลี่ยนระหว่างรอจะไม่ใช้แผนเก่า ให้สั่งใหม่เพื่อเตรียมข้อมูลล่าสุด

| งาน | ทำผ่านแชทได้ |
|---|---|
| บัญชี/หมวด | สร้างบัญชีเงิน/บัตรหรือหมวดรายรับ/รายจ่าย เปลี่ยนชื่อ; สร้างแล้วอ้างในงบ/รายการประจำในชุดเดียวกันได้ |
| งบเดือน | ตั้ง/แก้ยอด นำงบออก คัดลอกจากเดือนก่อนโดยไม่ทับงบเดิมในเดือนปลายทาง |
| เป้าออม | สร้าง แก้ชื่อ/ยอดเป้า/วันครบกำหนด เก็บหรือเปิดอีกครั้ง |
| รายการประจำ | สร้างรายรับ/รายจ่ายรายวัน/สัปดาห์/เดือน พักหรือเปิดอีกครั้ง |

บัญชีใหม่ยอด **0** ไม่เดายอดตั้งต้น เปลี่ยนชื่อจะเปลี่ยนชื่อที่แสดงในประวัติเดิมด้วยแต่ไม่แก้ ledger งบและเป้าเป็นแผน ไม่โอนเงินหรือจัดสรรเงินออมให้เอง รายการประจำสร้างข้อเสนอเข้า Inbox ที่ผู้ใช้ต้องยืนยันในแต่ละรอบ การพักไม่ลบข้อเสนอที่สร้างแล้ว เปิดใหม่อาจมีรอบค้าง

ดู **เมนูแชท → ประวัติงานผู้ช่วย** เพื่อดูแผนที่ทำสำเร็จ แบ่งหน้าครั้งละ 10 รายการ แสดงผู้ยืนยัน เวลา และรายละเอียด สมาชิกพื้นที่อ่านร่วมกันได้ ประวัติ append-only ใน PostgreSQL ยังอยู่หลังลบแชท/หมดอายุห้อง (ร่างที่ยังไม่ยืนยันจะถูกลบตามห้อง) เก็บ metadata แผนและ snapshots ในฐานข้อมูล จึงต้องจัดอายุ backup ให้เหมาะสม ไม่ส่ง payload ประวัติทั้งหมดให้ browser

ใช้สิทธิ์สมาชิกพื้นที่เช่นเดียวกับหน้าจัดการเดิม ไม่เพิ่มสิทธิ์ผ่านโมเดล รหัส/คีย์/สมาชิก/workspace ยังคงจัดการจากหน้าที่เกี่ยวข้อง ไม่มี tools ลบบัญชี หมวด หรือ ledger เปลี่ยนชนิดบัญชี หรือแก้ข้อมูลภายในตามใจ ชื่อซ้ำชนิดเดียวกันต้องเลือกชื่อใหม่ ส่วนงาน transaction กับ management เป็นข้อความทวนคนละประเภท ไม่รวมลงเงินกับเปลี่ยนโครงสร้างในคำยืนยันเดียว

ตอบทั่วไปทยอยแสดงได้ ส่วน tool arguments และฟิลด์ reasoning ไม่ส่งเป็นคำตอบ เริ่มด้วยคำสั่งผู้ช่วย/workspace/วันที่ และประวัติล่าสุดไม่เกิน20ข้อความ (24,000ตัวอักษรรวม/4,000ต่อข้อความ) ไม่แนบบัญชี ยอด แผน และความชอบทั้งพื้นที่ก่อนคุย ใช้ tools ค้นเฉพาะข้อมูลที่จำเป็น; แผนรอยืนยันที่กำลังแก้ส่งเป็นบริบทได้สูงสุด10ขั้นตอน โมเดลไม่มี SQL tool หรือสิทธิ์เลือก workspace/user อื่น การเรียบเรียงหรือคำตอบทั่วไปยังอาจผิดได้

รูปใหม่ไม่สร้าง pending Inbox แยกออกจากแชท ถ้าไม่มี vision provider ที่ใช้ได้ จะบอกว่ายังอ่านรูปไม่ได้ ไม่เดายอดและไม่สร้างร่างจากรูปใน demo mode ก่อนยืนยัน รูป/ร่างเป็นของเจ้าของห้อง หลังยืนยันจะเก็บรูปเป็นหลักฐานการเงินผ่าน confirmed Proposal และสมาชิกพื้นที่เห็นได้ หลักฐานยังอยู่หลังลบแชท รูปที่ยืนยันแล้วไม่บันทึกซ้ำผ่าน Chat/Inbox รูปหนึ่งที่มีร่างอีกห้องต้องจัดการร่างเดิมก่อน

## ข้อจำกัดและความเข้ากันได้

การแก้ยอดร่างใช้ “จริง ๆ 90 บาท” ได้ การแก้รายการที่บันทึกแล้วใช้ “แก้รายการล่าสุดเป็น 95 บาท” คำขอจากหน้ารายการ หรือค้นหาด้วยภาษาธรรมชาติตามรายละเอียดด้านล่าง งานจัดการรองรับเฉพาะตารางข้างต้น ยังไม่รองรับจัดสรรเงินเข้าเป้าออมผ่านโมเดล แก้รายละเอียดรายการประจำที่มีอยู่ ลบ ledger สมาชิก รหัสผ่าน หรือ API keys แบบอิสระ Telegram ใช้ conversation และเครื่องมือ AI ชุดเดียวกับเว็บแล้ว ถ้าไม่มีโมเดลหรือ fallback เป็น demo การคุยทั่วไปไม่ใช่ LLM

| Provider | การส่ง Thinking |
|---|---|
| OpenAI / Compatible / Ollama / Gemini | `reasoning_effort` เมื่อเลือกค่าที่ไม่ใช่ default |
| OpenRouter | `reasoning.effort` และ `reasoning.exclude=true` |
| Groq | `reasoning_effort` และซ่อน reasoning ตามรุ่น |

OpenAI/Groq ใช้ `max_completion_tokens`; provider อื่นใช้ `max_tokens` ไม่ retry ด้วยการลบ effort ที่ผู้ใช้เลือก เมื่อ request ใช้ไม่ได้จะ retry/fallback ตาม route ที่ตั้ง แต่ upstream บางตัว เช่น Ollama บางรุ่น อาจใช้ค่าเริ่มต้นเมื่อไม่รู้จักระดับ จึงไม่อ้างว่าค่า thinking บังคับได้เหมือนกันทุกบริการ

เอกสารอ้างอิงหลัก: [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create), [Gemini OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai), [OpenRouter reasoning](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens), [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility), [Groq reasoning](https://console.groq.com/docs/reasoning)

ผลทดสอบรอบนี้ใช้ PostgreSQL จริงใน Docker และ HTTP transport จำลอง ยังไม่ได้เรียกด้วย API key จริงหรือทดสอบคุณภาพโมเดล vision/Ollama จริง ดูผลที่ [VERIFICATION.md](VERIFICATION.md)


## ค้นหา แก้รายการ และเสนอปรับงบจากข้อมูลจริง

เมื่อใช้ Chat model ที่รองรับ native function tools ถามได้ เช่น “เดือนนี้ใช้เท่าไหร่ บัญชีไหนเยอะสุด” หรือ “ค่ากาแฟเมื่อวานที่ลง 90 จริง ๆ 75 ช่วยแก้ให้ที” โมเดลใช้ `query_finance` อ่านข้อมูลจริงใน workspace นี้ แล้วใช้ `prepare_correction` สร้างข้อความทวนก่อน/หลัง ต้องพิมพ์ **ยืนยัน** ก่อนแก้ ระบบใช้ correction แบบกลับรายการเดิมและสร้างรายการทดแทนพร้อมประวัติ ไม่แก้ journal เก่า

ค้นหารายการที่ยังใช้งานอยู่ด้วยคำค้น วันที่ ประเภท บัญชี หมวด หรือยอดเดิม ช่วงเริ่มต้นคือ 30 วันล่าสุด ระบุได้ไม่เกิน 366 วัน ผลครั้งละไม่เกิน 10 รายการและบอกเมื่อยังมีเพิ่มเติม พบหลายรายการต้องให้ผู้ใช้เลือก เช่น “รายการที่ 2” โมเดลเลือกตัวแรกหรือค้นแคบเองในข้อความเดียวเพื่อข้ามการถามไม่ได้ รายการที่ผู้ใช้เลือกต้องตรงกับรายการที่แก้ ผลค้นหามีอายุ 15 นาที และตรวจข้อมูลล่าสุดอีกครั้งก่อนสร้างร่าง

แก้ได้เฉพาะยอด คำอธิบาย วันที่ บัญชี หมวด และบัญชีปลายทางตามชนิดรายการเดิม ไม่เปลี่ยนประเภท ไม่ลบ ledger และไม่แก้ยอดตั้งต้นผ่าน tool นี้ ช่องที่ไม่ขอแก้คงค่าเดิม ขั้นตอนแก้ร่าง/ยืนยัน/กันกดซ้ำและข้อมูลเปลี่ยนระหว่างรอยืนยันใช้ระบบเดิม

“ช่วยวิเคราะห์เดือนนี้ แล้วเสนอปรับงบอาหารให้หน่อย” จะอ่านยอดรายรับ/รายจ่ายจริง เดือนก่อน หมวด บัญชีที่ใช้จ่าย และงบพร้อมยอดใช้จริงจาก backend ก่อนเสนอแผน คำขอวิเคราะห์อย่างเดียวตอบเป็นข้อความ ไม่มีการเปลี่ยนงบ หากขอปรับงบจึงสร้างแผนรอยืนยัน แยก **ข้อมูลจริงจากระบบ** ออกจาก **ข้อเสนอจากผู้ช่วย (ควรตรวจสอบ)** หากข้อมูลรายเดือนหรืองบที่ใช้วิเคราะห์เปลี่ยนก่อนยืนยัน แผนนั้นจะไม่ทำงาน ต้องทบทวนใหม่

ข้อมูลรายเดือนส่งรายละเอียดหมวด/บัญชี/งบสูงสุดกลุ่มละ 20 รายการ พร้อมจำนวนทั้งหมด ยอดรวมคำนวณจากข้อมูลทั้งเดือน หน่วยเครื่องมือเป็นสตางค์ ไม่มี SQL tool จำกัดอ่านไม่เกิน 3 ครั้งต่อข้อความ รวม retry/fallback และไม่เกิน 4 รอบโมเดลต่อ attempt บริบทผลค้นหาและรายงานสูงสุด 3 เดือนเก็บในห้องชั่วคราว 15 นาที ใช้ provider route ของ workspace ปิด Cloud AI เพื่อไม่ส่งไป cloud หากไม่มีโมเดลที่รองรับจะใช้ความสามารถแบบกฎ/รายงานเดิม ข้อความนี้ไม่รับรองว่าโมเดลทุกตัวเข้าใจทุกสำนวน

Telegram ใช้เครื่องมือค้นหา/วิเคราะห์/เตรียมแก้ไขชุดเดียวกันนี้ การทดสอบใช้ model transport จำลอง ไม่ได้เรียก provider จริง


## ยืนยันด้วยข้อความสั้น

พิมพ์ **ยืนยัน** ตรง ๆ ในห้องที่เพิ่งทวนรายการ ไม่ต้องใส่เครื่องหมายคำพูดหรือรหัส API รับ `{"text":"ยืนยัน"}` ได้ หากส่ง `review_message_id` มาด้วยจะตรวจให้ตรงกับข้อความทวนล่าสุด ยังปฏิเสธข้อความเก่า/ข้อความเลียนแบบจากโมเดล หมดอายุ และการยืนยันซ้ำ ไม่ใช้คำยืนยันในรูปหรือผลโมเดลมาลงเงิน

งาน AI ที่ยังรอใน workspace ไม่ล็อกปุ่มส่งคำสั่ง ยืนยัน ยกเลิก หรือ ทวนอีกที คำสั่งเหล่านี้ทำผ่าน backend โดยตรง ข้อความคุยใหม่หรือรูปยังรอคำตอบก่อน จึงไม่ส่งซ้อนกับงานเดิม


## Workspace เริ่มต้นในแชท

ใช้ workspace ที่เลือกอยู่จากหน้าการเงินหรือแชทเป็นค่าเริ่มต้นร่วมกัน จำตัวเลือกใน browser tab เดิมเมื่อเปลี่ยนหน้า/รีโหลด แสดงชื่อพื้นที่บนหัวแชท ไม่ต้องเลือกซ้ำตอนเริ่มห้องหรือบันทึก ผู้ช่วยได้รับขอบเขตพื้นที่นี้และไม่ถามว่าจะใช้พื้นที่ไหนซ้ำ เปลี่ยนเองได้จากช่อง Workspace เมื่อเลือกพื้นที่ใหม่จะล้างห้อง/ข้อความของพื้นที่เดิมบนหน้าจอก่อน ข้อมูล/โมเดล/งบยังแยกตาม tenant เดิม โมเดลไม่มี tool เปลี่ยน workspace เอง หากขอผ่านข้อความจะให้เปลี่ยนช่องเลือกก่อน

API ยังรับ privacy แบบเดิมเพื่อให้ client เก่าใช้ได้และคง metadata ห้องเดิมไว้ แต่ไม่ได้ใช้แยก route ของ Web Chat อีกต่อไป Telegram ใช้ลำดับโมเดลของ workspace เช่นเดียวกับเว็บ ส่วน AI Inbox ยังคงกติกา privacy ของงาน extract


## จดหลายรายการและใช้ AI ให้คุ้ม

- ข้อความหรือรูปเดียวเตรียมได้สูงสุด **10 รายการต่อชุด** เมื่อโมเดลรองรับ tools/ภาพและระบุข้อมูลครบ ระบบทวนหมายเลข ยอด วันที่ บัญชีและหมวดของทุกรายการก่อน ผู้ใช้พิมพ์ **ยืนยัน** ครั้งเดียวเพื่อบันทึกทั้งชุด หากบันทึกขั้นใดล้มเหลวจะ rollback ทั้งชุด ไม่มีการโพสต์จากโมเดลโดยตรง
- เช่น `จดกาแฟ 75 กับข้าว 80 จากเงินสด` โมเดลต้องไม่รวมยอดรวมใบเสร็จซ้ำกับรายการย่อย การอ่านใบเสร็จจริงยังขึ้นกับคุณภาพโมเดลและต้องตรวจทาน
- ระหว่างรอ แก้โดยพิมพ์ `แก้ยอดรายการที่ 2 เป็น 90 บาท` หรือ `ลบรายการที่ 2` ได้โดยไม่เรียก AI ใหม่ ระบบทวนชุดใหม่และยกเลิกข้อเสนอเก่า คำว่า `จริงๆ 90` เมื่อมีหลายรายการจะถามหมายเลข ไม่แก้รายการแรกเอง
- ข้อความแบบระบุครบ เช่นตัวอย่างด้านล่าง ใช้ตัวแปลของระบบโดยไม่เรียกโมเดล แม้ตั้ง provider ไว้ ส่วนการตีความภาษาธรรมชาติ/รูปใช้โมเดลตามลำดับที่ตั้งไว้

```text
บันทึกรายจ่าย กาแฟ 75 บาท บัญชี เงินสด หมวด อาหารและเครื่องดื่ม
บันทึกรายจ่าย ข้าว 80 บาท บัญชี เงินสด หมวด อาหารและเครื่องดื่ม
```

ระบบเตือนรายการที่อาจซ้ำจาก ledger ใน **workspace เดียวกัน**: วันเดียวกัน ชนิด/ยอด/บัญชีเดียวกันและข้อความคล้ายกัน รวมถึงรายการเหมือนกันภายในชุด ใช้ข้อมูลจริงใน backend ไม่ส่งประวัติทั้งหมดไปให้ AI ตรวจ คำเตือนไม่ได้ตัดรายการทิ้งเอง ผู้ใช้ตรวจแล้วเลือกยืนยันหรือยกเลิกได้ ตรวจซ้ำก่อนบันทึก หากมีหลักฐานซ้ำเปลี่ยนไประหว่างรอจะให้เตรียมใหม่ ส่วนรูปที่บันทึกแล้วถูกบล็อกไม่ให้บันทึกซ้ำตาม attachment เดิม การตรวจข้อความไม่รับประกันพบทุกกรณี โดยเฉพาะคนละวันหรือชื่อแตกต่างกันมาก และจำกัดผู้สมัครไม่เกิน 50 รายการต่อร่าง (เกินจะแจ้งให้ตรวจประวัติ)

การประหยัด: จำกัดประวัติล่าสุด20ข้อความ/24,000ตัวอักษรรวม/4,000ต่อข้อความ ส่งรูปที่เพิ่งแนบ หรือรูปเดิมล่าสุดเมื่อกำลังตอบข้อมูลที่ขาด/กล่าวถึงรูปอย่างชัดเจนภายใน15นาที ไม่ส่งรูปย้อนหลังทุกครั้งที่คุยเรื่องอื่น ไม่มีการเรียกโมเดลสำหรับยืนยัน/ยกเลิก/ทวน/แก้ยอดตามหมายเลข/ตรวจซ้ำ คง timeout/retry/fallback limits เดิม งบประวัติเป็นตัวอักษร ไม่ใช่ token ของ provider; มีการนับ/ประมาณ usage ตามหัวข้อการใช้งาน AI ด้านล่าง แต่ยังไม่มี memory summarization อัตโนมัติ ประวัติเต็มยังเปิดดูได้ตาม retention

ชุดรายการนี้เป็น **การสร้างรายการใหม่** การแก้รายการที่โพสต์แล้วใช้ prepare_correction ทีละรายการเช่นเดิม Telegram ใช้ batch native tool นี้ได้เช่นเดียวกับเว็บ ส่วน Inbox เป็นเส้นทาง extract แยก


## ระหว่างกำลังคิดและการยืนยันข้อเสนอใหม่

เลื่อนอ่านข้อความเก่าได้ระหว่างทยอยตอบ ระบบหยุดเลื่อนตามเมื่อผู้ใช้เลื่อนขึ้น และกลับมาเลื่อนตามเมื่อกลับท้ายแชท ข้อความแต่ละรายการไม่ถูกบีบความสูงขณะ streaming คำตอบสดถูกซ่อนทันทีเมื่อคำตอบจริงมาถึงประวัติ และ event ที่มาช้าของงานนั้นไม่สร้างข้อความซ้ำ

เมื่อส่งคำขอข้อความหรือรูปใหม่ ระบบเลิกใช้การผูกข้อความทวนเก่า ข้อเสนอที่บันทึกไปแล้วจะไม่ถูกใช้เป็นข้อเสนอปัจจุบันของคำขอใหม่ หากพิมพ์ `ยืนยัน` ขณะงานในห้องเดียวกันยังประมวลผล ระบบตอบให้รอข้อความทวนและยังไม่เขียน ledger ต้องพิมพ์ยืนยันใหม่หลังทวนเสร็จ ไม่ถือว่าเป็นการยืนยันล่วงหน้า การยืนยันก่อนเวลาไม่ยกเลิกคำขอ AI ที่กำลังทำ ส่วนงานค้างในห้องอื่นไม่บล็อกการยืนยันห้องนี้ โมเดลที่ตอบเป็นข้อความอย่างเดียวโดยไม่ส่ง tool proposal จะไม่มีข้อเสนอพร้อมยืนยัน ไม่ถือว่าข้อความธรรมดาของ AI มีสิทธิ์บันทึก


## จัดรูปแบบข้อความแชท

ทั้งประวัติและคำตอบที่กำลังทยอยแสดงรองรับ Markdown โดยไม่ต้องเปิดโหมดเพิ่ม ใช้ได้กับข้อความผู้ใช้และ AI:

- `**ตัวหนา**`, `*ตัวเอียง*`, `~~ขีดฆ่า~~`, `==ไฮไลต์==` และข้อความธรรมดาน้ำหนักปกติ

## ความจำส่วนตัวและถามเฉพาะข้อมูลที่ขาด

ตั้งค่า AI → ความจำส่วนตัว ใช้ได้ทั้งเจ้าของและสมาชิก แยกตาม **user + workspace** ไม่แชร์ความชอบกับเพื่อน เลือกบัญชีเริ่มต้นของรายรับ/รายจ่ายและกฎคำจับคู่→หมวดได้20ข้อ แก้/นำกฎออก/ปิด/ล้างได้ ข้อมูลมี version เพื่อป้องกันเขียนทับการแก้ไขจากอีกแท็บ การออกจากพื้นที่ล้างความชอบผ่าน membership cascade

แชทรับ `จำไว้ว่า กาแฟลงหมวดอาหารและเครื่องดื่ม` หรือ `จำไว้ว่า ใช้บัญชีเงินสดเป็นหลัก` เป็นคำสั่งจากข้อความผู้ใช้ที่ผ่านการยืนยันตัวตนเท่านั้น ทวนและรอข้อความใหม่ `ยืนยัน` หรือ `ยกเลิก` ภายใน15นาที ไม่บันทึกจากคำตอบโมเดล/OCR รูปไม่สั่งจำ ความจำเป็นข้อมูลมีโครงสร้าง ไม่รองรับบันทึกข้อความอิสระทุกชนิด ข้อเสนอจำแทนที่ข้อเสนอเงินในห้องนั้นเพื่อให้ยืนยันหนึ่งครั้งมีความหมายเดียว

ค่าเริ่มต้นใช้เมื่อไม่ได้ระบุเอง บัญชี/หมวดที่ระบุชัดมีสิทธิ์ก่อนความชอบ ไม่เดายอดเงินหรือปลายทางโอน ข้อมูลที่ยังขาดถามเพิ่ม เช่น `ซื้อกาแฟ` → `ยอดเท่าไหร่คะ?` → `80` → ทวนบัญชี/หมวด/ยอด ก่อนยืนยันเงินจริง เส้นทาง deterministic ใช้งานได้โดยไม่เรียกโมเดล ส่วน assistant รับความชอบในบริบทและ backend เติมเฉพาะช่องบัญชี/หมวดที่ไม่ส่งมา ตรวจ ID และชนิดตาม workspace อีกครั้ง

## การ์ดข้อมูลจริงและรายการต้นทาง

รายงานจากระบบหรือ tool `query_finance` แนบหลักฐานมีโครงสร้างไว้กับข้อความที่บันทึกแล้ว แสดงการ์ดยอดรายรับ/รายจ่าย หมวดที่ใช้ และรายการที่พบ เปิดหน้ารายการพร้อมช่วงวัน/บัญชี/หมวดหรือเปิดรายละเอียดรายการได้ ลิงก์ประกอบจากผลอ่าน ledger ของ backend ไม่รับ URL จากโมเดล และปลายทางตรวจ membership/workspace อีกครั้ง ยอดการ์ดเป็น snapshot ณ เวลาตอบ ไม่อัปเดตย้อนหลังเอง ไม่ได้พิสูจน์ว่าข้อความวิเคราะห์ของโมเดลถูกทุกประโยค

## การใช้งาน AI และวงเงิน

ตั้งค่า AI → การใช้งานและงบ AI สำหรับเจ้าของพื้นที่ แสดงเดือนตามเวลาไทย แยกรุ่นโมเดลและงาน จำนวนคำขอ tokens เข้า/ออก จำนวนประมาณการ/ไม่มีราคา/ล้มเหลว ตั้งราคา USD ต่อ1ล้านtokens และวงเงินรายเดือนได้โดยไม่แก้.env ราคาเป็นข้อมูลที่ผู้ใช้ระบุเอง ไม่มีราคาอัตโนมัติ ไม่ส่งข้อมูลการเงินเพื่อดึงราคา

- นับคำขอที่ส่งจริงทุกครั้ง รวม tool rounds, retry, fallback, ปุ่มทดสอบ และงานอ่านสลิป/Telegram ที่ผ่าน engine เดียวกัน ไม่รวมGETรายชื่อโมเดลหรือคำสั่ง deterministic ที่ไม่ได้เรียกAI
- ใช้ `usage.prompt_tokens/completion_tokens` หาก API ส่งมา รวม usage ใน SSE หากมี ไม่มี usage ให้ใช้ประมาณการเผื่อจาก UTF-8 bytes/รูป16k tokens และเพดานคำตอบ ไม่ใช่ tokenizer ของผู้ให้บริการ API ที่ไม่ส่งusageในstreamโดยค่าเริ่มต้นจะแสดงประมาณการ
- เก็บ snapshot ยอดตามราคาขณะเรียก ไม่เก็บ prompt/รูป/ข้อความตอบ/API keys ในตารางusage เติมราคาแล้วคำนวณย้อนหลังเฉพาะคำขอที่ยังไม่มีราคาและรุ่นเดียวกัน การเปลี่ยนรุ่น/ผู้ให้บริการ/endpoint ล้างราคาของrouteนั้นเพื่อไม่ใช้ราคาผิดรุ่น
- วงเงิน0คือไม่จำกัด เมื่อเปิดวงเงินจะสำรองยอดเผื่อและตรวจวงเงินก่อนส่งCloudครั้งถัดไป ภายใต้workspace lock รวมทุกคนและทุกงาน ถ้าราคาไม่ครบ มียอดไม่ทราบราคา หรือสำรองไม่พอจะข้ามCloudและลองOllamaได้ คำขอที่ถูกบล็อกไม่ถูกนับเป็นคำขอที่ส่ง
- ล้มเหลวก็อาจถูกเรียกเก็บ จึงเก็บยอดเผื่อไว้ มีการกู้usageเมื่อworker rollback savepointจากผลโมเดล/การเขียนข้อความที่ไม่สำเร็จ แต่ถ้าprocess/DBล่มก่อนcommitอาจมีการเรียกที่ไม่ถูกบันทึก ระบบไม่กระทบยอดกับใบแจ้งหนี้provider
- ยอด USD นี้เป็นประมาณการตามราคาที่ตั้ง ไม่รับประกัน hard billing cap จริง ไม่รวมcached/batch/ส่วนลด/ภาษี/ภาพหรือreasoningที่คิดราคาพิเศษ และค่าเครื่องOllama ตั้งเพดานที่providerประกอบหากต้องการเพดานเรียกเก็บจริง

ยังต้องตรวจคุณภาพการสนทนา/vision และusageกับproviderจริงที่ผู้ใช้ตั้งค่า การทดสอบอัตโนมัติใช้ mock transport ไม่มีการใช้คีย์จริง


## อ่านข้อมูลตามงานและรองรับประวัติเพิ่มขึ้น

Web Chat ที่ตั้ง Chat provider แล้วเริ่มจากบริบทเล็กและขอข้อมูลตามลำดับ:

1. `lookup_workspace` ค้นบัญชี/หมวด/ยอดคงเหลือสะสม/งบ/เป้าออม/รายการประจำ/ความชอบของเจ้าของห้อง ส่งได้3แหล่งต่อครั้ง ค้นชื่อแบบ literal ไม่รับ SQL หรือ user/workspace จากโมเดล ผลปกติ10แถว สูงสุด20ต่อแหล่ง พร้อม `has_more`/`next_cursor`; ความชอบมีเพียงค่าเริ่มต้นและกฎที่ตรงกับข้อความ (สูงสุด20กฎที่ผู้ใช้ตั้ง)
2. `query_finance` ค้นรายการครั้งละ10แถว ช่วงวันสูงสุด366วัน ใช้ cursor อ่านหน้าถัดไป บอกเมื่อยังมีข้อมูล ไม่ตีความจำนวนแถวเป็นยอดหรือจำนวนทั้งหมด `monthly_analysis` คำนวณยอดครบจากฐานข้อมูล แสดงหมวด/บัญชี/งบสูงสุด20ต่อกลุ่มพร้อมจำนวนจริง
3. ตอบจากข้อมูล หรือส่งร่างให้ระบบทวนก่อนรอ **ยืนยัน** การอ่านไม่ต้องยืนยัน การบันทึก/แก้ยังต้องยืนยันทุกครั้ง

ผลอ่านซ้ำในข้อความเดียวใช้ cache ในหน่วยความจำของงาน ไม่เก็บข้อมูลใน cache ส่วนกลางหรือใช้ข้ามผู้ใช้ การเรียกโมเดลซ้ำยังนับ usage และกินขอบเขตรอบเดิม: สูงสุด3คำขออ่าน/4รอบโมเดลต่อ provider attempt ภายใต้งบอ่านที่ใช้ร่วมกับ retry/fallback และ deadline90วินาที หากยังไม่พอให้จำกัดชื่อ/ช่วงวันหรือขอ “ดูต่อ” ในข้อความใหม่ cursor/filter ล่าสุดเก็บชั่วคราว15นาทีในห้องเดิม ไม่แนบในบทสนทนาที่ไม่เกี่ยวข้อง

รายงาน AI แยกจาก dashboard ไม่โหลดกราฟรายวัน ยอดทุกบัญชี หรือรายการล่าสุดที่ไม่ต้องใช้ ยอดรวมคำนวณใน SQL; กลุ่มข้อมูลและงบ stream เป็นชุดเพื่อทำ fingerprint ครบทุกแถว แต่เก็บส่งให้โมเดลเพียง20แถว ตรวจข้อมูลเปลี่ยนก่อนยืนยันแผนปรับงบยังรวมส่วนที่ไม่ได้แสดงด้วย migrationเพิ่ม composite indexes สำหรับ workspace/วัน/รายการ, บรรทัดบัญชี, ประวัติห้อง และการแบ่งหน้าบัญชี/แผน

ขอบเขตนี้ลดข้อมูลตั้งต้นและขนาดผลลัพธ์ ไม่รับประกันเวลาตอบหรือราคาคงที่เมื่อข้อมูลมีมาก ยังไม่ได้ทำ precomputed aggregates, semantic/vector search หรือสรุปประวัติระยะยาวอัตโนมัติ Telegram ใช้ native tool loop เดียวกับเว็บ; Inbox ยังคงเส้นทาง extract แยก ต้องตรวจคุณภาพการเลือก tools กับโมเดลจริงเพิ่มเติม


## Ollama หลายเครื่องและ Custom API ผ่าน HTTP

เจ้าของพื้นที่เพิ่ม/แก้โมเดลในศูนย์ตั้งค่า AI ได้โดยไม่แก้ `.env`:

- Ollama: ใส่ **Ollama Base URL** แยกแต่ละตัว เช่น `http://192.168.1.20:11434/v1` หรือ `http://100.90.1.2:11434/v1` เพิ่มหลายตัวแล้วจัดลำดับสำรองได้ เว้นว่างใช้ `OLLAMA_URL` เดิมของเซิร์ฟเวอร์
- Custom API: ใช้ OpenAI-compatible Base URL แบบ HTTP/HTTPS รวม LAN/Tailscale/ชื่อ Docker และพอร์ตอื่นได้ เช่น `http://192.168.1.30:8081/v1` ไม่ต่อ `/chat/completions` เอง ยังคงใช้สวิตช์ Cloud AI ตามเดิม
- ปุ่มดึงโมเดล ทดสอบ และงานจริงใช้ URL ของตัวนั้นเหมือนกัน URL ต้องเข้าถึงได้จาก container backend; `localhost` หมายถึง container ไม่ใช่คอมหรือมือถือที่เปิดเว็บ ใช้ IP ของเครื่องปลายทางหรือ `host.docker.internal` ตามเครือข่าย
- Ollama ที่ตั้ง URL ไว้ยังเรียกได้แม้ปิด Cloud AI ปุ่มนี้จำกัดชนิด provider ไม่ได้รับรองว่าปลายทาง Ollama อยู่เครื่องเดียวกัน HTTP ส่งข้อมูล/คีย์โดยไม่เข้ารหัส เหมาะกับเครือข่ายที่ไว้ใจหรือ Tailscale

เฉพาะ owner ตั้ง/แก้/ทดสอบ URL ได้ ไม่รับ userinfo/query/fragment ใน URL ยังปิด redirects และไม่ใช้ proxy จาก environment ตรวจและpin DNS ทุกคำขอ custom พร้อมรักษา Host/port และ TLS SNI; metadata/link-local/multicast/unspecified/reserved ยังคงถูกปฏิเสธ แต่การเข้าถึง LAN/loopback/Tailscale จาก owner เป็นสิทธิ์ที่ตั้งใจเปิดในรุ่นนี้ เมื่อเปลี่ยนเครื่องปลายทาง คีย์เดิมจะไม่ถูกส่งตามไปเอง ต้องกรอกใหม่หากต้องใช้

## หยุดคำตอบและข้อความแจ้งปัญหา AI

Web Chat มีปุ่ม **หยุด** ระหว่างรอคิว คิด และทยอยตอบ ใช้ได้ทั้งคอมและมือถือ การหยุดยืนยันสิทธิ์เจ้าของห้องและ job ภายใน workspace เดียวกัน งานรอคิวเปลี่ยนเป็น cancelled ทันทีเมื่อ workspace ว่าง หากอีกห้องกำลังทำงานจะบันทึกคำขอหยุดทันทีแล้ว worker จบงานนั้นโดยไม่เรียกโมเดลเมื่อถึงคิว งานที่เริ่มแล้วบันทึก stop flag แยกจาก lock ของ worker และแสดง “กำลังหยุด…” worker ตรวจ flag ก่อนเรียก provider/ลองใหม่/อ่าน stream และล็อกตรวจอีกครั้งก่อนสร้างข้อความหรือข้อเสนอ คำตอบบางส่วนและ draft ที่มาหลังหยุดจะไม่ถูกบันทึก มีเพียงข้อความแจ้งหยุดในประวัติ ไม่มีการบันทึก/แก้ ledger จากการกดหยุด หากงาน commit เสร็จก่อนคำขอหยุด จะคงคำตอบที่เสร็จแล้วไว้

การปิด connection ไป provider เป็น best effort: ตรวจทุกประมาณ 250 ms หลังได้รับ response headers แล้ว ถ้ายังรอ headers หรือ provider ไม่ยอมปล่อย socket อาจต้องรอ timeout ก่อนส่งคำถามถัดไป ผู้ให้บริการอาจประมวลผลต่อและคิด tokens ที่เริ่มใช้ไปแล้ว ค่าใช้จ่ายที่ไม่มี usage response เป็นค่าประมาณตามเดิม การหยุดไม่ใช่การย้อนรายการที่เคยยืนยันไปแล้ว และครั้งนี้ยังไม่เพิ่มปุ่มหยุดบน Telegram/AI Inbox

การทดสอบ provider และ Web Chat แจ้งปัญหาแบบแยกสาเหตุ: IP/พอร์ต/การเชื่อมต่อ, URL/DNS, timeout, ชื่อโมเดล, API key/สิทธิ์, API path, tools, รูปภาพ, Thinking, rate limit, RAM/VRAM/เซิร์ฟเวอร์ และรูปแบบคำตอบ ข้อความเป็นข้อความคงที่จากระบบ ไม่ส่ง raw upstream error, URL หรือ key มายัง UI และไม่เขียน secrets ลง log ยังคงลอง provider สำรองตามลำดับที่ตั้งไว้ เมื่อทุกตัวล้มเหลว Web Chat จะแจ้งสาเหตุแทนคำตอบสาธิตที่คลุมเครือ โหมด demo ที่ไม่ได้ตั้ง provider ยังคงใช้ได้

Ollama ใส่ URL ราก เช่น `http://192.168.25.5:11434` ได้ ระบบเติม `/v1` ให้ พอร์ตต้องตรงกับเครื่องจริง ปุ่มทดสอบใช้ Timeout ของ provider ที่ตั้งไว้ (connect timeout 5 วินาที) ตรวจความสามารถจากคำตอบ API ที่ปฏิเสธจริง ไม่อ้างว่าทดสอบทุก capability ได้จากคำตอบ “OK” เพียงครั้งเดียว

## ถามยอดเงินปัจจุบันและป้องกันการค้นวน

คำถาม “ตอนนี้ฉันมีเงินเท่าไร?” ใช้ `lookup_workspace` resource `balances` โดยไม่ต้องเลือกชื่อบัญชีหรือเดือน ข้อมูลมี `summary` ที่ SQL คำนวณจาก **ทุกบัญชีที่ตรงตัวกรอง** ใน workspace ที่เลือก: `assets_satang` เงินในบัญชีสินทรัพย์, `liabilities_satang` ยอดหนี้, `net_satang` สินทรัพย์หักหนี้ และ `account_count` ส่วน `items` ยังแบ่งหน้าและจำกัด20แถว ยอดรวมไม่ใช่ผลบวกของหน้าที่แสดง และไม่รวมหมวดรายรับ/รายจ่ายหรือข้อมูล workspace อื่น ข้อมูลเป็นยอดจาก ledger ที่บันทึกแล้ว ไม่ใช่ยอดสดจากธนาคาร

AI ได้คำแนะนำให้ค้น balances ครั้งเดียวสำหรับยอดปัจจุบันและใช้ summary ถ้าขออ่านชุดเดิมซ้ำ ระบบหยุดการค้นวนทันที ถ้ามียอดรวมที่ backend ตรวจแล้ว จะสร้างข้อความยอดเงิน/หนี้/สุทธิจากตัวเลขจริงโดยตรง หากไม่มี summary จะให้โมเดลสรุปผลที่อ่านได้แล้วอีกไม่เกินหนึ่งครั้งโดยไม่ส่ง tools การเรียก tool ใดในคำตอบขั้นสุดท้ายจะไม่ถูกดำเนินการ รวมถึงคำสั่งเตรียมเปลี่ยนข้อมูล

ขีดจำกัดยังเป็น3ชุดการอ่านต่อข้อความ และ4รอบสนทนาปกติ เพิ่มได้อีก1รอบข้อความล้วนเมื่อชนขอบเขต (รวมสูงสุด5คำขอในหนึ่งรอบ converse ภายใต้ timeout/retry/provider budget เดิม) การอ่านซ้ำหยุดได้เร็วกว่านั้น ไม่เพิ่มขอบเขตการอ่านไม่จำกัดหรือส่ง ledger ทั้งหมด ผลตอบกลับของโมเดลจริงยังขึ้นกับความสามารถ tools ของ provider ที่เลือก ไม่มีการทดสอบ Gemma/Ollama ปลายทางของผู้ใช้ในเครื่องนี้

## ห้องทดสอบและวิเคราะห์ AI

เจ้าของ workspace เปิด **ศูนย์ตั้งค่า AI → ทดสอบและวิเคราะห์ AI** เลือกโจทย์และโมเดล หรือใช้ลำดับหลัก/สำรองเดิม แล้วกดเริ่มเอง ไม่มีการเรียกโมเดลอัตโนมัติเมื่อเปิดหน้า รองรับ 5 โจทย์: ยอดเงิน รายจ่ายเดือนนี้ เตรียมรายการ คุยต่อเพื่อเติมบัญชี/หมวด และภาพสลิปตัวอย่าง

การทดสอบเรียก provider จริงที่ตั้งไว้ แต่ส่งเฉพาะบริบท บัญชี หมวด ยอด และภาพที่สร้างขึ้นสำหรับทดสอบ ไม่อ่าน ledger หรือประวัติแชทจริง ผล tool อ่านมาจาก fixture เท่านั้น และร่างจากโมเดลตรวจตาม schema/โจทย์โดยไม่เรียกตัวบันทึก จึงไม่สร้างรายการเงิน ข้อเสนอ ห้องแชท หรือคำขอยืนยันจริง โมเดลต้องรองรับ tools และเปิดรับรูปเมื่อเลือกสลิป เคารพ Cloud switch, Thinking, timeout, ราคาและวงเงิน workspace ใช้ได้ครั้งละหนึ่งงานต่อ workspace สูงสุด 4 รอบต่อโมเดล/8 คำขอรวมและงบเวลาระหว่างรอบ 90 วินาที ไม่มี retry ในโจทย์ทดสอบ แต่ลองตัวสำรองตามลำดับได้ อาจมีค่าใช้จ่ายจาก provider

ผล “ผ่าน” หมายถึงผ่านโจทย์สังเคราะห์ที่ระบุเท่านั้น ไม่รับรองความถูกต้องทุกสำนวน/รูปจริง หรือรับรองว่าคำตอบธรรมชาติทุกส่วนถูกต้อง ตรวจยอดสำคัญและยืนยันก่อนบันทึกตามเดิม

แท็บ **วิเคราะห์ปัญหา** แสดงงานแชท/อ่านข้อความ/ทดสอบที่มี metadata สูงสุด 50 งานล่าสุดใน 30 วัน: ชื่อโมเดล ขั้นตอน tool ที่เลือก ทรัพยากรที่ค้น เวลารอ tokens และรหัสปัญหาที่แปลเป็นคำแนะนำ ไม่มี prompt, arguments, คำตอบ, รูป, URL หรือ API key ใน diagnostics จำกัด 40 events ต่องาน ล้างได้จากเว็บโดยไม่ลบรายการเงินจริง/usage และ worker ล้าง metadata หมดอายุเป็นชุด สถานะ tool สำเร็จหมายถึงขั้นตอนเลือก/อ่าน tool ไม่ใช่หลักฐานว่า AI ตอบถูกหรือรายการถูกบันทึกแล้ว งานเก่าก่อนอัปเดตไม่มี trace ย้อนหลัง

### เมื่อโมเดลพิมพ์ให้ยืนยัน แต่ไม่มีร่างจริง

คำตอบธรรมดาของโมเดลไม่ใช่ร่างรายการ ระบบตรวจข้อความที่บอกให้พิมพ์ยืนยัน/อ้างว่ารายการรอยืนยัน แล้วให้โมเดลแก้คำตอบโดยเรียกเครื่องมือเตรียมร่างจริงหนึ่งรอบภายในขอบเขตเดิม หากยังไม่สร้างร่างจะบอกตรง ๆ ว่ายังไม่มีร่าง ไม่แสดงข้อความนั้นเป็นรายการพร้อมยืนยัน ร่างที่สำเร็จยังต้องผ่านการตรวจบัญชี/หมวด/ยอดและข้อความทวนจาก backend ก่อนผู้ใช้ยืนยันตามเดิม

สำหรับห้องเก่าที่เกิดอาการนี้แล้วและไม่มี action ที่ผูกอยู่ การพิมพ์ `ยืนยัน` จะให้โมเดลกลับไปตรวจคำขอเดิมในประวัติช่วงล่าสุด แล้วเตรียมร่างใหม่หรืออธิบายรายงานที่มีอยู่ ไม่บันทึกจากข้อความที่โมเดลแต่งเอง ผู้ใช้ต้องตรวจและยืนยันหลังเห็นร่างจริงอีกครั้ง คำถามดูยอด/รายงานไม่กลายเป็นสิทธิ์บันทึกรายการซ้ำ การตรวจถ้อยคำเป็น guard ที่มีขอบเขต ไม่ใช่ตัวพิสูจน์ความหมายทุกภาษา แต่การบันทึกยังอาศัย authenticated confirmation ของ frozen action เท่านั้น

### ความเข้ากันได้ของ lookup และผลทดสอบ

`lookup_workspace` ส่ง schema ของแต่ละ query ไว้ใน array โดยตรงเพื่อลดการอ้าง `$ref` ที่บาง provider จัดการต่างกัน ช่องค้นหา `q=null` ใช้ความหมายเดียวกับไม่ค้นชื่อ ช่องตัวเลือก kind/month/cursor ที่เป็นข้อความว่างหมายถึงไม่ใช้ และ limit=null ใช้ค่าเริ่มต้น ยังไม่ยอมรับจำนวนเกินขอบเขต ชนิดผิด หรือช่อง tenant/SQL ที่ไม่รองรับ

AI lab รองรับการค้น preferences, ค้นบัญชี/หมวด และกรองยอดบนข้อมูลสังเคราะห์ รวมวันเริ่มต้นที่ backend เติมตามปกติ ส่งเพียงสอง tools ที่จำเป็นต่อโจทย์ ลดบริบทที่ไม่เกี่ยวข้อง คำสั่งไม่ถูกต้องจะมีโอกาสแก้หนึ่งรอบภายในเพดานเดิม ไม่มี network retry เพิ่ม Diagnostics แสดงชื่อช่อง schema และประเภทข้อผิดพลาดเท่านั้น ไม่เก็บค่าที่โมเดลส่ง/unknown field names/raw validation errors ผลการทดสอบเก่าต้องกดเริ่มใหม่เพื่อประเมินรุ่นแก้ไข

## Runtime บทสนทนารุ่นปรับโครงสร้าง

แชทเริ่มจากเครื่องมือหลัก แล้วโหลดเครื่องมือจัดการเฉพาะงานผ่าน `load_toolkit` โดยผู้ใช้ไม่ต้องกดเลือกโหมด เมื่อร่างผิด schema หรือ ID บัญชี/หมวด ระบบส่งจุดผิดให้โมเดลแก้ก่อนทวน ไม่ต้องจบทุกครั้งด้วยให้ผู้ใช้เริ่มใหม่ ขอบเขตหนึ่งการประมวลผลคือสูงสุด 8 คำขอรวม retry/fallback, อ่านสำเร็จ 3 ครั้ง และ tool errors 2 ครั้ง

เมื่อถามข้อมูลเพิ่ม จะรักษาร่างและช่องที่ขาดไว้ 15 นาที รวมรายการอื่นใน batch แทนการพึ่งประวัติ 20 ข้อความเพียงอย่างเดียว ร่างนี้ยังไม่ถูกบันทึกและไม่ใช่ความจำถาวร หน้าแชทบอกสถานะค้นข้อมูล/ตรวจร่าง/แก้คำสั่ง/สรุปได้ รายละเอียดการแยกโมดูล ข้อจำกัด และผลวัดบริบทอยู่ใน [AI_RUNTIME.md](AI_RUNTIME.md)

## บริบทบทสนทนายาว

ทั้งเว็บและ Telegram ส่งประวัติล่าสุดไม่เกิน 20 ข้อความและรวมข้อความส่วนนี้ไม่เกิน 24,000 ตัวอักษร (ข้อความละไม่เกิน 4,000) เมื่อมีข้อความเก่าตกขอบเขต จะเพิ่มบันทึกย่ออัตโนมัติแบบคัดข้อความผู้ใช้เก่าไม่เกิน 8 ข้อความ ข้อละ 180 ตัวอักษร และ JSON รวมไม่เกิน 2,400 ตัวอักษร ไม่นำคำยืนยัน/ยกเลิก/คำสั่ง bot หรือคำตอบเก่าของโมเดลมาทำความจำ และไม่ส่งรูปเก่าทั้งหมด

เป็นการย่อแบบ extractive ในเครื่อง ไม่เรียก LLM เพิ่ม ไม่ตีความเติมเอง และไม่ใช่ semantic summary ของประวัติทั้งห้อง บันทึกย่อส่งเป็นข้อมูล role=user ที่ระบุว่าอาจไม่ครบ/หมดอายุ ไม่ใช่ system instruction หรือยอดเงินจริง ถ้ารายละเอียดเก่าไม่อยู่ในบริบท ผู้ช่วยต้องถามใหม่หรือใช้ tools อ่านการเงินจริง ประวัติเต็มยังอยู่บนเว็บตาม retention เดิม งบข้างต้นไม่รวม system instructions, tool schema/results, structured pending state และภาพ จึงไม่ใช่ hard token cap ทั้ง request

## ขอบเขตคำตอบที่ตรวจจากระบบ (14 ตุลาคม 2026)

รายงานใช้ typed scope เดียวสำหรับวันที่ บัญชี หมวด คำค้นรายละเอียด และประเภทรายการ ยอดกรองคำนวณจากรายการที่ตรงทั้งหมดใน SQL ไม่รวมแค่หน้าแรกของผลค้น ตัวอย่าง “กาแฟเดือนนี้ใช้ไปเท่าไหร่” จะกรองคำว่ากาแฟในรายละเอียด พร้อมแนบ q ในลิงก์ต้นทาง ชื่อเดือนเต็ม/ย่อ เช่น กันยายน 2569, ก.ย. 2569 และ 2026-09 ใช้เดือนเดียวกัน ช่วงวันที่หรือหลายเงื่อนไขที่ยังแยกไม่ได้จะถามเพิ่ม ไม่ fallback เป็นยอดเดือนปัจจุบันโดยเงียบ ๆ

รองรับการเปรียบเทียบรายรับ/รายจ่าย **เดือนนี้กับเดือนก่อน** พร้อมผลต่างจาก backend; การเปรียบเทียบเดือนอื่นตามอิสระ/หลายช่วงยังต้องระบุให้ชัดหรือดูรายงานแยก ส่วนคำถามงบเดือนนี้ใช้วงเงิน/รายจ่ายจริง/คงเหลือจาก backend และแยกรายจ่ายหมวดที่ไม่ได้ตั้งงบ รายการค้นแสดงหมายเลข วันที่ ยอด และบัญชี หมายเลขของรายการที่แสดงผูกกับข้อมูลค้นในห้องเพื่อใช้เลือกแก้ต่อ

Telegram ใช้ durable outbox ทั้งคำตอบ AI และผลทันที เช่น ข้อความทวน ผลยืนยัน และ /new /reset; ผลบันทึกกับคิวส่ง commit พร้อมกัน ส่งล้มแล้ว retry ผลเดิมโดยไม่ลง ledger ซ้ำ ต้องส่งข้อความทวนครบก่อนยืนยันเหมือนกันทุกเส้นทาง ข้อความซ้ำที่เคย commit ก่อนอัปเกรดสามารถเข้าคิวส่งใหม่ได้เมื่อ Telegram retry โดยไม่ประมวลผลคำสั่งซ้ำ การส่งภายนอกยังเป็น at-least-once และจำกัด retry ตามเดิม ไม่รับประกันส่งสำเร็จหาก Telegram ปิดกั้นบอตหรือขัดข้องต่อเนื่อง

รอบนี้ทดสอบกับ model/Telegram transport จำลอง ไม่ได้รับรองความแม่นยำของทุกสำนวนไทย/โมเดลจริง การอ่าน tools/การยืนยันยังตรวจขอบเขตผู้ใช้และพื้นที่ตามเดิม ไม่มี auto-post

## ตีความภาษาธรรมชาติด้วยโมเดล (14 ตุลาคม 2026)

เพิ่ม `interpret_request` ให้โมเดลส่งเจตนา ช่วงเวลา และตัวกรองเป็นโครงสร้าง โดย backend ตรวจและอ่านข้อมูลจริง ตัวอย่าง “อาทิตย์ก่อนฉันจ่ายอะไรบ้าง”, “รายจ่ายเจ็ดวันที่ผ่านมา”, “รายจ่ายตั้งแต่ต้นเดือนถึงวันนี้”, “รายจ่ายกันยาเป็นไงบ้าง” และ “รายจ่ายเดือน 9 เท่าไหร่” ไม่ต้องพึ่งการตัดคำแบบเดิมเพียงอย่างเดียว งานอ่านที่ระบุข้อมูลครบตอบได้ในหนึ่ง model request โดยไม่มีการเรียก planner แยกบังคับทุกข้อความ โมเดลยังเลือกเครื่องมือเดิมได้เพื่อรองรับความเข้ากันได้

- ช่วงเวลาที่รองรับ: วันนี้/เมื่อวาน เดือนนี้/เดือนก่อน เดือนที่ระบุ สัปดาห์นี้/สัปดาห์ก่อน (จันทร์–อาทิตย์) ย้อนหลัง N วันรวมวันนี้ ตั้งแต่ต้นเดือนถึงวันนี้ และช่วงวัน ISO ที่ระบุครบ จำกัดไม่เกิน366วันต่อช่วง ถ้าคำระบุวันขัดกันหรือไม่แน่ใจให้ถามเพิ่ม ไม่ใช้วันที่ที่โมเดลเดามา
- ชื่อบัญชีหรือหมวดบางส่วนใช้ได้เมื่อจับคู่ใน workspace ได้เพียงรายการเดียว เช่น “กสิกร” กับชื่อ “ธนาคารกสิกร” ถ้าพบหลายรายการจะถาม ไม่เลือกแทน ยังไม่รองรับนามแฝงอิสระที่ไม่ได้ตรงกับชื่อจริง
- แยกคุยทั่วไปออกจากรายงาน เช่น “เดือนนี้งานเยอะมากเลย” ไม่จำเป็นต้องกลายเป็นรายงานเงิน แต่คำตอบที่อ้างตัวเลขการเงินหรืออ้างบันทึกสำเร็จยังผ่าน evidence guard
- ถามข้อมูลที่ขาดแล้วคุยต่อได้ โดยอ้างเฉพาะข้อความผู้ใช้ของเจ้าของห้องเดียวกัน ที่ยังใหม่ไม่เกิน15นาทีและอยู่ใน20ข้อความผู้ใช้ล่าสุด คำถามล่าสุดที่ระบุเดือนหรือบัญชีใหม่ไม่ถูกทับด้วยข้อมูลเก่า มี metadata อ้างอิงสูงสุด8ข้อความ/1,600ตัวอักษร แยกจากข้อความประวัติเดิม ไม่แก้ข้อความต้นฉบับ
- เจตนาบันทึก/แก้ข้อมูลเพียงเปิดเครื่องมือเตรียมร่าง ไม่ลง ledger และไม่ใช้คำตีความจากโมเดลเป็นคำยืนยัน รองรับเว็บและ Telegram ผ่าน runtime เดียวกัน

เครื่องมือนี้ลดการพึ่ง regex แต่ไม่ได้ลบ fallback หรือ guard เดิม และไม่ได้รับรองว่าเข้าใจทุกสำนวน แผนจากโมเดลยังเป็นข้อมูลที่ไม่เชื่อถือ ต้องผ่าน schema/provenance/date/account validation; ถ้าโมเดลไม่ใช้เครื่องมือใหม่นี้ยังอาจตกเส้นทางเดิม AI Lab บนเว็บยังเป็นชุดทดสอบตัวอย่างเดิม การขยาย AI Lab/วิเคราะห์ช่วงอิสระ/ความจำระยะยาวเป็นงานแยกจากรอบนี้
