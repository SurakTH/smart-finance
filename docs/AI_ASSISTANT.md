# ผู้ช่วย AI บนเว็บ

## ตั้งค่า

เจ้าของ workspace เปิด **ตั้งค่า → ศูนย์ตั้งค่า AI** (`/ai-settings`) เพิ่มโมเดลงาน **Chat** ระบุ provider/ชื่อโมเดล/API key หรือเลือก Ollama ที่ผู้ดูแลติดตั้งแล้ว จัดลำดับหลักและสำรองได้ คีย์เข้ารหัสที่ backend และไม่ส่งกลับ browser ไม่ต้องใส่คีย์ใน `.env`

- เปิด **รับรูปภาพในแชท** เฉพาะโมเดลที่รองรับภาพจริง การเรียก Chat ใช้ OpenAI-compatible Chat Completions พร้อม function tools; รุ่นที่รับแต่ข้อความหรือไม่รับ tools อาจใช้ไม่ได้
- เลือก **Thinking** ของแต่ละโมเดล ค่าเริ่มต้นไม่ส่ง effort เพิ่ม ระดับอื่นขึ้นกับ provider/รุ่น ไม่ใช่ทุกโมเดลรองรับทุกค่า ระบบปฏิเสธบางชุดที่ทราบว่าใช้ไม่ได้ แต่ไม่สามารถยืนยันความสามารถจากชื่อโมเดลเพียงอย่างเดียว
- เพิ่ม timeout และจำนวน output tokens สำหรับ thinking มาก (บางบริการนับ reasoning ในงบเดียวกับคำตอบ) เมื่อเลือก effort ระบบไม่ส่ง temperature และใช้ sampling default ของโมเดล Timeout ต่อ request สูงสุด 60 วินาทีและมีงบ soft deadline รวม 90 วินาที ไม่รองรับงานคิดยาวหลายสิบนาที
- ปุ่มทดสอบใช้ข้อความสังเคราะห์ และภาพขาวสังเคราะห์เมื่อเปิดรับรูป ไม่ส่งบัญชีหรือประวัติการเงิน เป็นเพียงการตรวจเรียก API ได้ ไม่รับรองคุณภาพ OCR หรือความถูกต้องของ function arguments
- **Private** ใช้ Ollama เท่านั้นหรือ demo; **Standard** ใช้ Cloud ได้เมื่อ workspace อนุญาต Cloud แล้ว ทั้งรูปและประวัติที่ส่งให้ Cloud อยู่ภายใต้นโยบายของบริการนั้น

## สนทนาและจดเงิน

โมเดล Chat รับข้อความทั่วไปได้ ไม่จำเป็นต้องเริ่มจากคำสั่งการเงิน เช่น “วันนี้เหนื่อย ช่วยวางแผนพรุ่งนี้หน่อย” จากนั้นคุยเรื่องเงินต่อได้ ตัวอย่าง:

```text
คุณ: [แนบรูป] ช่วยจดค่าอาหารในรูปนี้หน่อย
ผู้ช่วย: จ่ายจากบัญชีไหนคะ?
คุณ: เงินสดจ้า
ผู้ช่วย: [ทวนยอด วันที่ บัญชี หมวด และรูปหลักฐาน]
คุณ: ยืนยัน
ผู้ช่วย: [ผลการบันทึกจากระบบ]
```

โมเดลใช้ `prepare_transaction` เสนอรายการเงิน หรือ `prepare_management_plan` เสนอแผนจัดการ 1–10 ขั้นตอนต่อครั้ง ทั้งสองไม่มีสิทธิ์ยืนยัน ต้องพิมพ์ “ยืนยัน” จากห้องและข้อความทวนล่าสุดภายใน 15 นาที เมื่อข้อมูลเปลี่ยนให้สั่งใหม่ หากโมเดลอ่านรูปหรือเข้าใจผิด ผู้ใช้ต้องแก้/ยกเลิกก่อนยืนยัน

## สั่งงานแบบเลขาเป็นชุด

ใช้ Chat model ที่รองรับ function tools แล้วบอกความต้องการ เช่น:

- “สร้างหมวดสัตว์เลี้ยง ตั้งงบเดือนนี้ 2,000 บาท แล้วสร้างเป้าเงินฉุกเฉิน 50,000 บาท”
- “เปลี่ยนชื่อเงินสดเป็นกระเป๋าสตางค์ แล้วคัดลอกงบเดือนก่อนมาเดือนนี้”
- “เปลี่ยนเป้าเที่ยวญี่ปุ่นเป็น 80,000 บาท สิ้นปีนี้ ส่วนรายการค่าเน็ตพักไว้ก่อน”
- “ตั้งค่าอาหารแมว 600 บาททุกเดือนจากเงินสด หมวดสัตว์เลี้ยง เริ่มวันนี้”

ก่อนยืนยันยังแก้บางส่วนต่อได้ เช่น “งบสัตว์เลี้ยงเอาเป็น 3,000 ที่เหลือเหมือนเดิม” ระบบส่งแผนเดิมที่ยังไม่ยืนยันเป็นบริบทให้โมเดลเตรียมทั้งชุดใหม่ ต้องตรวจและยืนยันข้อความทวนใหม่ ไม่ใช้ข้อความทวนเก่า

ถ้าชื่อ/ข้อมูลกำกวมผู้ช่วยควรถามก่อน และเมื่อได้ข้อมูลครบ backend ทวนทั้งชุดให้ตรวจพร้อมรายละเอียด **ก่อน → หลัง** ผู้ใช้พิมพ์ยืนยันครั้งเดียว ทำทั้งชุดใน transaction เดียว หากล้มเหลวย้อนกลับทั้งหมด ยืนยันซ้ำไม่ทำซ้ำ ระบบตรวจบัญชี/งบ/เวอร์ชันเป้าหมายและรายการประจำจาก snapshot ก่อนเขียน หากมีการเปลี่ยนระหว่างรอจะไม่ใช้แผนเก่า ให้สั่งใหม่เพื่อเตรียมข้อมูลล่าสุด

| งาน | ทำผ่านแชทได้ |
|---|---|
| บัญชี/หมวด | สร้างบัญชีเงิน/บัตรหรือหมวดรายรับ/รายจ่าย เปลี่ยนชื่อ; สร้างแล้วอ้างในงบ/รายการประจำในชุดเดียวกันได้ |
| งบเดือน | ตั้ง/แก้ยอด นำงบออก คัดลอกจากเดือนก่อนโดยไม่ทับงบเดิมในเดือนปลายทาง |
| เป้าออม | สร้าง แก้ชื่อ/ยอดเป้า/วันครบกำหนด เก็บหรือเปิดอีกครั้ง |
| รายการประจำ | สร้างรายรับ/รายจ่ายรายวัน/สัปดาห์/เดือน พักหรือเปิดอีกครั้ง |

บัญชีใหม่ยอด **0** ไม่เดายอดตั้งต้น เปลี่ยนชื่อจะเปลี่ยนชื่อที่แสดงในประวัติเดิมด้วยแต่ไม่แก้ ledger งบและเป้าเป็นแผน ไม่โอนเงินหรือจัดสรรเงินออมให้เอง รายการประจำสร้างข้อเสนอเข้า Inbox ที่ผู้ใช้ต้องยืนยันในแต่ละรอบ การพักไม่ลบข้อเสนอที่สร้างแล้ว เปิดใหม่อาจมีรอบค้าง

ดู **เมนูแชท → ประวัติงานผู้ช่วย** เพื่อดูแผนที่ทำสำเร็จ แบ่งหน้าครั้งละ 10 รายการ แสดงผู้ยืนยัน เวลา และรายละเอียด สมาชิกพื้นที่อ่านร่วมกันได้ ประวัติ append-only ใน PostgreSQL ยังอยู่หลังลบแชท/หมดอายุห้อง (ร่างที่ยังไม่ยืนยันจะถูกลบตามห้อง) เก็บ metadata แผนและ snapshots ในฐานข้อมูล จึงต้องจัดอายุ backup ให้เหมาะสม ไม่ส่ง payload ประวัติทั้งหมดให้ browser

ใช้สิทธิ์สมาชิกพื้นที่เช่นเดียวกับหน้าจัดการเดิม ไม่เพิ่มสิทธิ์ผ่านโมเดล รหัส/คีย์/สมาชิก/workspace ยังคงจัดการจากหน้าที่เกี่ยวข้อง ไม่มี tools ลบบัญชี หมวด หรือ ledger เปลี่ยนชนิดบัญชี หรือแก้ข้อมูลภายในตามใจ ชื่อซ้ำชนิดเดียวกันต้องเลือกชื่อใหม่ ส่วนงาน transaction กับ management เป็นข้อความทวนคนละประเภท ไม่รวมลงเงินกับเปลี่ยนโครงสร้างในคำยืนยันเดียว

ตอบทั่วไปทยอยแสดงได้ ส่วน tool arguments และฟิลด์ reasoning ไม่ส่งเป็นคำตอบ บริบทแผนจำกัดงบ 60 รายการล่าสุด เป้าออม 50 และรายการประจำ 50 รายการ ไม่ใช่ความจำทุกข้อมูล ประวัติที่ส่งให้โมเดลจำกัด 20 ข้อความล่าสุดและ 3 รูปล่าสุด ไม่ใช่ความจำถาวรทั้งประวัติ รายงานที่รองรับใช้ตัวเลขจาก backend และยอดสะสมบัญชีจริง โมเดลไม่มี SQL tool หรือสิทธิ์อ่าน workspace อื่น การเรียบเรียงหรือคำตอบทั่วไปยังอาจผิดได้

รูปใหม่ไม่สร้าง pending Inbox แยกออกจากแชท ถ้าไม่มี vision provider ที่ใช้ได้ จะบอกว่ายังอ่านรูปไม่ได้ ไม่เดายอดและไม่สร้างร่างจากรูปใน demo mode ก่อนยืนยัน รูป/ร่างเป็นของเจ้าของห้อง หลังยืนยันจะเก็บรูปเป็นหลักฐานการเงินผ่าน confirmed Proposal และสมาชิกพื้นที่เห็นได้ หลักฐานยังอยู่หลังลบแชท รูปที่ยืนยันแล้วไม่บันทึกซ้ำผ่าน Chat/Inbox รูปหนึ่งที่มีร่างอีกห้องต้องจัดการร่างเดิมก่อน

## ข้อจำกัดและความเข้ากันได้

การแก้ยอดร่างใช้ “จริง ๆ 90 บาท” ได้ การแก้รายการที่บันทึกแล้วใช้ “แก้รายการล่าสุดเป็น 95 บาท” หรือคำขอที่คัดลอกจากหน้ารายการ งานจัดการรองรับเฉพาะตารางข้างต้น ยังไม่รองรับจัดสรรเงินเข้าเป้าออมผ่านโมเดล แก้รายละเอียดรายการประจำที่มีอยู่ ลบ ledger สมาชิก รหัสผ่าน หรือ API keys แบบอิสระ Telegram ยังใช้กฎภาษาไทยและภาพเข้า Inbox ไม่ได้เปลี่ยนเป็น native AI conversation ในรอบนี้ ถ้าไม่มีโมเดลหรือ fallback เป็น demo การคุยทั่วไปไม่ใช่ LLM

| Provider | การส่ง Thinking |
|---|---|
| OpenAI / Compatible / Ollama / Gemini | `reasoning_effort` เมื่อเลือกค่าที่ไม่ใช่ default |
| OpenRouter | `reasoning.effort` และ `reasoning.exclude=true` |
| Groq | `reasoning_effort` และซ่อน reasoning ตามรุ่น |

OpenAI/Groq ใช้ `max_completion_tokens`; provider อื่นใช้ `max_tokens` ไม่ retry ด้วยการลบ effort ที่ผู้ใช้เลือก เมื่อ request ใช้ไม่ได้จะ retry/fallback ตาม route ที่ตั้ง แต่ upstream บางตัว เช่น Ollama บางรุ่น อาจใช้ค่าเริ่มต้นเมื่อไม่รู้จักระดับ จึงไม่อ้างว่าค่า thinking บังคับได้เหมือนกันทุกบริการ

เอกสารอ้างอิงหลัก: [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create), [Gemini OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai), [OpenRouter reasoning](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens), [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility), [Groq reasoning](https://console.groq.com/docs/reasoning)

ผลทดสอบรอบนี้ใช้ PostgreSQL จริงใน Docker และ HTTP transport จำลอง ยังไม่ได้เรียกด้วย API key จริงหรือทดสอบคุณภาพโมเดล vision/Ollama จริง ดูผลที่ [VERIFICATION.md](VERIFICATION.md)
