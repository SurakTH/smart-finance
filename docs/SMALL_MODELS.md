# โมเดลเล็กและการอ่านสลิป

การทดสอบนี้ใช้แอปในเครื่องและ Ollama โดยไม่มีโมเดลสำรองหรือโหมดสาธิตช่วยตอบ ไม่ใช่ผลทดสอบผ่าน AI Lab อย่างเดียว ผลหนึ่งชุดไม่ใช่การรับประกันความแม่นยำกับทุกภาพ

## ขั้นตอนอ่านรูป

1. **อ่านเอกสาร**: ส่งภาพกับคำอธิบายให้ vision model ด้วยคำขอสั้น ๆ ไม่มีประวัติแชท บัญชี หรือ tools ในรอบนี้ แยกยอดจ่ายจริง ราคาก่อนลด ส่วนลด/สิทธิช่วยจ่าย ค่าธรรมเนียม และวันที่ ใช้ JSON schema กับ Ollama
2. **ตรวจข้อมูล**: backend แปลงบาทเป็นสตางค์ด้วยเลขทศนิยม ตรวจความสอดคล้องของยอด แปลงปี พ.ศ. และวันที่ที่พิมพ์ในภาพ ช่องที่อ่านไม่ได้จะไม่ถูกแทนด้วยตัวเลขที่เดา หากมีหลักฐานว่าเป็นเอกสารการเงินแต่ยอดไม่ชัด จะอ่านซ้ำได้อีกหนึ่งครั้งภายในเวลาและจำนวนรอบที่กำหนด
3. **เตรียมร่าง**: Inbox ใช้ยอดจ่ายจริงและวันที่จากเอกสาร ส่วนแชทได้รับข้อมูลที่อ่านแล้วแทนภาพ ให้ AI เลือกบัญชี หมวด และงานที่ต้องทำ หาก Ollama ตอบเป็นตัวเลขลอย ๆ หรืออ้างว่ามีร่างแต่ไม่เรียก tool จะมีการตัดสินใจแบบ JSON schema อีกได้หนึ่งครั้งเพื่อให้โมเดลเลือกว่าจะเตรียมร่าง อธิบายรูป หรือกลับไปใช้ tools อื่น โดยไม่ส่งภาพซ้ำ ยอด/วันที่ของร่างจากรูปใหม่ผูกกับผลอ่านของ backend เพื่อป้องกันการแปลงหน่วยซ้ำผิด เช่น 18 บาทกลายเป็น 180 บาท
4. **ตรวจและยืนยัน**: ไม่มีการลงบัญชีอัตโนมัติ ผู้ใช้ยังแก้ยอดในบทสนทนาถัดไปได้ ตอนอ่านรูปใหม่ ร่างหลายรายการจากสลิปเดียวต้องรวมตรงยอดจ่ายจริง ไม่ลงยอดเต็มซ้ำทุกรายการ

ไม่มีเงื่อนไขเลือกธนาคาร ตำแหน่งช่องเงิน หรือเลขอ้างอิงเฉพาะแบบ วันที่ใช้ตัวแปลงปฏิทินทั่วไป ยอดก่อนลดและเงินช่วยจ่ายไม่ถูกสร้างเป็นรายรับ/รายจ่ายอีกชุดหนึ่งเอง ค่าธรรมเนียมที่พบจะแจ้งให้ตรวจ ไม่บวกเพิ่มโดยเดา

ผลอ่านในห้องแชทเก็บเฉพาะห้องนั้นและอ้างถึง attachment ของห้องเดิม คุยต่อใช้ข้อมูลเดิมและส่งภาพต้นฉบับอีกครั้งเฉพาะเมื่อจำเป็น การถามยอดจากภาพมีเครื่องมือแยกจากรายงาน ledger จึงไม่ใช้ยอดในบัญชีมาแทนยอดที่เห็นในสลิป

Inbox แสดงส่วนลด/สิทธิและคำเตือนพร้อมรูป และใช้วันที่จากสลิปในหน้าตรวจรายการ หากอ่านวันที่ไม่ได้ ผู้ใช้ต้องระบุวันที่เอง ไม่ตั้งเป็นวันนี้โดยเงียบ ๆ ผลอ่านถูกเก็บใน `proposals.receipt` ด้วย migration `receipt_readings` ซึ่งเพิ่ม JSON column แบบ nullable และไม่แก้รายการบัญชีเดิม

## ข้อจำกัด

- นี่คือการอ่านข้อมูล ไม่ใช่ตรวจว่าสลิปแท้หรือเงินเข้าธนาคารจริง
- ตัวอักษรไทย ชื่อร้าน ภาพเบลอ ภาพตัดยอด และเอกสารที่มีหลายยอดยังอาจอ่านผิด ต้องตรวจรูปก่อนยืนยัน
- ภาพที่ไม่ใช่เงินบาทจะไม่แปลงสกุลเงินเอง ยอดที่ไม่ชัด/ขัดกันจะให้ผู้ใช้ตรวจ
- สำหรับรูปใหม่ ระบบใช้ยอดจ่ายจริงทั้งสลิปก่อน หากต้องแบ่งค่าใช้จ่ายเฉพาะส่วน ให้ตรวจและแก้ร่างอย่างชัดเจนก่อนยืนยัน
- งานคิดยาวของโมเดลเล็กอาจชน output budget หรือ timeout ได้ การเปิด Thinking ไม่ได้ทำให้ทุกงานดีขึ้น การอ่านสลิปทั่วไปควรเริ่มทดสอบแบบปิด Thinking แล้ววัดผลจริงกับโมเดลและเครื่องที่ใช้
- ค่าการตั้งค่าของผู้ใช้และลำดับผู้ให้บริการยังมีผล ไม่ได้เปลี่ยนทุกโมเดลให้ปิด Thinking โดยอัตโนมัติ

## ทดสอบซ้ำในเครื่อง

แอปและ worker ต้องรันแล้ว ใช้ Python dependencies ของ backend และ Pillow สคริปต์สร้างบัญชีทดสอบกับ workspace ใหม่ในแอป **localhost เท่านั้น** การสร้างบัญชีทดสอบใช้ Docker ภายในเครื่อง เก็บรหัสบัญชีทดสอบในไฟล์ชั่วคราวสิทธิ์ `0600` ไม่ต้องใส่ API key ในคำสั่ง

```bash
python scripts/evaluate_small_model.py \
  --ollama-url http://YOUR-OLLAMA-HOST:11434 \
  --model qwen3.5:9b --thinking none \
  --output /tmp/small-model-evaluation.json
```

คำสั่งข้างบนทดสอบสนทนา ยอดเงิน ช่วงวัน คำถามต่อเนื่อง ร่าง แก้ยอด ยืนยันซ้ำ และภาพจำลอง มี assertion สำหรับผลลัพธ์ จำนวนรายการ token และเวลา การทดสอบโมเดลจริงเป็น opt-in; CI ใช้ regression tests ที่ไม่ต้องต่อเครื่อง Ollama

ทดสอบภาพส่วนตัวเฉพาะชุด โดยระบุยอด **บาท** และวันที่ **ค.ศ.** ที่คาดหวัง:

```bash
python scripts/evaluate_small_model.py \
  --ollama-url http://YOUR-OLLAMA-HOST:11434 \
  --model qwen3.5:9b --thinking none \
  --receipt /path/to/receipt.jpg 125.50 2026-10-20 \
  --receipt /path/to/another-receipt.png 79.50 2026-10-19 \
  --output /tmp/receipt-evaluation.json
```

ชุดรูปทดสอบทั้ง Chat และ Inbox โดยไม่ยืนยันรายการ ภาพและข้อความตอบส่วนตัวไม่ถูกบันทึกลงรายงาน สคริปต์ไม่ส่งภาพขึ้น Git หรือบริการ cloud และไม่ push โค้ด หาก Docker ใช้ context/socket เฉพาะเครื่อง ให้ตั้ง `DOCKER_HOST` ตามการติดตั้งของคุณก่อนรัน

อย่าส่งรูปส่วนตัวเข้า repository ใช้ภาพจำลองสำหรับ CI และตรวจ `checks` ในรายงาน ไม่ดูเพียงว่า job ขึ้น `done`

### ตอบบัญชีและหมวดระหว่างกรอกร่าง

เมื่อร่างขาดบัญชี/หมวด ระบบแสดงชื่อที่ใช้ได้จริงใน workspace และประเภทรายการนั้น (แสดงก่อนสูงสุด 6 ชื่อ ถ้ามีมากกว่านี้จะบอกจำนวนและขอดูเพิ่มได้) บัญชีปลายทางไม่รวมต้นทาง การตอบชื่อที่ตรงเพียงรายการเดียวเติมเฉพาะช่องที่กำลังถามในร่างเดิมได้ทันที ไม่เรียกโมเดลหรือส่งภาพซ้ำ เก็บยอด วันที่ และหลักฐานเดิมไว้ รวมถึงร่างหลายรายการ

คำตอบยาวหรือกำกวมยังให้โมเดลตีความตามบริบท ไม่เลือกจากคำที่แทรกอยู่ในประโยค เช่น “ไม่เอาเงินสด” ชื่อซ้ำ ร่างหมดอายุ/ยกเลิก และข้อมูลคนละห้องหรือ workspace ไม่ใช้ทางลัดนี้ การเลือกบัญชี/หมวดเพียงอย่างเดียวยังไม่บันทึกรายการ ต้องตรวจร่างและยืนยันเหมือนเดิม

สำหรับสลิปใหม่ที่โมเดลตอบเป็นข้อความโดยไม่ใช้เครื่องมือ จะตรวจเจตนาผ่านผลลัพธ์แบบโครงสร้างได้อีกหนึ่งครั้ง (ใช้ข้อเท็จจริงที่อ่านแล้ว ไม่ส่งรูปซ้ำ) เพื่อให้คำขอจดที่ขาดบัญชี/หมวดมีร่างจริงก่อนถาม ไม่ถือว่าข้อความอ้างว่ารอข้อมูลเป็นร่างที่ยืนยันได้เอง

### เสนอหมวดจากความหมายก่อนถาม

AI ใช้รายละเอียดที่พิมพ์หรือ caption ของสลิปเพื่อเลือกหมวดที่เหมาะจากหมวดที่มีจริง แม้ผู้ใช้ไม่ได้ระบุชื่อหมวด เช่น ค่ากาแฟ/อาหารเข้าหมวดอาหารและเครื่องดื่มถ้ามี เมื่อยังขาดบัญชี จะเก็บหมวดที่เลือกไว้ในร่างแล้วถามเฉพาะบัญชี ไม่ส่งรูปหรือเรียกโมเดลใหม่เพื่อเลือกหมวดซ้ำ ชื่อหมวดต้องผ่านการตรวจ workspace และชนิดรายรับ/รายจ่ายตามเดิม

หากรายละเอียดกำกวม ไม่มีหมวดที่เหมาะ หรือผู้ใช้ขอเลือกเอง จะถามพร้อมตัวเลือก หมวดที่ผู้ใช้ระบุและความชอบส่วนตัวมีลำดับก่อนข้อเสนอของ AI ข้อเสนอปรากฏในร่างให้ตรวจและเปลี่ยนได้ก่อนยืนยัน ไม่มีการสร้างหมวดใหม่หรือบันทึกรายการอัตโนมัติ

### ซ่อมรูปแบบการเรียกเครื่องมือของ Ollama

เมื่อ Ollama ปฏิเสธ native tool request ด้วย HTTP 500 ก่อนมีผลอ่านที่ใช้ตอบได้ ระบบลอง JSON schema กับ **provider/model เดิม** ได้หนึ่งทางสำรอง ใช้เครื่องมือชุดเดิมและการตรวจ workspace/argument เดิม ไม่เพิ่มสิทธิ์โมเดลและไม่สลับไป cloud หากอ่านข้อมูลเงินจริงได้แล้ว จะใช้ข้อมูลนั้นตอบแทนการเรียกโมเดลซ้ำเมื่อการสรุปล้มเหลว

คำตอบที่อ้างยอดโดยไม่อ่านข้อมูลหรือแต่งข้อความทวนเองต้องเรียกเครื่องมือให้สำเร็จก่อนส่ง ผู้ให้บริการที่ละเลยรูปแบบ JSON ยังถูกตรวจคำตอบและร่างจริงตามเดิม ผลเครื่องมือคงสถานะข้อมูล untrusted และไม่ยกระดับเป็นคำสั่งระบบ จำนวน request/deadline/งบต่อ turn ยังบังคับร่วมกัน

ถ้าโมเดลเลือกเตรียมร่างแต่ลืมยอด ทั้งที่ข้อความมีตัวเลขพร้อมหน่วยเงิน ระบบให้โมเดลทวน argument ได้อีกครั้ง ไม่ดึงยอดจาก regex ไปเติมเอง กรณีอ้างชื่อหมวดที่ไม่มี จะให้ส่งร่างส่วนที่รู้จริงกลับมาเพื่อเก็บบริบทก่อนถาม ไม่ปล่อยให้ถามเป็นข้อความอย่างเดียวแล้วลืมร่าง

การซ่อมคำสั่งใน turn เดียวกันรักษาเฉพาะช่องที่ผ่าน schema และการตรวจ reference แล้ว ไม่ทิ้งยอด/รายละเอียดเมื่อโมเดลส่งกลับมาแก้แค่หมวด ข้อมูลนี้ไม่ใช้ข้ามคำขอหรือข้ามห้อง ส่วนห้องที่ไม่มีรูปจะไม่แสดงช่อง attachment_id ใน schema ของเครื่องมือเตรียมรายการ เพื่อลดการแต่งรหัสรูปขึ้นมา การตรวจสิทธิ์แหล่งภาพจริงยังบังคับที่ backend ตามเดิม

**โหมดปิด Thinking ยังมีความไม่นิ่ง** ในการเลือกหมวด/ตามร่างและแยกรายการหลายชิ้น จึงไม่ถือว่าผ่านครบ แม้ backend จะปฏิเสธคำสั่งผิดและไม่บันทึกอัตโนมัติ สำหรับโมเดล 9B ตัวที่ทดสอบนี้ ผลชุดนี้สนับสนุนให้เปิด Thinking เมื่อต้องการใช้เป็นผู้ช่วยหลายขั้นตอน โดยแลกเวลาตอบเพิ่ม ค่าที่เทียบเป็น profile ใน workspace ทดสอบเท่านั้น ไม่ได้เปลี่ยน profile ใช้งานจริง

Thinking เพิ่ม output/reasoning และลดบางรอบซ่อม argument; รายงาน default มี 1 request ที่ usage เป็นค่าประมาณ จึงไม่ใช้ผลรวม token ทั้งชุดเป็นจำนวนจริงที่แน่นอน ผลหนึ่งชุดนี้ไม่ใช่การรับรองทุกประโยค/ทุกภาพ ต้องตรวจร่างก่อนยืนยันตาม flow ปกติ

ชุดตรวจครอบคลุมยอดเงิน ช่วงวันที่และคำถามต่อ อันดับบัญชี การเสนอหมวด ข้อมูลที่ขาด รายการหลายชิ้น รูป/วันที่/ยอดที่คงอยู่หลังแก้หมวด การเลือกหมวดเอง การยืนยัน/ยืนยันซ้ำ และการไม่โพสต์ระหว่างถามตอบ กรณีไม่มีหมวดเหมาะและถามเพิ่ม จะตอบช่องที่ขาดจริงก่อนตรวจว่ากลับมาทวนร่างได้ครบ ไม่บังคับให้โมเดลจัดหมวดผิดเพื่อให้เทสผ่าน

ตัวแก้สำคัญเพิ่มจากรอบก่อน: ซ่อม protocol โดยใช้ provider เดิม, คงช่องที่ตรวจผ่านระหว่างซ่อมคำสั่งใน turn เดียวกัน, ตรวจการอ้างร่างที่ไม่มีอยู่ก่อน resolve, และเปิดช่อง UUID ของบัญชี/หมวดหลัง lookup ที่มีสิทธิ์เท่านั้น ก่อนหน้านั้นใช้ชื่อที่มีจริงเพื่อลดการแต่งรหัสอ้างอิง ทุกเส้นทางยังตรวจ workspace และยืนยันผ่านผู้ใช้ตามเดิม

### Debug ต่อ: รูปแบบร่างและราคาต่อรายการ

แยก JSON schema ของร่างเดี่ยวกับร่างหลายรายการเป็นคนละทางเลือก โดยทางหลายรายการต้องมี `transactions` และไม่มีช่องยอด/รายละเอียด/บัญชีของรายการเดี่ยวปนอยู่ที่ root ลดโอกาสที่โมเดลแก้รูปแบบผิดด้วยการทิ้งรายการย่อย ทั้งสองทางยังผ่าน validation เดิม และไม่เพิ่มเครื่องมือยืนยันหรือสิทธิ์เขียนให้โมเดล

คำอธิบายช่องยอดระบุหน่วยสตางค์และตัวเลขที่ติดคำภาษาไทยโดยตรง ส่วนหลายรายการระบุว่าต้องใช้ราคาของแต่ละชิ้น ไม่รวมเป็นรายการเดียว คำอธิบายหมวดให้เว้นเมื่อผู้ใช้ต้องการเลือกเอง รูปแบบเครื่องมือเริ่มต้นยังอยู่ในงบ regression เดิม: 8,974 bytes (เพดานทดสอบ 9,000 bytes) ไม่เพิ่มเพดานเพื่อให้เทสผ่าน

เพิ่ม live evaluation ให้ยืนยันร่างหลายรายการจริงแล้วตรวจว่าจำนวนรายการเพิ่มสองรายการและยอดรายจ่ายเพิ่ม 75 บาท พร้อมตรวจว่าการพิมพ์ยืนยันซ้ำไม่เพิ่มรายการ หากโมเดลเตรียมร่างไม่ตรงโจทย์จะบันทึกผลไม่ผ่านและยกเลิก ไม่ยืนยันร่างผิดเพื่อทดสอบขั้นถัดไป

เมื่อร่างที่ผิดมี array รายการอยู่แล้ว ทางซ่อม JSON ของ turn นั้นจะใช้เฉพาะรูปแบบ batch พร้อม feedback ให้คงราคาแยกและลบช่อง root ที่ปนมา ไม่เปิดทางให้ซ่อมโครงสร้างด้วยการทิ้ง array การละเลยรูปแบบจาก provider ยังต้องผ่าน validation/confirmation เดิม

พบเพิ่มเติมว่าโมเดลบางรอบอ่านยอดปัจจุบันด้วย `balances` แต่ใส่ช่วงวันหรือ metric รายจ่ายมา ระบบยังปฏิเสธตัวกรองที่ขัดกัน แต่เพิ่มข้อผิดพลาดแบบระบุช่องและคำแนะนำให้แก้ให้ถูกชนิดข้อมูล ไม่ตัดตัวกรองทิ้งเงียบ ๆ การซ่อม `fetch_finance` เฉพาะข้อขัดแย้งนี้ต้องเรียกเครื่องมือจริงและใช้ทาง JSON สำรองของ Ollama ได้ภายใต้งบเดิม ข้อผิดพลาดชนิดอื่นคง native continuation เดิม พร้อมเทสทั้ง stream/non-stream เพื่อป้องกันผลข้างเคียง

### Debug ต่อหลัง commit `ebe42a9`: เลือกหมวดเองและคุยต่อจากสลิป

เพิ่ม `category_choice=ask|auto` ในร่างที่โมเดลเตรียม เมื่อเป็น ask ระบบเก็บร่างและถามตัวเลือกจริง แทนการเติมจากหมวดที่โมเดลเสนอหรือกฎส่วนตัวเดิม การตอบชื่อหมวดที่ตรงเติมเฉพาะช่องเดิมและปล่อยสถานะรอเลือกโดยไม่เรียกโมเดล ส่วนคำตอบยาวที่โมเดลแปลงเป็น category_id จะปล่อยสถานะนี้เมื่อเป็นคำตอบเลือกหมวดใหม่ รองรับการเลือกทีละรายการใน batch และเก็บสถานะนี้เมื่อรวมหลาย tool calls ไม่ใช้ regex ตัดสินว่าเจตนาผู้ใช้จะเลือกเองหรือไม่

จัดลำดับคำแนะนำให้คำขอเลือกเองมาก่อนการเสนอหมวดอัตโนมัติ พร้อมตัวอย่างเปรียบเทียบขอเลือกเองกับขอให้ AI เลือก Tool schema ให้โมเดลตัดสิน `continue_draft` อย่างชัดเจนก่อนรายละเอียด เพื่อแยกการแก้ร่างเดิมจากรายการใหม่ การตัดสินยังเป็นของโมเดล ไม่มีการบังคับ merge จากการจับคำภาษาไทย Backend ยังรับ transport เก่าที่ไม่ได้ส่ง bool นี้ได้ตามเดิม

ตรวจข้อมูล **หลัง merge continuation** และสิทธิ์ของรูปก่อนส่งต่อไปสร้าง review รูปต้องอยู่ใน user message ของห้อง/workspace นี้ ไม่ยอมรับรูปจากอีกห้อง อีก workspace หรือ assistant message เท่านั้น กรณี array หนึ่งรายการใส่รูปไว้เฉพาะในรายการย่อย จะย้ายแหล่งภาพที่ระบุไว้อย่างไม่กำกวมมาใช้กับร่างเดี่ยวและตรวจสิทธิ์เดิม ถ้ารูป root/รายการย่อยขัดกันไม่เลือกแทนให้ การซ่อม array หนึ่งรายการไม่บังคับให้คงรูปแบบ batch จนกลับมาแก้ร่างเดี่ยวไม่ได้

ตัวเลขเก้าข้อความแรกมาจาก provider ทั้งหมด ลด input ราว 12% ในการรันคู่เดียว ไม่ใช่การรับประกันเวลาหรือ token สำหรับทุกข้อความ Full suite หลังแก้มีหนึ่ง request ที่หมดเวลาและ usage เป็นค่าประมาณ จึงไม่ใช้ผลรวมทั้งชุดเป็นตัวเลขประหยัด token ที่แน่นอน

- แชทให้โมเดลเลือกข้อมูลตามความหมายเดิม แต่ใช้ `render_finance {}` เพื่อแสดงผลที่อ่านแล้วได้ทันที ถ้าโมเดลเลือกแสดงรายงานแต่ส่งรูปแบบไม่ถูก ใช้ผลอ่านจริงแทนการเรียกซ้ำ ข้อมูลประกอบอย่างเดียวใช้แทนคำตอบไม่ได้
- แยกการขอช่วงเดิมจากการเดาวันใหม่ ถ้าไม่มีช่วงเดิมที่ใช้ได้จะไม่แทนด้วยเดือนนี้ ชุด `--focus breakdown` หลังปรับคำแนะนำเพิ่มผ่าน **8/8**: รายการ 4 รายการ รวม 372 บาท แยกเงินสด 235 และธนาคาร 137 บาท โดยยังเป็นวันเดิม เทสนี้เข้มกว่าการตรวจว่าเห็นชื่อบัญชีในรายการ
- การระบุหมวดที่ตรงกับชื่อหมวดของร่างที่รอตรวจ อัปเดตร่างเดียวกันโดยไม่เรียกโมเดล ช่อง null จากโมเดลไม่ล้างยอด/วัน/หมวด/รูปเดิม และไม่มีการบันทึกจนกว่าผู้ใช้ยืนยัน
- เมื่ออ่านสลิปแล้วแต่การทำร่างล้มเหลว ระบบยังคืนข้อมูลจากภาพที่อ่านได้และเก็บรูปเดิมสำหรับการคุยต่อ ชุด full รอบแรกเจอ timeout ในขั้นทำร่างและกู้รายการได้ในข้อความถัดไป ชุด backend ตรวจ fallback ใหม่นี้แยกต่างหาก จึงยังไม่ถือว่าอัตราการทำร่างสลิปสำเร็จดีขึ้น

ที่ยังต้องปรับ: บางสำนวนที่ส่งรายละเอียดก่อนแล้วเติมยอดในข้อความถัดไปยังถามหมวดเพิ่ม แม้หมวดจะพอเดาได้; การทำร่างจากสลิปใน Qwen 9B ยังมีความผันผวนด้านเวลา ไม่มีการเปลี่ยนข้อมูลหรือการตั้งค่า production

ตรวจผ่านหน้าแชทจริงบน Chrome ขนาดมือถือ: ส่งคำถามจาก composer, คุยต่อแยกบัญชี, แก้หมวดของร่าง, พิมพ์ยืนยันหนึ่งครั้งแล้วตรวจรายการเงิน และยืนยันซ้ำไม่เกิดรายการเพิ่ม ชุด PostgreSQL ผ่าน 984 เทสก่อนเพิ่มข้อความกู้สลิป และชุดที่เกี่ยวข้องกับสลิป ร่าง และการอ่านข้อมูลผ่าน 95 เทสหลังเพิ่มการกู้สลิป

บนโค้ดล่าสุด ชุด Qwen `--focus clarifications` ผ่าน **42/42** จาก 16 ข้อความและ 7 คำขอโมเดล รวมการเลือกหมวดเอง การคุยต่อจากสลิป และการยืนยันแบบไม่บันทึกซ้ำ ใช้ 23,428 input / 2,508 output tokens ที่ provider รายงาน ผลนี้เป็นของชุดเฉพาะ ไม่แทนผล full suite เดิม

### เติมยอดให้ร่างเดิม

ชุด `--focus draft-followup` ใช้บทสนทนาสั้นสามแบบ: ค่าข้าว ค่ารถ และผู้ใช้ขอเลือกหมวดเอง ตรวจว่าถามเฉพาะยอด เมื่อเติมยอดแล้วร่างยังรักษารายละเอียดและหมวด และไม่ลงบัญชีระหว่างทดสอบ

สำหรับ Ollama เมื่อร่างข้อความหนึ่งรายการกำลังรอยอด จะเรียกขั้นตรวจเพิ่มเติมได้ไม่เกินหนึ่งครั้ง: ใช้ยอดจากร่างที่โมเดลส่งมาและตรวจว่าข้อความล่าสุดเป็นคำตอบของร่างเดิมหรือไม่ หากหมวดขาด ใช้ตัวเลือกที่อนุญาตใน workspace เดียวกันเท่านั้น ถ้าโมเดลเพิ่งเปลี่ยนเป็น “ผู้ใช้เลือกเอง” ทั้งที่ร่างเดิมไม่ได้ตั้งไว้ ให้ตรวจคำตอบล่าสุดก่อนล้างหมวดเดิม ไม่เปลี่ยนตัวเลือกเองที่บันทึกในร่างเดิม และไม่เลือกแทนกฎส่วนตัวที่ตรง ใช้ข้อมูลร่างและตัวเลือกที่จำเป็น ไม่ส่งประวัติซ้ำ จำกัดคำตอบ 512 tokens และเวลารอ 12 วินาทีตามเวลาที่เหลือของงาน ถ้าตัดสินไม่ได้ให้ถามตามเดิม

การรันก่อนแก้ด้วย Thinking ค่าเริ่มต้นได้ 23/27: เคสข้าวถามรายละเอียดซ้ำ เคสแท็กซี่ถามหมวด และเคสเลือกหมวดเองหมดเวลาหนึ่งครั้ง การรันถัดมาใช้โปรไฟล์ทดสอบ Thinking ปิด จึงใช้ตรวจพฤติกรรมได้ แต่ใช้สรุปว่าความเร็วหรือ token ดีขึ้นจากโค้ดอย่างเดียวไม่ได้

โค้ดล่าสุดผ่าน PostgreSQL ชุดเฉพาะ 50 เทส และการเรียกตัวตัดสินกับ Qwen จริงโดยเตรียมร่างสมมติให้ครบเงื่อนไขผ่าน 5/5: เก็บหมวดเดิม (ไม่เรียกโมเดลเพิ่ม), เคารพการขอเลือกเอง, เลือกหมวดที่ขาด, ไม่ดึงร่างเดิมมาใช้กับรายการใหม่ และเชื่อมคำตอบกลับร่างเดิม สำหรับข้อความที่มีเพียงยอดและบัญชีที่ระบุชัด เช่น “ทั้งหมด 95 บาท ใช้เงินสด” การเก็บหมวดที่มีอยู่แล้วไม่ต้องรอโมเดล

อย่างไรก็ตาม การรันทั้งบทสนทนาบนโค้ดล่าสุดด้วย Thinking ปิดผ่านเพียง **24/27**: เคสข้าวยังถามผิดช่องตั้งแต่ข้อความแรก และเคสข้าวกับแท็กซี่ยังไม่ทวนร่างครบหมวดหลังตอบยอดในรอบนี้ กรณีผู้ใช้ขอเลือกหมวดเองผ่านและไม่มีการลงบัญชีอัตโนมัติ ผลตัวตัดสิน 5/5 จึงไม่ใช่ผลทั้งระบบ ขั้นถัดไปคือตรวจที่มาของยอดและการสร้างร่างตั้งแต่เทิร์นแรกก่อนแก้คำถามต่อเนื่องเพิ่ม

### ตรวจว่าร่างข้อความมีแหล่งยอดที่เป็นไปได้

ก่อนใช้ยอดที่ Ollama เสนอ ระบบตรวจข้อความจริงจากผู้ใช้ไม่เกิน 12 ข้อความในห้องเดิม ไม่นับตัวอย่างใน system prompt หรือคำตอบของโมเดล ถ้าไม่มีทั้งตัวเลข คำบอกจำนวน สลิปที่อยู่ในขอบเขต หรือผลอ่านที่มีจำนวนเงินจริง ให้ล้างเฉพาะยอดที่โมเดลเสนอและถามยอดต่อ ข้อความอย่าง “แปดสิบบาท” ยังใช้ได้ การค้นชื่อหมวดอย่างเดียวไม่ใช่แหล่งยอดเงิน และการพบตัวเลขในบทสนทนายังไม่ใช่หลักฐานว่ายอดตรงกับคำขอ จึงยังต้องให้ผู้ใช้ตรวจร่างก่อนยืนยัน

การรัน Qwen `--focus draft-followup --thinking none` หลังเพิ่มตัวตรวจได้ **26/27**: ทั้งข้าวและแท็กซี่ถามยอดก่อน แท็กซี่ 95 บาททวนพร้อมหมวดเดินทาง และคำขอเลือกหมวดเองยังทำงาน เคสข้าวยังถามหมวดเพิ่มหลังได้ยอดในรอบนี้ ไม่มีการลงบัญชีอัตโนมัติ ชุด PostgreSQL ที่เกี่ยวข้องบนโค้ดล่าสุดผ่าน **60 เทส** รวมกรณีรักษาคำจำนวนที่ผู้ใช้พูดและกรณีค้นชื่อหมวดแต่ไม่มีแหล่งยอด

รอบ Chrome ขนาดมือถือแรกถามยอดได้และทวน 95 บาทถูก แต่ได้หมวด “อื่น ๆ” แทน “เดินทาง” จึงเพิ่มการรักษาหมวดเดิมเมื่อข้อความมีแค่ยอดและบัญชี แม้โมเดลจะส่งหมวดอื่นมาทับ เทสล่าสุดผ่าน 61 ข้อในชุดที่เกี่ยวข้อง ส่วนการรัน PostgreSQL ทั้งชุดก่อนเพิ่มตัวตรวจกรณีทับหมวดครั้งสุดท้ายผ่าน 996 ข้อ

รัน Chrome ซ้ำหลังแก้การทับหมวด: แชทรับยอดแล้วถามให้เลือกหมวด จึงยังไม่ผ่านการทวนพร้อมหมวดอัตโนมัติ และหยุดการทดสอบก่อนยืนยัน ผลนี้บ่งชี้ว่าต้องแยกความตั้งใจเลือกหมวดจากคำขอต้นทางให้ดีกว่าเดิม โดยยังรักษาการเลือกเองที่ผู้ใช้ขอจริง

### ผูกการเลือกหมวดกับข้อความต้นทาง

ร่างที่รอข้อมูลเก็บ ID ของข้อความจริงที่เริ่มร่าง ไม่เก็บสำเนาข้อความเพิ่ม หากผู้ใช้ตอบเพียงยอดและบัญชีตรงกับร่าง แต่โมเดลเคยตั้งให้ผู้ใช้เลือกหมวด ระบบสามารถตรวจข้อความต้นทางร่วมกับคำตอบล่าสุดในคำขอขนาดเล็กเดิมได้ การตรวจเกิดเฉพาะสองข้อความผู้ใช้ที่ติดกันในห้องเดียวกัน ถ้าหาข้อความต้นทางไม่ได้ มีข้อความอื่นคั่น ข้อความยาวเกินขอบเขต หรือคำขอจริงระบุว่าจะเลือกเอง ให้รักษาการรอเลือกไว้ ไม่มีการข้ามไปอ่านห้องอื่น และยังต้องยืนยันก่อนลงบัญชี

รอบ Qwen จริงก่อนเพิ่มข้อจำกัดสองข้อความติดกันผ่าน **27/27** ในชุดเติมยอด: ข้าวและแท็กซี่ได้หมวดที่เหมาะ และกาแฟที่ขอเลือกหมวดเองยังรอคำตอบ ใช้ 7 คำขอโมเดลใน 10 ข้อความ โดยทดสอบด้วย Thinking ปิดบนข้อมูลสมมติ

การรัน PostgreSQL ทั้งชุดหลังเพิ่มขอบเขตข้อความต้นทางผ่าน **1,002 เทส** การทดสอบ Qwen แบบกว้างบนเวอร์ชันเดียวกันด้วย Thinking ปิดได้ **74/82** มีคำถามต่อเนื่องแยกบัญชีหนึ่งเคสที่ไม่ถึงเกณฑ์ และบางเคสเตรียมร่างกาแฟ รายการหลายยอด และคุยต่อจากสลิปไม่ครบ ยังไม่มีการลงบัญชีอัตโนมัติในชุดทดสอบ โปรไฟล์และจำนวนเกณฑ์ต่างจากรอบก่อน จึงไม่ใช่ผลเทียบตรง

Chrome พบคำตอบที่สัญญาว่าจะสร้างร่างแล้วถามยอดและวันที่ แต่ไม่ได้เรียกเครื่องมือ จึงเพิ่มการขอแก้หนึ่งครั้งเฉพาะเมื่อข้อความโมเดลสัญญาจะจดหรือทำร่างจริง ระบบให้โมเดลเตรียมร่างบางส่วนและถามเฉพาะช่องที่ขาด ไม่ได้ใช้ข้อความผู้ใช้จับคำเพื่อบังคับเส้นทาง เทสชุดที่เกี่ยวข้องหลังแก้ผ่าน **52 ข้อ**

โค้ดล่าสุดผ่านชุด backend เฉพาะ 57 เทส ส่วน Qwen ชุดเติมยอดได้ **26/27** และ Chrome ยังถามหมวดแท็กซี่หลังเติมยอด การตรวจงานมือถือพบว่าข้อความต้นทางถูกเก็บและมีการเรียกขั้นตัดสินจริง ดังนั้นปัญหาที่เหลือไม่ใช่แค่ร่างหลุดหรือขาดข้อความต้นทาง แต่เป็นการตัดสินหมวดที่ยังแกว่งระหว่างรัน ยังไม่มีการยืนยันรายการจากการทดสอบมือถือที่ไม่ผ่าน

### ผลลัพธ์เดียวสำหรับการเลือกหมวด

เมื่อจำเป็นต้องตรวจคำขอเลือกหมวดจากข้อความต้นทาง ให้ Ollama เลือกผลลัพธ์เดียวจากรายการที่อนุญาต เช่น หมวดใน workspace, เว้นให้ผู้ใช้เลือก, หรือเชื่อมกับร่างเดิมโดยยังไม่เลือกหมวด จึงไม่ต้องตีความผลสองช่องที่ขัดกัน เช่น เลือกหมวดแต่ตั้งให้ผู้ใช้เลือกเอง ไม่มีการส่ง ID บัญชีให้โมเดลหรือรับ ID จากโมเดลในขั้นนี้

Chrome ขนาดมือถือผ่านเคสแท็กซี่: ถามยอด ทวน 95 บาทเป็นหมวดเดินทาง ยืนยันหนึ่งครั้งสร้างหนึ่งรายการ ยืนยันซ้ำไม่สร้างเพิ่ม Qwen ชุดเติมยอดด้วย Thinking ปิดผ่าน **26/27** ในรอบเดียวกัน: ทั้งข้าวและแท็กซี่ได้หมวดเมื่อเติมยอด ส่วนเคสแท็กซี่ข้อความแรกมีหนึ่งรอบที่โมเดลถามวันที่เพิ่มและใช้ข้อความสัญญาทำร่าง แทนการถามยอดผ่านร่างจริง กรณีขอเลือกหมวดเองยังผ่าน

บนโค้ดล่าสุด PostgreSQL ผ่าน **1,009 เทส** และ Qwen โปรไฟล์ Thinking ค่าเริ่มต้นผ่าน **78/79** จาก 29 ข้อความ เทียบกับ **75/79** ก่อนแก้ด้วยโปรไฟล์เดียวกัน ข้อที่ไม่ผ่านคือเกณฑ์จับข้อความ “ยอดเท่าไหร่”: คำตอบจริงขอให้บอกยอดเงินและบัญชี และข้อความถัดไปเตรียมร่างได้ถูกต้อง เคสแยกบัญชี คุยต่อจากสลิป แก้หมวดโดยเก็บรูป และยืนยันรายการที่แก้ผ่านทั้งหมด

คำขอโมเดลลดจาก 36 เป็น 33, input tokens จาก 137,057 เป็น 127,557 และเวลาตอบมัธยฐานจาก 15.96 เป็น 10.78 วินาที ตัวเลขนี้เป็นการรันคู่เดียวบนข้อมูลสมมติ ไม่ใช่การรับประกันประสิทธิภาพ ทั้งสองรอบไม่ใช้ fallback โมเดลอื่นและไม่มีการลงบัญชีก่อนยืนยัน

ชุดแยกยอดตามบัญชีแบบเข้มบนโค้ดเดียวกันผ่าน **8/8** ด้วยโปรไฟล์ค่าเริ่มต้น โดยมี 4 รายการใน 2 บัญชีและตรวจยอดย่อยของแต่ละบัญชีในวันเดิม ไม่ใช้แค่การพบชื่อบัญชีในรายการเพื่อให้ผ่าน
